Latency Chain Mental Model

Every request crosses client → APISIX → Ingress(nginx) → Feature Platform → YugabyteDB / MySQL. Each hop has a dashboard. Memorize the chain; bisection becomes mechanical.

This is the deck's most-used slide. The tree is the actual order an experienced oncall walks. Start with Waiting because it's the cheapest read — high Waiting immediately scopes you to network/client side, no need to look at the other two. Only when Waiting is clean do you check Upstream. If both are clean but Response Percentiles is high, the latency is happening BETWEEN client→ingress and ingress→FP — that means infra layer (ingress controller, APISIX, recent config push).

Example 2 — Kafka Lag / MirrorMaker Triage

Two alertnames, two dashboards. Mixing them up is the #1 mistake — always reverse-match alertname first.

Alertname patternSevWhat it meansDashboard
MirrorMakerConsumerLagDecliningTooSlow PAGER MM2 replication slow. Decline-rate: (L5m − Lnow) / L5m < 0.3 AND Lnow > 500 MirrorLag v2 — -N7cUPZNk
Kafka_*_consumergroup_lag_High (cm / fp / detection / VelocityDetail_*) HIGH Business consumer group can't keep up. Per-client variants: galileo / onefinance / tabapay / wex … Kafka Exporter for all — cluster_kafkfa_exporter

4-step triage flow

  1. Read alertname. MirrorMaker* → MirrorLag v2. Kafka_*_consumergroup_lag_High → Exporter.
  2. Set variables. MirrorLag: cluster (group prefix, no -a/-b) / namespace / topic. Exporter: pod (binds to one cluster) / topic / consumergroup.
  3. Read the primary panel.
    MirrorLag: panel 1 (MM2 pod up) + 2/3 (lag a→b, b→a).
    Exporter: panel 12 Lag by Consumer Group (per cg + topic + partition).
  4. Diagnose root. ① MM2 pod down → restart (most common). ② Lag stuck + consumer offset rate ≈ 0 → consumer crashed. ③ Lag growing + producer rate > consumer rate → consumer can't keep up; compare Exporter panel 3 (produce) vs 4 (consume).
Caveats
  • MirrorMakerConsumerLagDecliningTooSlow namespace filter is hardcoded prod|pci|gov|demo — useastprod-style namespaces are not covered.
  • Default MirrorLag window is 30m — for alerts that fired 20-30min ago, expand to 1h to see the trigger trend.
  • cluster var in MirrorLag is kubernetes_cluster_groups (e.g. aws-uswest2-prod), without -a/-b suffix.
  • DV does NOT use MM2's default <source>.<topic> renaming — same topic name on both clusters, direction is in the source / target labels.
Kafka lag is the second-most-common alert family. The #1 mistake is opening the wrong dashboard — MirrorLag v2 is ONLY for MM2 replication; Kafka Exporter handles every other consumer group (including MM2 if it happens to be the lagging consumer). Always reverse-match the alertname before clicking through. The DV-specific topology note (same topic on both clusters, no renaming) is worth calling out — it surprises people coming from upstream Kafka docs.

5-Step Universal Oncall Workflow

Muscle memory: 1 → 1.5 → 2 → 3 → 4 → 5.

  1. 1

    Read the alert (don't query yet)

    Grab severity / cluster / namespace / ts / client / metric + threshold. Stop if any field is missing. Compute window: ts ± 3min (widen 2× if rule eval interval > 5min).

  2. 1.5

    Click the alert's source URL (orange)

    Drops you straight into vmui with the current value; pull window to 24h to check if it's chronic noise.

  3. 2

    Open the funnel-top dashboard

    Decided by alertname (see routing table on Slide 8).

  4. 3

    Bisect on the SLA dashboard using the 4 quadrants

    Order: panel 192/359 → 371 → 373 → 194.

  5. 4

    Drill into logs

    Window ±3min, use a time-pinned link.

  6. 5

    Write one-sentence hypothesis → one query to verify → then act (teal)

    Any K8s mutating op must be prefixed with # INTENT:.

These 5 steps are muscle memory. Step 1.5 is the easiest to skip but the biggest time-saver — vmalert's source URL drops you into vmui with the exact PromQL the alert was firing on.

TOP 5 Pitfalls

Five highest-step-rate pitfalls across SLA dashboard, Loki, PromQL, and Node Resource panels.

1. OOM uses container_memory_working_set_bytes

Not RSS, not usage. Pod Resources panel 14. working_set includes active anonymous + active file cache, which is what the cgroup OOM killer judges against.

2. After switching client on SLA dashboard, re-pick Batch_Pipeline

Switching client requires re-picking Batch_Pipeline/pipeline. The two variables aren't linked; the Batch row goes falsely blank and makes you think batch is offline.

3. gcp-uswest1-prod-a's Loki tenant is nonprod

The name misleads. When you script a query and forget LOKI_ORG_ID=nonprod, you get empty results.

4. Always add a cluster filter to PromQL

Unfiltered rate(kubernetes_monitoring_request_total_ingress_nginx[1m]) scans the whole table on VM, averaging 2.9 seconds per call — 117s of CPU per 10min.

5. Node Resource's $nodeHost must select a specific IP, not $__all

Otherwise it averages/sums all node metrics across the cluster, hiding single-node hot spots. Node-dimension panels are almost all aggregated by instance; All is self-deception.

These 5 have the highest step-rate. Full list of 20 pitfalls in REPORT §7, spanning SLA dashboard, Logging, Pod/Node, DB, and VM/alert — 5 domains.

Edit-alert workflow

  1. Sync-edit both yamls (VM primary, Prom backup)
  2. PR + lint CI → merge to main
  3. CI auto-syncs; visible in vmui Alerts/Groups within minutes
  4. Verify: search alertname in the vmui Alerts tab

Required labels for new rules

  • severity — currently 91 rules missing
  • team — currently 79 rules missing
  • Don't use alertname suffixes for per-client splits (e.g. _Affirm, _Nasa) — use the client label
VM is the primary alert rule set, Prom is compatibility backup — historical reason, you must edit both. New rules without severity/team labels route inaccurately and get dropped into the default channel.

30-Second Elevator Summary

Monitoring is three layers: metrics all in VictoriaMetrics, alerts all through vmalert (not Grafana managed), logs all in Loki multi-tenant.

When things break, dashboard order is decided by the latency chain: client → APISIX → ingress → fp → yuga/mysql.

First stop is always the SLA dashboard (p1KqfRAMk) — use panels 371 / 373 / 194 for bisection: fp slow, network slow, or client closed early.

Always add a cluster filter to PromQL. OOM uses working_set, not RSS. Node variables always pick a specific IP.
