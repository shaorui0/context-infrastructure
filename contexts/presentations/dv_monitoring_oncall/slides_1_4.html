Monitoring Stack Architecture (one picture)

Metrics all live in VictoriaMetrics, alerts all go through vmalert (NOT Grafana managed alerting), logs all live in Loki with multi-tenancy.

Metrics backend

VictoriaMetrics @ vm-mgt-a.dv-api.com. Deepflow-Prometheus as backup datasource.

Alerting

540 rules running on vmalert. Grafana managed alerting is not enabled.

Logs

Loki multi-tenant. tenant = prod / nonprod.

Emphasize "alerts all go through vmalert" — this is the #1 misconception for new oncall. Grafana's left-sidebar Alerting is empty; check vmalert UI or alertmanager for alert state.

Before Your First Page

Three things to memorize before pager goes off — entry URLs, severity SLAs, and the cluster-name → tenant trap.

Entry URLs

  • Grafana — grafana-mgt.dv-api.com (SSO + VPN)
  • VictoriaMetrics — vm-mgt-a.dv-api.com/vmui/ (raw queries)
  • Alertmanager — k8s-us-mgt-a.dv-api.com/alertmanager/ (silence ops)

Cluster naming trap

  • aws-*-prod-*, *-pci-*, *-mgt-*, *-sandbox-* → Loki tenant prod
  • aws-*-dev-*, *-preprod-* → tenant nonprod
  • ⚠️ Biggest trap: gcp-uswest1-prod-a has prod in its name but tenant is nonprod

Latency Chain Mental Model

Every request crosses client → APISIX → Ingress(nginx) → Feature Platform → YugabyteDB / MySQL. Each hop has a dashboard. Memorize the chain; bisection becomes mechanical.
