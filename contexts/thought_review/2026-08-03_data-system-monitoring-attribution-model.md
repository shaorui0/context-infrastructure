## Part 1 — Summary：讨论里达成了什么

我的原始输入是一份按工作内容展开的列表：监控（消费端行为 + 引擎侧压力 + 从 SLA 往下拆）、部署（HA、有状态与无状态、安全、调优）、容量规划与成本权衡。核心直觉有两条，都是对的：一是从 SLA 往下拆而不是从 CPU 往上堆，二是 oncall 的第一要务是快速回答「是谁的问题」。

ChatGPT 把它整理成 6+1 层分类：

1. Service Reliability（SLO 层，最上层）
2. Workload（查询模式、慢 SQL、扫描量）
3. Database Health（FE/BE/compaction/tablet/cache）
4. Capacity（预测三个月后会不会炸）
5. Change Management（变更可观测、可回滚、可恢复）
6. Disaster Recovery（HA、备份、RTO/RPO）
7. Operational Excellence（告警质量、runbook、自动化、复盘、error budget、混沌工程）

一句话收尾：数据库 SRE 的职责是持续保证 SQL 服务在成本可控的前提下，以可预测的性能和可靠性向用户提供服务。

## Part 2 — Review

### 2.1 值得保留的三点

**Workload 单独成层是这份回答里最好的判断。** 多数团队把 SQL 分析划给 DBA，把它划进 SRE 责任范围才对。因为分析型数据库的绝大多数事故是消费侧引发的，而消费侧的行为只有 SRE 有全局视角去测量。

**告警于症状、诊断于原因的分层方向正确。** 把 CPU/memory 从告警的第一现场移走，这个判断本身没问题。

**补上 Operational Excellence 是对的。** 系统本身的可靠性有天花板，团队的运维效率没有。

### 2.2 六个需要修正或补上的地方

**一，它是分类，不是路径。** 六层是并列关系，缺少因果链。真实 oncall 是有时间顺序的：先确认承诺是否被破坏，再判断责任归属，再决定短期止血还是长期治理。分类可以照抄，路径必须自己走一遍才有。这是整篇讨论里最重要的一个结构性缺陷。

**二，我提到的降级和过载保护被丢掉了。** 我原话是「你当前这个配置是否能够承受住，是否有对应的降级处理」，六层里没有任何一层承接隔离与过载。这对 OLAP 集群是第一现实问题：一个租户、一张 BI 看板、一个跑飞的 adhoc 查询就能打满整个集群。Doris 侧对应的是 workload group 的 CPU/内存软硬限、query queue、大查询熔断、单查询内存上限。结论可以说得更硬一点：**没有降级方案的容量规划是赌博**，因为容量总有被突破的一天，区别只在于突破时是有序退化还是雪崩。

**三，SLO 的定义方式套了 OLTP 模板。** 「P99 < 3s、成功率 99.99%」对分析型数据库不成立。OLAP 的延迟分布是多模态的：点查毫秒级，固定报表几十秒，adhoc 全表几分钟。把它们混进一个 P99，这个数字在该告警时不告警，在不该告警时乱抖。两条修法：按 workload class 或 workload group 分桶，各自定阈值；以及用 query fingerprint 的自身历史基线做相对劣化判定（同一指纹的延迟相对自身 P95 基线放大多少倍）。这里接我自己的四层模型：SLI 是「阈值内完成请求数 / 有效请求数」，quantile 只是观测视角，不要当 SLI 本体。

**四，缺 freshness 和 correctness 这一维，这是最大的漏洞。** Doris 是读写一体系统。导入侧（Stream Load / Routine Load / Broker Load / INSERT）延迟或部分失败时，查询照样成功返回，延迟也正常，返回的却是旧数据或缺数据。可用性和延迟全绿，业务已经在错的数据上做决策了。这是静默正确性故障，比宕机更难发现，因为没有任何红色指标。

我在 7-20 那份 SLO 笔记里已经建过这套谱系：请求驱动型服务看 availability/latency，数据管道型看 freshness/coverage，存储型看 durability/consistency。**关键认知是 Doris 同时是这三类系统**，所以 SLI 必须分组立，而不是只立一组查询 SLI。这一条是我能在 blog 里给出的最有增量的判断。

**五，列表病，没有数据源。** 回答里列了十几个 Top N（Top Slow SQL、Top Scan Bytes、Top Memory Query……），但没有说这些数从哪来、彼此什么关系。真正的地基只有一个：**FE audit log**。它是 per-query 的、可归因的、可离线聚合的，包含 scan rows/bytes、cpu time、peak memory、query state、user、db。把 audit log 通过 audit loader 落进 Doris 自己，workload 分析就从「盯 dashboard」变成「可以写 SQL 的历史资产」。

在 audit log 之上还有一个必须做的动作：**SQL fingerprint 归一化**（参数化后取 hash）。没有指纹，Top Slow SQL 每次都是不同的文本，无法聚合、无法看趋势、无法判断这次慢是不是回归。指纹是后面归因方法的前提。

**六，CPU/memory 在最下面这个说法要修正。** 作为告警源它们价值低，作为诊断证据和容量输入它们价值很高。正确的分野是告警于症状、诊断于原因，而不是资源指标不重要。很多人读完 SRE book 就把资源 dashboard 删干净了，等到 oncall 时手上没有证据。

### 2.3 关于容量三角

我问的是「latency、throughput 和 cost 吗」。更本质的答案来自排队论而不是工程经验：在 M/M/1 近似下等待时间随利用率按 ρ/(1-ρ) 放大，ρ 从 0.5 涨到 0.9，排队时间涨 9 倍，从 0.9 涨到 0.95 再翻一倍。

所以真正的三角是 **利用率（省钱）、延迟（P99 稳定性）、余量（抗突发能力）**，三选二。这不是工程水平决定的，是数学决定的。想同时要高利用率和稳定 P99，唯一的出路是把突发流量转化成可控的排队和降级，也就是第 2.2 条里那个被丢掉的维度。

### 2.4 变更管理的具体形态

「canary → observe → rollback」这个抽象对无状态服务成立，对数据库不够用。Doris 上最危险的变更是 schema change（触发数据 rewrite）、tablet rebalance、BE decommission、compaction 策略调整、版本升级中的 FE 元数据兼容性。

这些变更的共同特征是：**长时间运行的后台任务，且与在线查询争抢同一份 CPU、IO 和内存**。所以数据库变更可观测性的本质是后台任务的进度与资源占用可见（还剩多少 tablet 没搬完、当前占用多少 IO、预计多久结束、能否暂停），而不是通用的灰度回滚流程。回滚在数据库上经常是不可用的选项，能暂停和能限速比能回滚更现实。

### 2.5 DR 部分补两条

备份存在不等于能恢复，只有演练过的恢复路径才算数。FE metadata（bdbje editlog + image）是整个集群最致命的单点：BE 数据一份不少，FE 元数据丢了，集群等于不存在。RTO/RPO 写在文档里没有意义，需要定期真跑一遍并计时。

### 2.6 一个双方都漏掉的：监控系统自身的成本

per-tablet 粒度的指标在 Doris 上会直接导致基数爆炸。参考量级：单张 event_result 表就有 566 个 tablet，一个生产集群几十万 tablet 是常态。监控体系本身需要有基数预算，否则 SRE 会先被自己的 TSDB 打垮。

## Part 3 — 重构后的结构（blog 骨架）

用四层加一条贯穿线替换 6+1 分类。每层对应 oncall 时按顺序问的一个问题。

### 第一层 契约：我承诺了什么

三组 SLI，缺一不可，因为 Doris 同时是请求型服务、数据管道和存储系统。

查询可用性：成功返回的查询比例，把客户端语法错误从 valid 里剔除，把客户端超时单独盯住。

查询性能：按 workload class 分桶的「阈值内完成比例」，配合 fingerprint 相对基线的劣化倍数。拒绝全局单一 P99。

数据新鲜度与完整性：导入端到端延迟、分区应到未到、导入失败率。这一组抓的是查询全绿但数据是错的那类故障。

### 第二层 归因：坏了以后，是谁的问题

只有两个方向：需求侧变了，或者供给侧变了。这个二分能用 audit log 直接判定，不需要猜。

同一 fingerprint、扫描量不变、延迟变了，指向供给侧（集群资源、后台任务抢占、缓存失效、硬件降级）。

出现新 fingerprint，或旧 fingerprint 的 scan bytes / scan rows 暴涨，指向需求侧（业务上线、数据量增长、剪枝条件失效）。

所有 fingerprint 一起劣化，指向全局过载或供给侧。单一 fingerprint 劣化，指向该查询自身或它命中的数据分布变化。

这一层是整篇文章的核心，也是清单文给不了的东西。它把「是你的问题还是我的问题」从一句口号变成一条可执行的判定规则。

### 第三层 能力：我还能扛多久，扛不住时怎么退

容量规划的部分讲排队论三角，重点是利用率与 P99 的非线性关系，以及为什么按平均利用率做容量规划一定会翻车。

过载保护的部分讲隔离与降级：workload group 分租户、query queue 排队而不是拒绝、单查询内存上限、大查询熔断。核心论点是容量规划和降级方案必须成对出现。

### 第四层 变更与恢复：如何安全地改，以及改坏了怎么回来

把 Change Management 和 DR 合并。它们是同一件事的两面：系统状态发生非预期跳变之后如何收敛。合并之后解释力更强，也避免了两份互相脱节的清单。

重点是数据库变更的特殊性（后台任务与在线查询争资源、回滚常常不可用、能暂停比能回滚更现实），以及元数据备份的可恢复性验证。

### 贯穿层 运维效率

衡量标准不是有没有 runbook，而是几个可测的数：告警的动作率（多少比例的告警最终对应了一个人的具体动作，低于一半就是在制造噪音）、MTTD、MTTR、以及重复事故的比例。

## Part 4 — 写 blog 的关键点

### 4.1 主论点（thesis）

监控数据库的难点从来不是指标不够多，而是指标无法归因。一个可用的监控体系要能在故障发生的第一分钟把责任收敛到需求侧或供给侧，剩下的所有指标都是为这个判定服务的证据。

### 4.2 反直觉钩子（开篇用）

用 event_result 那个案例开场，它能一句话打掉读者对资源监控的信任：

4TB 宽表点查慢到 1.12 秒，此时 CPU 不高、内存不高、S3 带宽用了不到 1%，缓存全命中，零次远程读。任何以 CPU 和 memory 为核心的监控体系在这个故障面前全绿。真正的原因是查询没带分桶键和分区键，探遍了全部 566 个 tablet、6689 个 segment，时间全花在打开倒排索引 searcher 上。

这个案例同时证明了两件事：资源指标全绿而用户很痛是常态；per-query 的扇出与扫描量才是分析型数据库的一等指标。

### 4.3 可以直接搬走的硬核点

第一，OLAP 不能用单一 P99 立 SLO，因为延迟分布是多模态的。给出按 workload class 分桶和 fingerprint 相对基线两种替代方案。

第二，需求侧与供给侧的二分判定表（第二层那四条规则），这是全文最实用的部分。

第三，容量三角是利用率、延迟、余量，根源是 ρ/(1-ρ)，三选二。

第四，查询全绿但数据是旧的，这类静默正确性故障需要独立的 freshness SLI 才能抓到。

第五，FE audit log 加 fingerprint 归一化是 workload 可观测性的地基，没有它上面的一切都是拍脑袋。

### 4.4 差异化策略

互联网上「数据库监控必看的 N 个指标」已经饱和，纯方法论文章没有护城河。可用的护城河只有真实生产集群的案例：存算分离架构、4TB 宽表、扇出根因、缓存持久性的误判与纠正、加 BE 对点查无效这类反直觉结论。

建议配比：方法论四成，案例六成。每提出一个判断，紧跟一个自己踩过的证据。

### 4.5 避免的写法

不要写成「我总结的 X 层框架」。框架文的天花板低，读者读完点头然后忘记。改成按 oncall 时间顺序展开的叙事（收到告警的第一分钟看什么、第五分钟看什么、第一小时决定什么），读者可以直接搬进自己的 runbook。

不要把六层或四层平铺成小标题然后每层列十个指标。层与层之间的因果关系才是内容，指标本身是公共知识。

### 4.6 标题候选

「CPU 100% 不是故障：数据系统监控的归因链」

「运维一个数据库，到底在运维什么」

「查询很慢，但所有指标都是绿的」
