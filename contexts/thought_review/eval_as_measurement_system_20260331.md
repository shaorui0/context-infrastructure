# Eval 是质量度量系统设计，不是测试问题

**Date**: 2026-03-31

---

## 核心命题

Agent 评估的本质是质量度量系统设计，和 SRE 设计 SLI/SLO 是同一类工作。

但 SLI/SLO 有一个前提：failure mode 是已知的（延迟、错误率、可用性）。Agent eval 的真正难处在于 failure mode 本身需要被发现，输出空间是开放的、不可穷举的。所以它更接近 chaos engineering + SLO 的组合：先通过故障注入探索边界，再定义收敛标准。把 agent eval 当纯测试框架来做，卡住的原因往往就是这里——测什么本身就是未知的。


## 执行成本下降时，价值往哪里转移

这是个更普遍的模式：

每次执行成本大幅下降，价值就往「判断什么是好的执行」那一层转移。

- 编译器出现：汇编调优不值钱，算法设计变贵
- AI 写代码：打字速度不值钱，「这段代码是否正确解决了正确的问题」的判断变贵

代码 writing 被替代的是 translation layer（把想法翻译成代码），不是 engineering。工作的价值中心从 execution 移到了 specification 和 verification。


## 开放 process 的评价为什么是稀缺能力

封闭 process（输入输出完全确定）的评价可以自动化，写死在 CI 里。

开放 process 的特征：
- 输出空间不可穷举
- 失败模式不可预知
- 评价标准本身需要持续重新定义

在这种情况下，能把评价系统化的能力是稀缺的，因为它同时要求：
- 领域语义理解（什么叫对）
- 测量工程能力（怎么可重复地验证）

「拍脑袋说这个不好」不是工程能力。把判断转化成可执行标准、可度量指标、可追踪趋势，才是杠杆所在。


## 为什么 eval 天然抵抗自动化

Eval 工程的本质是把人的判断压缩进系统。

不能用 AI 来定义「AI 好不好」的标准——那是循环的。判断什么叫好，永远需要一个站在系统外面的人。

这使得 eval 层在 AI 替代浪潮里是结构性稀缺的，不是暂时的。


## 连接到 SRE 价值重估

上一篇（agent_sre_production_systems_synthesis_20260330.md）的结论是 SRE 能力和 agent 工程同构。

这篇的补充：当 AI 把 code writing 接管之后，剩下最值钱的恰好是 SRE 式能力，即测量、质量把关、架构决策、failure taxonomy。这不是偶然的，是因为 SRE 能力天然靠近「什么叫做对」的判断，而不是「怎么把它写出来」的执行。

懂得做质量度量系统设计的人，价值变高了，不是变低了。
