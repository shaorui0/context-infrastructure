# V06. 用工程化暴露对抗认知盲区

## 1. 核心公理

**认知盲区（unknown unknowns）是个人认知的系统性缺陷，不能用"更努力想"或"更多经验"去解决，只能用工程化的暴露机制去持续转化。**

把"想不到"当作个人智力问题，答案永远是"我再想仔细点"——这无法收敛。把"想不到"当作系统问题，答案变成"我需要一个能持续暴露未知的机制"——这可以工程化。

SRE 文化给这件事最漂亮的答案：**公开 postmortem + 主动 chaos + 定期 audit**。不假设你能主动想到所有失败模式，而是用**机制持续把未知转成已知**。这套思想不只适用于 SRE，是所有高不确定性领域的通用解。

## 2. 深度推演

### 2.1 认知盲区的分类（Rumsfeld 模型）

| 类型 | 含义 | 处理方式 |
|-----|------|--------|
| Known knowns | 你知道自己知道 | 执行 |
| Known unknowns | 你知道自己不知道 | 学习、查资料、问人 |
| Unknown unknowns | 你不知道自己不知道 | **这是本公理要处理的** |
| Unknown knowns | 你不知道自己已经知道了 | 反思、对话、外化 |

Unknown unknowns 的危险性在于：**你不会主动去找答案**，因为你不知道有问题。没有触发，就没有学习信号。

### 2.2 为什么个人努力解决不了 unknown unknowns

三个根本原因：

1. **你的思维模式本身就是盲区的来源**。你之所以想不到某件事，是因为你的心智模型把它排除在考虑范围外。同一个心智模型不会同时生成"盲区"和"盲区的解药"。
2. **检索机制失效**。Known unknowns 可以触发"我去查一下"——有一个明确的检索目标。Unknown unknowns 没有检索目标，搜索 "我不知道什么" 没有结果。
3. **时间一致性偏差**。你过去没撞到 X 问题，所以你不会为 X 准备——**直到 X 第一次发生**。但 SRE 领域的核心教训是：第一次发生时代价可能已经无法承担。

### 2.3 工程化暴露的四种机制

**机制 1：别人的失败当你的数据**

SRE 领域的 postmortem 文化是人类工程史上少见的"高质量失败共享"。AWS/Cloudflare/GitHub 每次大事故都写详细 postmortem，公开披露因果链和修复方案。

- 价值：用别人几百人几天的教训换你 20 分钟阅读
- 机制：**强制消费"我不会主动撞到的失败模式"**
- 泛化：证券市场"别人的爆仓录"、医疗的 case study、军事的战史研究，本质同构

**机制 2：主动制造失败（Chaos）**

不等故障发生，主动注入。

- Netflix Chaos Monkey、Google DiRT、Amazon GameDay
- 核心：**假设系统会以你想不到的方式失败 → 那就帮它失败一次，看看到底怎么失败**
- 重点不是"修复发现的问题"，是"暴露你从未想过的问题"

**机制 3：定期对照框架 audit**

这是最低成本的机制。只要有一个覆盖全面的 framework（如 SRE 7 层、OWASP Top 10、STRIDE），定期对照自检，**就能强制扫过你平时不看的角落**。

- 关键是 framework 要**涵盖完整维度**，不是只覆盖你熟悉的部分
- 没有对照物的"自我审视"=强化既有盲区
- 框架的作用是**借别人的脑子补自己的盲区**

**机制 4：Red Team / 外部视角**

主动请别人用对抗性视角看你的系统/计划/思考。

- 安全领域的 red team
- 投资决策的 devil's advocate
- 写作的 editor / peer review
- 本质：**借外部心智模型暴露内部盲区**

### 2.4 为什么"实践中学"不够

"边做边学"只能覆盖**你的系统实际撞到的问题**。这在两种情况下失效：

1. **长尾失败模式**：某些故障几年才发生一次，但发生一次代价极大。纯实践永远学不到
2. **新领域**：AI 系统很多失败模式整个行业还没撞到，等你撞到就已经在用户那里炸了
3. **环境变化**：去年学的教训可能因为 infra 变化不再适用；而新的失败模式正在别人那里发生

**结论**：实践只能教你 known knowns 的深化和 known unknowns 的解决。对 unknown unknowns 无效。必须引入外部暴露机制。

### 2.5 机制化比意志化可靠

依赖"我以后会更小心" = 依赖意志力。依赖"我每月 audit 一次" = 依赖机制。**前者随精力波动，后者稳定执行**。

工程化的关键是把"我应该想到"转成"我有流程会强制我想到"：

- 不靠记住要防范 BGP 错配 → 靠每次发布走 canary
- 不靠记住要检查内存泄漏 → 靠 monitoring 配 saturation alert
- 不靠记住有 10 种失败模式 → 靠每月过一次 framework checklist

### 2.6 与 V02（可验证性）的关系

V02 说：**要让错误可发现**（已知错误类型的可检测）。
V06 说：**要让未知错误类型可发现**（还没想到的错误模式的可暴露）。

V02 是 V06 的子集——V06 包括让"错误类型本身"可以被发现。两条合起来是完整的"信任工程化"：
- V02 处理：当错误按已知模式发生时，能否检测
- V06 处理：当错误按你还没想到的模式发生时，能否暴露

## 3. 应用判定

### 3.1 何时调用

- **做高不确定性领域的工作**：AI 系统、分布式系统、安全、投资、研究
- **你对一个领域有"自信"时**：自信本身是盲区的信号——你可能把 unknown unknowns 误判成 known knowns
- **重要决策前**：个人决策容易陷入单一视角，需要强制暴露
- **系统长期运行且稳定**：稳定期是盲区累积期，需要主动搅动

### 3.2 如何设计暴露机制

对任何你在做的系统/领域，问三个问题：

1. **别人在这个领域怎么失败的？** → 找公开失败案例，系统性读
2. **我能主动测试这个系统的失败边界吗？** → 设计 chaos / 压测 / red team
3. **有没有成熟的 framework 可以对照？** → 找、用、定期 audit

### 3.3 具体落地模板

**SRE/AI 系统**：
- 读 10 篇经典 postmortem（见 TODO/sre_postmortem_reading_list.md）
- 每季度做一次 gameday
- 每月过一次 SRE 7 问 checklist

**投资/决策**：
- 读《信号与噪声》《反脆弱》式的失败案例集
- 写决策前的 pre-mortem（假设决策失败了，是什么原因？）
- 定期请朋友做 devil's advocate

**写作/研究**：
- 读同领域的"失败论文"和撤稿案例
- 主动给对手派 reviewer 写 red team review
- 对照经典框架检查论证完整性

**个人成长**：
- 读别人的"我是怎么走错路的"（retrospective）
- 定期找背景差异大的人聊天
- 按成长 framework（如年度 retro 模板）定期 audit

### 3.4 反模式

- **只靠内省**：想再久也想不出 unknown unknowns
- **只靠经验**：经验只覆盖你已经历的失败空间
- **只靠聪明人**：聪明人的盲区更深（因为他们更自信）
- **不做 audit 的"持续学习"**：学新知识 ≠ 扫描旧盲区
- **用同一个思维伙伴**：同温层化，盲区会被共享放大

## 4. 常见陷阱

### 4.1 "我很聪明，我能想到所有情况"

智力高和盲区少不相关。历史上所有重大事故的事后分析都显示："聪明的人"事前都想过很多情况，但**他们想的维度和事故发生的维度不重合**。盲区不是思考深度问题，是思考维度问题。

### 4.2 "公开失败案例太极端，不适用于我"

**非极端的失败案例不会被写成 postmortem**。你读到的都是被重视的、典型的、教训深刻的。"不适用"通常是因为细节不同，但模式（哪一层失效、因果链长度、恢复难点）高度可迁移。读 postmortem 的正确方法是提取**模式**，不是**细节**。

### 4.3 "Audit 太形式化，做了也没用"

Audit 没用 = audit 设计得太浅。好的 audit checklist 的每一条都应该让你有三种可能答案：
- "有"（明确的证据）
- "没有"（这就是一个 finding）
- "说不清"（**这就是最有价值的 finding——盲区被暴露了**）

如果所有条目都能快速"有"，说明 checklist 太浅，需要下沉一层。

### 4.4 "Chaos 太危险，不敢做"

"不敢做 chaos"通常意味着你的系统已经脆到禁不起测试——这本身就是最大的盲区信号。**你不做 chaos，用户会帮你做**。分阶段：先从 staging 开始，从小爆炸半径开始，逐步拓展。

## 5. 实践案例

### 5.1 Google SRE 的三重机制

- **Postmortem**：每次 SEV1 必写，全司共享
- **DiRT**：每年系统性灾难演练
- **Error budget policy**：对照 SLO 定期 audit，烧光就冻结发布

三重机制互相覆盖：postmortem 是别人的教训，DiRT 是主动暴露，error budget 是定期扫描。**没有单一机制能覆盖所有 unknown unknowns，必须多重叠加**。

### 5.2 AI 系统的反面教材

典型的"AI 产品 3 个月崩盘"故事（见 T12 axiom）：

- 团队没读过任何 AI 失败案例（机制 1 缺失）
- 没做过 prompt injection / model downgrade chaos（机制 2 缺失）
- 没定期对照 SRE framework audit（机制 3 缺失）
- 结果：用户成为他们的 chaos monkey

**三机制全缺 = 把所有 unknown unknowns 都让用户去触发**。

### 5.3 个人决策的 pre-mortem

Gary Klein 提出的方法：决策前假设"6 个月后这个决策已经失败了"，然后反推失败原因。

这是个人决策层面的"工程化暴露"：
- 不是事后后悔
- 不是事前乐观
- 是**主动在事前把大脑切换到"失败已发生"的模式**扫描原因

### 5.4 投资领域的 Mohnish Pabrai

Pabrai 的"Dhandho 投资法"核心之一是**系统性研究失败案例**。他花大量时间读破产案例和亏损案例，不是为了研究赢家，是为了**建立自己的失败模式库**。

## 6. 与其他公理的关联

- **V02 可验证性** — V02 处理"已知错误类型的检测"，V06 处理"未知错误类型的暴露"。两者互补
- **T12 第一性 SRE 是 AI 系统的外壳** — SRE 方法论是 V06 最成熟的工程化实现，postmortem/chaos/audit 都是 V06 的具体机制
- **M01 闭环校准** — 闭环校准依赖"能收到反馈"。V06 扩展为"主动制造高质量反馈源"
- **M02 逆向调试心智** — 逆向调试是个人层面的 pre-mortem，V06 是把这种思维机制化、规模化
- **T08 第一性原理方法论设计** — 第一性原理要求质疑框架，而 V06 提醒即使质疑过的框架也可能有盲区，需要外部暴露

## 7. 结论

**想不到的事情不会因为你再想一遍就想到。** 认知盲区是结构性问题，不是努力问题。

个人层面的解法（更聪明、更谨慎、更有经验）会遇到天花板。机制层面的解法（暴露自己、对照框架、主动压测）可以持续扩展。

在高不确定性领域（AI、SRE、投资、安全、研究），能否建立自己的"工程化暴露流程"，决定了你的上限是你当前视野的大小，还是所有你可以接触到的外部视野的并集。

**暴露机制 > 个人聪明。** 这是工程化文化给认知谦逊的一个具体答案。
