# Skill: 数据系统监控归因模型（OLAP / 数据库）

## When to Use

设计或 review 一个数据库、数仓、分析引擎的监控与 SLO 体系时；oncall 收到「查询慢」类告警需要快速定责任方向时；被问到「运维 XX 数据库要关注哪些方面」时。

覆盖 Doris / ClickHouse / StarRocks 这类读写一体的分析型系统，多数结论也适用于 ES、Kafka 这类同时具备服务、管道、存储三重身份的系统。

## 核心判据

监控体系是否可用，用一个问题验收：**出问题时，能否在五分钟内判定该找写 SQL 的人还是该找管集群的人。** 答不出来，指标数量没有意义。

因此这套模型按 oncall 的提问顺序组织，而不是按系统模块分类。分类给的是清单，顺序给的是动作。

## 第一层 契约：我承诺了什么

数据库对外提供 SQL 服务，最顶层指标是这个服务的契约。三组 SLI，缺一不可，因为这类系统同时是请求型服务、数据管道和存储系统。

**查询可用性**：成功返回比例。客户端语法错误从 valid 剔除；客户端主动断开单独盯（往往是你太慢）。

**查询性能**：按 workload class 分桶的「阈值内完成比例」。对 adhoc 这类无法预分类的，用 query fingerprint 相对自身历史基线的劣化倍数。

> 陷阱：全局单一 P99 对 OLAP 无效。延迟分布是多模态的（点查毫秒 / 报表几十秒 / adhoc 几分钟），混在一起既会在该告警时沉默，也会在业务只是换了报表时乱抖。

> 口径：SLI = 阈值内完成请求数 / 有效请求数。quantile 是观测视角，不是 SLI 本体，否则 error budget 算不出来。

**新鲜度与完整性**：端到端导入延迟、分区应到未到、导入失败率。这一组抓的是**静默正确性故障**：导入侧延迟或部分失败时，查询照样成功、延迟正常、返回旧数据，可用性和延迟全绿而业务已经在错数据上做决策。这是最容易被漏掉的一组。

## 第二层 归因：是需求侧还是供给侧

oncall 第一个要收敛的是责任方向，不是根因。方向错了，后面一小时全是浪费。

**两个前置基础设施**（缺任何一个，本层退化为猜）：

1. FE audit log 落成可查询的表（per-query：scan rows/bytes、cpu time、peak memory、state、user、db）
2. SQL fingerprint 归一化（参数抹除后取 hash）

**判定表**：

| 现象 | 方向 | 典型原因 |
|---|---|---|
| 同一指纹，扫描量不变，延迟变了 | 供给侧 | 资源竞争、后台任务抢占、缓存失效、硬件降级 |
| 新指纹出现，或旧指纹 scan bytes 暴涨 | 需求侧 | 业务上线、数据量增长、剪枝条件失效 |
| 所有指纹一起劣化 | 供给侧 / 全局过载 | 集群级事件 |
| 单一指纹劣化，其余正常 | 需求侧 / 数据分布 | 该查询自身，或它命中的数据分布变化 |

没有 fingerprint，Top Slow SQL 每次都是不同文本，无法聚合、无法看趋势、无法判断是否回归。

## 第三层 能力：还能扛多久，扛不住怎么退

**容量的真实约束来自排队论**，不是加法。等待时间随利用率按 `ρ/(1-ρ)` 放大：0.5→0.9 排队时间涨 9 倍，0.9→0.95 再翻一倍。

权衡三角是 **利用率（成本）、延迟、余量（抗突发）**，三选二。按平均利用率做容量规划必然在峰值翻车。

**隔离与降级必须与容量规划成对出现**。手段：workload group 的 CPU/内存软硬限、查询排队（优于直接拒绝）、单查询内存上限、大查询熔断。

> 没有降级方案的容量规划是赌博。容量总会被突破，区别只在于突破时是有序退化还是雪崩。

## 第四层 变更与恢复

两者是同一件事的两面：系统状态非预期跳变后如何收敛。

**数据库变更的特殊性**：危险动作都是长时间运行的后台任务，且与在线查询争抢同一份 CPU/IO/内存（schema change 触发的 rewrite、tablet rebalance、BE 下线、compaction 策略调整、升级中的元数据兼容）。

所以变更可观测性的核心是**后台任务的进度与资源占用可见**：还剩多少未完成、当前占用多少 IO、预计多久结束、能否暂停、能否限速。在线服务那套灰度加回滚在数据库上经常不成立，**能暂停和能限速比能回滚更现实**。

**恢复侧**：备份存在不等于能恢复。FE 元数据是最致命单点（BE 数据一份不少，元数据丢了集群等于不存在）。RTO/RPO 需要定期真跑并计时。

## 贯穿层 运维效率

衡量标准是可测的数：告警动作率（多少比例的告警最终对应一个人的具体动作，低于一半即在制造噪音）、MTTD、MTTR、重复事故比例。

**监控体系自身需要基数预算**：tablet 粒度指标会打垮 TSDB（单表 566 tablet，生产集群几十万 tablet 是常态）。

## 资源指标的正确位置

CPU/内存作为**告警源**价值低（与用户痛感相关性弱）；作为**诊断证据与容量输入**价值很高。告警看症状，诊断看原因，是两条不同的指标链路。读完 SRE 方法论就删掉资源 dashboard 的做法，代价是出事时手上没有证据。

## 陷阱表（实测反例）

| 陷阱 | 实测反例 |
|---|---|
| 资源全绿即健康 | 4TB 宽表点查暖缓存零远程读仍 1.12s，CPU/内存/带宽全部正常，瓶颈在 566 tablet / 6689 segment 的扇出 |
| 慢就加机器 | 点查带 `LIMIT` 时并发退化为 1，落在单 tablet 单 BE，加 BE 与调大 scan 线程完全无效 |
| 剪枝能解决一切 | 宽表 `SELECT *` 有独立的列读放大，剪到单 tablet 仍 30s；扇出与列读放大正交，需两个正交动作 |
| 推断当事实 | 曾判定 file cache 重启即丢并据此提升级方案，现场核实缓存盘是持久卷且有 dump/replay，实测自暖 2%→61%，升级理由不成立 |

## 自检三问

1. 我的 SLI 里有没有「查询成功但数据是旧的」这类故障的检测能力？
2. 我能否在不登录任何一台机器的前提下，用一条 SQL 判定上次故障是需求侧还是供给侧？
3. 容量被突破时，系统的退化路径是什么？谁先被拒绝？
