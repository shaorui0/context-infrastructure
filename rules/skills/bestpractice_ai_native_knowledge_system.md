# AI-native 知识系统：Day-N 蒸馏优先

## 元数据

- 类型: BestPractice
- 适用场景: 个人知识库, AI 作为第二大脑, 多 Agent 共享记忆, 文档驱动开发
- 创建日期: 2026-03-26
- 来源: 多次对话 + ai_heartbeat 体系实践

---

## 核心判断

1. 知识系统的首要消费者是 AI, 不是未来的人类自己。
2. 知识管理的关键矛盾是 Day-0 捕获 vs Day-N 蒸馏。
3. 当前规模下的主要瓶颈通常是 distillation quality, 不是 retrieval speed。

## 设计原则

- 捕获阶段尽量零组织: 先把碎片写下来, 不强迫当场分类。
- 组织负担后置给 AI: 由 reflector/distiller 定期把碎片提升为可复用规则/框架。
- 信息密度优先: 少记, 但每条都能指导未来行动或决策。
- 为 AI 消费而写: 交付清晰的定义, 条件, 反例, 验证方式, 以及可复用的命名。
- 连接在检索时发生: 先让搜索/语义检索把相关片段拉出来, 再做归纳与抽象。

## 评估框架(六维)

- 捕获摩擦: 写入是否足够快, 会不会因为麻烦而不记录。
- 组织负担: Day-0 是否强迫你做高不确定性的分类决策。
- 检索能力: keyword/glob 是否能稳定找回语义相关内容。
- 连接生成: 系统是否鼓励跨主题的链接与复用。
- 消费者身份: 输出是否更利于 AI 复用(结构化, 可验证, 可引用)。
- 知识密度演化: 噪音是否会被周期性 GC, 规则是否会持续晋升。

## Flat files vs Vector DB: 什么时候升级

- 不要为理论上的先进升级。
- 触发条件更像是 recall 下降而不是速度慢:
  - keyword/glob 频繁 miss 明显相关内容
  - OBSERVATIONS + daily records 规模增长后, 检索结果噪音显著上升
  - 需要跨文档概念关联, 但命名/标签体系无法承载
- 推荐升级路径: Vector DB 作为 read-only 加速层叠加在 flat markdown 之上, 不替换。

## 直觉类比(用于解释)

把系统当作一个需要长期维护的环境: 先把环境搭好(路由/规则/GC 机制), 再持续投喂碎片, 最关键的是保持水质(信噪比)并定期收获(晋升)。
