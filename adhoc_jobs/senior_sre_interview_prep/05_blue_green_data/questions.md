## A. 发布策略选型（5 题）

### Q1. blue/green 和 canary 什么时候选哪个？

**一句定位**：分水岭不是「哪个更先进」，而是**小流量下的验证信号是否可信**，以及**新旧两侧是否共享一份持久数据**。这两个问题决定了选型，其他都是次要因素。

**展开结构**：
1. 先给两个判据，各一句：小流量信号不可信（有状态系统的资源画像只在真实并发下暴露）→ canary 是安全感表演，blue/green 加完整验证更诚实；两侧共享持久数据 → 走数据层切换谱系（`methodology.md` §4），blue/green 和 canary 都不足以描述这次变更。
2. 再补四个次要维度：资源能否短时翻倍、回退速度要求、流量可分割性、数据不可逆性（六维矩阵在 §1.2）。
3. 给自己的实例：K8s 升级用集群级 blue/green（有对侧可用，且 control plane 的健康不是小流量能验的）；同一次变更里 worker 用不可变 rolling，因为它无本地权威状态。**同一次变更里两种策略并存，依据是每一层的状态性质。**
4. 主动给边界：我做的是集群级切换与数据层切换，**不是渐进交付流水线**，没有「按比例放量 + 指标门禁自动推进」的生产实践。

**挂哪个故事**：S01（两种策略并存）+ S03（数据层切换为什么要用完整门禁而不是小流量 canary）。

### Q2. rolling update 有什么问题，为什么还要 blue/green？

**一句定位**：rolling 的根本问题是**没有干净的回退点**，回退本身也是一次 rolling，所以它的 MTTR 下限等于一次完整发布的时长。

**展开结构**：
1. rolling 的三个具体代价：新旧版本必须互相兼容（因为共存）；回退慢；出问题时「已替换的实例」和「未替换的实例」两种状态混在一起，定位困难。
2. blue/green 买到的是什么：一个**始终存在的已知良好状态**。回退是把流量切回去，不是重新部署。
3. 代价：资源近 2 倍、切换粒度粗（不能只影响 1% 用户）。
4. 我的实践里对这个取舍的具体处理：worker 用不可变替换加 20% batch，而在双集群流量前置转移的模式下 **20% batch 不再是保护用户的机制而是节奏控制机制**，因为用户流量已经完全移出这个集群了。这句话说明我理解每个机制在具体上下文里的真实作用，而不是照搬。

**挂哪个故事**：S01。

### Q3. 什么是 shadow / dark launch，你会在什么时候用？

**一句定位**：影子流量是**用真实流量形状验证新系统而不承担用户风险**的唯一手段，它的前提是写路径副作用能被隔离。

**展开结构**：
1. 机制：真实请求复制一份打到 green，结果丢弃或只做 diff。
2. 三个必须先解决的前提：写副作用隔离（不能真的改数据、发邮件、扣钱）、不可重放请求（一次性 token）的处理、结果不可比时的 diff 逻辑。
3. 拿不到的信号：用户主观体验、以及「green 承担全量后会不会被压垮」（影子流量通常只镜像一部分）。
4. 我的诚实边界：**没做过标准的影子读机制**。做过的是同一个论点的另一个版本：在提交不可逆的表布局之前，我挖了 14 天生产 `system.query_log`（7,470 万条日志行）来确定真实流量分布，结论把原设计推翻了（超过 90% 是点查，第二张 serving 表从「也许要」变成「必须要」）。**真实流量分布是设计输入，不是验证阶段的确认项。**

**挂哪个故事**：S02（日志挖掘替代影子读）。

### Q4. 你怎么设计一个渐进交付流程（progressive delivery）？

**一句定位**：⚠️ 这题我要先划边界：我做过集群级 blue/green 与数据层的双写门禁切换，**没有做过指标门禁自动推进的渐进交付流水线**。我能讲清它应该长什么样，也能讲清我手上具备哪几个环节、缺的是哪一个控制环。

**展开结构**：
1. 先给边界（上面那句），这一步不能省。
2. 我手上具备的环节：集群级的整体切换与切回（K8s 升级的双集群模式）、切换门禁的设计经验（监控栈换引擎时双写并行两周、逐条告警规则 diff 触发行为，门禁不过就不动通知路由）、回滚点显式保留（旧栈全程 live）。**缺的是「按比例放量 + 指标门禁自动推进 / 自动 abort」这个控制环。**
3. 如果要补，我会怎么设计：门禁指标必须是多窗口 burn rate 而不是瞬时阈值（小流量下瞬时指标信噪比太差）；每一档放量后的观察窗口要覆盖一个业务周期；abort 的判定要比 promote 的判定更灵敏（错误代价不对称）；每一档都要能人工中断。
4. `[外环]` 工具生态：Argo Rollouts、Flagger 这类把 analysis template 与自动 promote/abort 做成 CRD 的方案，我读过没上过，这是我明确的补课项。

**挂哪个故事**：S03（门禁设计）+ S01（整体切换与回滚点）。**这题的价值在于诚实分环，不在于答得漂亮。**

### Q5. feature flag 和 blue/green 是什么关系？你们有 feature flag 体系吗？

**一句定位**：两者解决的是不同层面的解耦：blue/green 解耦「部署」和「流量」，feature flag 解耦「部署」和「功能可见性」。**我有配置开关，没有产品级 feature flag 平台**，这个区分我要主动讲。

**展开结构**：
1. 概念区分一句：flag 让你可以先部署代码后开功能，粒度可以到单个用户；blue/green 的粒度是整个环境。
2. 我实际有的（中环，标准口径）：K8s 升级里按 `cluster_type` 分类加 **per-cluster feature flag** 表达残余例外，例如已知驱逐慢的集群把 drain timeout 从 300 秒调到 600 秒 (src: `p_k8s_upgrade.md`)；Doris fork 侧每个 feature 带 kill-switch 且默认 parity-safe，约 21 个阈值全部是可热调的配置项（`ADMIN SET FRONTEND CONFIG`，调参不需要重编译）(src: `contexts/resume_highlights_doris_dcluster.md`)；弹性控制面的两个 reconciler cron **默认关闭、可灰度开启** (src: 同上)。
3. 明确区分：这些是**运维配置开关与 kill switch**，不是按用户维度定向的产品 flag 平台（LaunchDarkly/Unleash 那类）。我没有做过 flag 的债务治理、按用户分群定向、flag 与实验平台的结合。
4. 一个我可以讲得很硬的相关设计判断：**kill switch 的默认值方向要按「哪个方向的错误代价更高」来定**。我的三个读信号是分别推理方向的：队列读或 readiness 读出错返回 0 或 -1（绝不误报 ready、绝不因不确定而扩容），idle 判定出错返回 false（绝不因不确定而回收）。**fail-safe 不是一个方向，而是对该操作避免代价高错误动作的那个方向** (src: `resume_highlights_doris_dcluster.md` §2.2)。

**挂哪个故事**：S01（cluster_type + flag）+ 引 Doris 侧 kill-switch 设计。

## B. 有状态与数据切换（6 题）

### Q6. 你怎么做一次零停机的数据库迁移？（必考题）

**一句定位**：核心骨架是**读切换和写切换分开、读先切，写切换是不可逆点，回滚窗口在停掉双写那一刻关闭**。我按十二环节走，其中最花时间的是对账和追平判定，不是搬数据。

**展开结构**（白板顺序）：
1. 画十二环节主干（`methodology.md` §0），标出 E09 是不可逆点、E10 的窗口在 E12 关闭。
2. 数据同步选型：同步双写 / 异步双写 / CDC 三种及各自一致性风险（§4.1）。给一句判断：**大多数生产场景默认异步双写，因为同步双写没有跨存储事务、并发顺序不同会产生永久分叉。**
3. backfill + 增量追平的收敛判定四层：lag 阈值 → 哨兵写入测端到端 → 行数/checksum 对账 → 业务语义验证（§4.2）。强调**门禁而不是观察**：我的实践是每个月的迁移做无损校验门禁，各切片行数之和必须等于重新计算的当月源侧总数，对不上就告警且这个月不标记完成 (src: `contexts/survey_sessions/ch_to_doris_migration_interview_arsenal_20260717.md`)。
4. 切换阶梯 P0-P5：影子读 → 灰度读 → 全量读 → 写切换 → 停双写 → 退役（§4.4）。
5. 回滚窗口的概念（§4.5.1）：**停双写是一个独立的、需要显式决策的变更，不是切换的自然尾巴。** 判据是 green 稳定跑满一个完整业务周期（含月末结算这类低频路径）且期间对账全通过。
6. 最后主动给自己的边界：我做过的是一次性批量迁移加逐月门禁加全量行数对账（S02），以及监控栈的双写并行加语义 diff 门禁（S03）；**没有在核心 OLTP 数据库上做过长期双写 + 灰度读写切换的完整流程**，这个区分我要讲清。

**挂哪个故事**：S02（对账）+ S03（双写与门禁）。

### Q7. 怎么验证迁移后数据是对的？（必考题）

**一句定位**：口径分三层（行数、checksum、业务语义），而**对账本身是一次生产变更，必须按生产变更来设计**，不是「跑个 SQL 看看」。

**展开结构**：
1. 三层口径各自能抓什么、抓不到什么（§4.3.2）。给一句判断：**行数做门禁、checksum 做抽样、业务语义对账做上线前最后一道人工确认。**
2. 全量 vs 采样的适用位置：全量用于一次性迁移的终态门禁，采样用于持续双写期间的常态巡检；采样必须按主键 hash 取模才均匀，按时间或自增 ID 取头尾会漏掉分布中段。
3. **对账会打挂生产**这一课：一条朴素的 `COUNT(*)` 审计打挂了全部 8 个 backend，根因是几十亿行的宽 Merge-on-Write 表上 `COUNT(*)` 要合并 delete-bitmap；改成按月分区分别计数并调高 `query_timeout` (src: `adhoc_jobs/dynamic_resume_site/content/case_study_ch_to_doris.md`、`ch_to_doris_migration_interview_arsenal_20260717.md`)。
4. checksum 前必须先对齐类型语义：浮点聚合顺序、NULL 语义、时区与精度截断，否则产出的全是假差异。
5. 一个更强的口径示例（S03）：对监控平台来说「数据正确」的业务定义就是「该响的告警响、不该响的不响」，所以我直接把口径定在**逐条告警规则的触发行为 diff**，跳过中间口径。

**挂哪个故事**：S02（三层口径与对账工程化）+ S03（语义级对账）。

### Q8. 你的对账率是 99.945%，剩下的 0.055% 是什么？为什么可以接受？（本方向最高频追问）

**一句定位**：差的是 **2,820,078 行**（源侧 5,173,508,562 行），机制是去重语义，**这是设计意图不是数据丢失**，而且能逐行归因。

**展开结构**（严格按这个顺序，四步）：
1. **先给绝对数不给百分比**。「0.055%」听起来像误差，「282 万行」听起来像事故，我主动给更难听的那个说法再解释，先建立可信度。
2. **构成机制**：目标表是 Unique Key 加 Merge-on-Write 按主键去重；源侧 ClickHouse MergeTree 不做主键唯一约束，同键多行可共存。源侧同键 N 行在目标侧收敛为 1 行。差额是「源侧存在的重复」，不是「目标侧缺失的信息」(src: `case_study_ch_to_doris.md`)。
3. **怎么证明是这个原因而不是别的**：在源侧按主键分组统计 `count(*) > 1` 的超出行数总和，看是否等于差额。能完整解释掉才叫逐行归因；解释不掉的余量必须单独调查。**这是「归因」和「找了个理由」的分界线。**
4. **为什么不做到 100%**：两条路都更糟（目标侧不去重会把数据质量问题搬过来且点查返回多行、业务语义错了；源侧先清洗是一个独立的有业务影响的治理项目，不该塞进迁移关键路径）。所以正确目标不是「行数相等」而是「差异可完整归因且归因结果符合设计意图」。**可接受差异的定义是机制已知且已量化，不是比例足够小。**
5. **追问才说的第五段**：跨引擎迁移的「合法差异清单」，必须在对账之前声明、对账时逐项排除：迁移窗口内源侧仍在写入（所以只对已封闭分区对账）、类型精度截断、NULL 与空值语义差异、稀疏宽表缺列被填默认值。**先声明再对账，而不是对完账再找理由。**

**挂哪个故事**：S02。

### Q9. 双写怎么做？同步还是异步？一致性风险在哪？

**一句定位**：三种形态（同步双写、异步双写、CDC），选择取决于能不能改业务代码和能容忍多大的一致性风险；**没有跨存储事务这一点是所有双写方案的共同前提。**

**展开结构**：
1. 三种形态的机制与风险表（§4.1）。核心判断：同步双写在写 A 成功写 B 失败时只能二选一（牺牲可用性回滚报错，或牺牲一致性记日志继续），并发写顺序在两侧可能不同产生**永久分叉**；异步双写把风险转成「lag 可观测 + 需要幂等写 + 同 key 走同分区保序」；CDC 零改代码但**schema 变更会直接打断它**。
2. CDC 风险的一手证据：一次 release 把 MySQL 某表从 4 列改成 2 列，CDC connector 缓存的旧 schema 与 binlog 不匹配导致崩溃，重启触发全量 snapshot，snapshot 的读类型事件没有映射 `_sign` 列，被 ClickHouse 的 NOT NULL 约束拒绝写入 (src: `adhoc_jobs/dynamic_resume_site/content/integration/oncall_track_record.md` 案例 3)。**一条故障链跨三跳**，所以上游 schema 变更必须按跨系统变更评审。
3. 我实际做过的双写形态（S03）：同一份 scrape 数据写两个后端，两侧同时评估全量告警规则再 diff 触发行为，修完分歧才切通知路由，旧栈全程 live 作为 fallback (src: `adhoc_jobs/dynamic_resume_site/content/projects/p_vm_platform.md`)。这个场景的特殊性是没有分叉风险（不是两库互同步），但有 push 模型丢数据风险，所以每个 vmagent 跑本地 persistent queue。
4. 诚实边界：**没有在核心 OLTP 上做过应用层双写**，也没用过 CDC 做迁移（只在 oncall 里排障过别人的 CDC 链路）。

**挂哪个故事**：S03（双写实践）+ oncall 案例 3（CDC 风险）。

### Q10. 有状态服务怎么做 blue/green？

**一句定位**：核心手法是**让状态离开被切换的单元**；存算分离是这个手法在数据库上最彻底的形态，但它不消除状态，只是把状态浓缩到一层。

**展开结构**：
1. 先说有状态为什么难，四个具体原因（§3.1）：数据复制不便宜、两侧同时写会分叉、quorum 约束并行度、驱逐顺序不是随机的。
2. 存算分离带来的三个可验证性质（这是我最想讲透的技术论点，§3.2）：
   - **节点替换安全**：BE 没有本地权威数据，杀节点不需要 `DECOMMISSION` 流程，这直接使「在 spot 上跑重查询池」可行（FE 心跳约 2 秒检测失联、锁约 7 秒释放、失败查询重试一次，全部落在 spot 的 2 分钟回收窗口内）(src: `contexts/resume_highlights_doris_dcluster.md`、`adhoc_jobs/dynamic_resume_site/content/projects/p_elastic_compute.md`)
   - **扩容零数据搬迁**：线上把 serving 池 2 台扩到 4 台，移动了零字节数据，tablet 归属只是元数据操作 rebalance 成 131/128/128/125 (src: `p_elastic_compute.md`)
   - **compaction 只处理单副本**，副本健康指标的权重跟着下降 (src: `ch_to_doris_migration_interview_arsenal_20260717.md`)
3. **同时给三条诚实边界**（不给这段就变成卖架构）：存算分离把状态浓缩到 MetaService / FoundationDB / S3 recycler 三个新的有状态失效域，而这一层恰恰不能偷工减料 (src: `case_study_ch_to_doris.md`)；缩到 0 的 compute group 可能留下 orphan lease 阻塞其他组的 compaction，说明「无状态」不等于「无注册状态」(src: `p_elastic_compute.md`)；弹性是分钟级不是秒级且冷 cache 有性能税（部分命中约降 10%、完全 miss 约降 35%）。
4. 通用降级手法表（§3.3）：状态外置到共享存储 / 外置到独立集群 / 用复制换切换窗口 / 用不可变替换换原地升级。**我的 K8s 升级正好是最后一行的实例：control plane 原地升级因为 etcd 在本地，worker 不可变替换因为状态已外置。**

**挂哪个故事**：S02/S01，Doris 弹性池细节引 `p_elastic_compute.md`。

### Q11. schema 变更怎么做到不停机？

**一句定位**：底层骨架是 **expand-contract（扩展-收缩，又称 parallel change）**：加新结构保留旧结构 → 切读并 backfill → 证明没有读者后才删旧结构；每一步之间要隔一次完整部署周期，因为部署本身不是原子的。

**展开结构**：
1. 三步骨架 + 「每步之间隔一个部署周期」的理由（滚动期间新旧代码共存）。
2. 常见翻车点四条：直接 rename 列（必然有一侧代码找不到列，正确做法是四次变更）；加 NOT NULL 无默认值列；加唯一索引（已有重复数据会失败，且大表上是长事务）；**忘了下游**。
3. 「忘了下游」的一手案例：上游把表从 4 列改成 2 列，三跳之外的数据落地断了 (src: `oncall_track_record.md` 案例 3)。**contract 步要求「证明没有读者」，就是为了防这个，而 CDC connector 是一类容易被漏掉的隐形读者。** 「证明」要用指标或日志，不是靠翻代码。
4. `[外环]` 工具生态明确标为补课项：gh-ost、pt-online-schema-change（影子表 + 触发器/binlog 追平 + 原子 rename）、pg_repack、Vitess 在线 DDL，我读过没上过。
5. 我在引擎侧知道的机制（可以显示深度但要说清它不是 OSC 工具经验）：Doris 存算分离下 schema change 与导入、compaction 竞争同一把 `delete_bitmap_update_lock`，高并发导入时容易长等待 (src: `ch_to_doris_migration_interview_arsenal_20260717.md`)；ClickHouse 上按租户动态演化的宽表落成数千稀疏列、靠脆弱的 `ALTER ADD COLUMN` 维护，这是我们离开 ClickHouse 的四个理由之一 (src: `case_study_ch_to_doris.md`)。

**挂哪个故事**：oncall 案例 3 + S02（宽表 schema 演化）。

## C. 跨集群切换（1 题）

### Q12. 跨集群切换时数据怎么办？

**一句定位**：转移流量的同时必须管**复制方向和复制进度**，而「等 lag 降回阈值」是切回去的前置门禁，不是切完再看的观察项。

**展开结构**：
1. 完整序列（S01）：流量全部切到对侧 → 暂停跨集群 Kafka 复制（双向都 scale 到 0）→ 升级已变 dark 的一侧 → 恢复复制**先启动接收流量那一侧** → 等 lag 降回阈值（切回 checklist 里写的是 B→A lag < 1000）→ 按 checklist 验证 → 切回流量 → 恢复双向复制 (src: `p_k8s_upgrade.md`；细节 src: `adhoc_jobs/dynamic_resume_site/knowledge_raw/runbooks/runbook-k8s-upgrade-plan-runbook.md` §1.4 / §6.2-6.5)。
2. 停复制期间反向 lag 上升**是预期行为**（写入都进对侧了），所以升级窗口长度实际被「停复制期间积压多少、恢复后追平要多久」约束着，这是容量问题不是时间问题。
3. 恢复顺序有讲究：先启动接收流量那一侧，让刚升级完的那侧数据新鲜度先追上来。
4. offset 的机制要讲清（高区分度）：镜像 topic 是改名的（`cluster_<src>.<topic>`，前缀常量 `cluster_`，消费侧反序列化剥前缀），消费者同时订阅 local 加 mirror；**consumer group 与 offset 在两个集群是完全独立的两份 state**，所以切换不需要搬 offset。⚠️ 我**没有**用 MirrorMaker 2 的 offset translation，如果要做「同一个 group 从 A 无缝续到 B」才需要它，那是我没做过的场景。
5. 追平能力是硬约束（S04）：某租户 QPS 增长超过 topic 仅 3 个分区能承载的复制吞吐，**每分区吞吐是复制并行度的硬天花板**，加机器无效；扩分区是不可逆操作，需先评估 key 分布 (src: `oncall_track_record.md` 案例 4)。所以切换前要算：待追平量 ÷（每分区吞吐 × 分区数）是否落在窗口内。

**挂哪个故事**：S01 + S04。

## D. 回滚与风险控制（5 题）

### Q13. 切换失败怎么回滚？（必考题）

**一句定位**：回滚设计必须回答三个问题：**回滚到哪（回滚点）、还有多久能回（回滚窗口）、什么条件触发（触发器）**。第二个问题最容易被漏掉，也是数据层切换的关键。

**展开结构**：
1. 三问框架先给出来。
2. 回滚点按层设计（S01 的一手实例）：control plane 回滚 = etcd snapshot 恢复**加**二进制降级（因为 snapshot 恢复的是数据不是二进制，这个区分很多人答不出）；worker 回滚 = 停止 ASG Instance Refresh 并回退 Launch Template；addon 回滚 = `kubectl rollout undo` (src: `p_k8s_upgrade.md`)。
3. 触发条件**事前写死**：master 升级失败、超过 50% pod 非 Running、关键服务不可达、告警洪水 (src: 同上)。**事前声明的价值是把「要不要回滚」从事故当中的判断题变成查表题**，因为事故当中的人会倾向于再试一次。
4. 数据层的回滚窗口（§4.5.1）：写切换到 green 之后，只要 blue 还在接收双写，回滚就是把写切回去、代价接近零；**一旦停掉 blue 侧双写，回滚从「切回去」变成「把 green 这段增量反向搬回 blue 再切回去」**，代价从秒级变成小时级，且可能不可行（green 的新 schema 数据未必能表达成 blue 的旧 schema）。所以停双写是独立决策，判据是 green 稳定跑满一个完整业务周期且期间对账全通过；停双写后 blue 转只读保留一段时间再 drop。
5. 一条 oncall 沉淀的操作规则：**容量受损时先回滚到已知良好的 launch template 或 AMI 恢复容量，然后再追根因** (src: `oncall_track_record.md` 案例 8)。止血优先于归因。

**挂哪个故事**：S01（分层回滚）+ S03（旧栈 live 作为回滚点）。

### Q14. 有没有不能回滚的情况？你怎么处理？

**一句定位**：有，而且**主动识别不可逆点并给它额外买保险**，是我认为切换设计里最能区分资深程度的一件事。

**展开结构**：
1. 不可逆点清单：分布键/分区键（很多引擎不能 ALTER）、压缩与编码格式、主键语义（是否去重）、停掉双写、drop 旧表、Kafka 分区数扩容（只能增不能减，且改变 key 到分区的映射所以顺序保证在扩容点前后不同）。
2. 我的两个一手处理方式：
   - **对不可逆点额外买保险**：分布键是唯一一个后续不能 ALTER 的决策，所以做了两表 A/B（同样的数据、镜像的键、四次测量）才提交；并在迁移中的三个检查点（15M → 107M → 286M 行）重测延迟，证明表增长 19 倍延迟仍平坦 (src: `case_study_ch_to_doris.md`)。
   - **把不可逆操作显式标注并交给 owner 评审**：分区扩容标为不可逆操作、需先评估 key 分布与 consumer rebalance 影响 (src: `oncall_track_record.md` 案例 4、`adhoc_jobs/dynamic_resume_site/knowledge_raw/cases/case-kafka-mirrormaker-lag-tabapay-partition-bottleneck.md`)。
3. 一类「可以自动切走但不能自动切回」的判断 `[理论]`：故障场景下把流量切离故障侧可以自动化，切回去通常不行，因为探测只能证明「现在探得通」，证明不了「根因已消除」。自动切走的错误代价是流量落在健康侧，自动切回的错误代价是流量落回可能仍在故障的一侧，**两个方向的错误代价不对称，所以自动化的方向也不对称**。工程上的落地形态是给切换动作带一个到期时间，到期不做自动回滚，而是强制人做一次决策。
4. 收一句原则：**fail-safe 不是一个方向，而是对该操作避免代价高错误动作的那个方向。**

**挂哪个故事**：S02（A/B 定布局）+ S04（分区扩容）。

### Q15. 切换前后你会对比哪些指标？怎么判断切换成功？

**一句定位**：判断标准不是「绝对值达标」，是「**和切换前落盘的 baseline 逐项 diff**」；而且验证必须覆盖 **infra 健康与业务正确性两层**，只验一层是最常见的失败模式。

**展开结构**：
1. 两层验证的框架先给（§5.1）。infra 层容易做也容易给虚假的安全感；业务层才是决定性的。一手实例：K8s 升级明确要求验证范围覆盖业务层正确性不止 infra 健康 (src: `p_k8s_upgrade.md`)；VM 平台的门禁是每条告警规则在两侧同时评估、diff 触发行为，且 dashboard 查询在 MetricsQL 下返回等价结果 (src: `p_vm_platform.md`)。
2. 七类信号清单（§5.2）：流量（按 endpoint/租户分解，总量看不出「少了一块」）、延迟（分冷热分类型）、错误（错误码分布比错误率更早暴露问题）、饱和度、数据（复制 lag 与两侧写入增长曲线**都要看**）、正确性（业务关键查询结果 diff）、元层（监控自身活着）。
3. **对比而非绝对值**：post-verify 重跑完整 check 与落盘 baseline 做 diff，对比的是落盘 baseline 而不是工程师的记忆 (src: `p_k8s_upgrade.md`)。
4. **baseline 本身可能是错的**：所以 check 结果要与外部监控交叉验证，专门防御这一失效模式 (src: 同上)。同一思路的另一实例：一条 P99 告警声称越限但应用日志与 APM 都干净，调查第一步是**先证伪真实用户影响**再解释指标（多实例采集时间错位叠加 histogram 分桶聚合偏差把 P99 虚高）(src: `oncall_track_record.md` 案例 7)。
5. 元层单独强调：切换监控系统时，「没有告警」既可能是一切正常也可能是全都坏了，必须有 out-of-band 手段区分（vmalert 心跳 + deadman's switch + 独立探针）。推广成一句：**任何切换都要问「验证这次切换的那个系统，本身在切换范围内吗」。**

**挂哪个故事**：S01（baseline diff 与交叉验证）+ S03（元层与语义验证）。

### Q16. 自动化的切换怎么保证不失控？

**一句定位**：**事前有审批、事中有幂等与状态、事后有证据**。自动化程度越高，治理要求越高，这不是矛盾而是配套。

**展开结构**：
1. 三段治理框架先给。
2. 事前 `[理论]`：高权限的切换动作要有显式的审批态（草稿 → 已批准 → 生效），任何变更强制回到未批准状态重走一遍；目标地址这类关键参数应当从系统里自动填充而不是接受手工输入，因为人因错误是这类自动化最常见的失效源。
3. 事中（S01）：K8s 升级每步落状态文件（completed / in-progress / pending），中断可从状态恢复、幂等步骤直接重跑 (src: `p_k8s_upgrade.md`)。`[理论]` 切换动作本身要做成读实际状态、比目标状态、upsert 的声明式幂等操作，而不是 delta 操作，因为 delta 在重试下会叠加。
4. 事后（S01）：落四类 evidence（结构化 JSON 健康快照、plan diff、完整执行日志、每步状态文件），任何一次执行都能事后复盘 (src: 同上)。
5. 人工闸门放在哪：K8s 升级保留在四个位置（check、plan、每一台 master、最终 post-verify），且任何集群失败就全局暂停、人工批准才继续 (src: 同上)。**闸门位置的选择原则是放在不可逆点之前和 blast radius 跃升之前。**
6. 一条我会主动给的设计判断 `[理论]`：配置或规则要分发到大量节点时，用 reconcile 拉取模型而不是 best-effort 推送。推送失败的节点会长期停在旧视图上而系统不主动收敛，拉取模型让每个节点自己负责追上期望状态，视图不一致是可收敛的而不是永久的。

**挂哪个故事**：S01（门禁、状态文件与 evidence）+ S03（门禁不过就不动不可逆点）。

### Q17. 切换类操作最容易在哪翻车？

**一句定位**：我整理过一张 20 条的失败模式清单（`methodology.md` §6），排前三的是**误切（假阳性）、切换不幂等被重试放大、回滚窗口已经关了才发现问题**。

**展开结构**：挑四到五条讲，每条一句表现加一句止血。
1. **F01 误切**：网络抖动被放大成故障切换 → 三态判定 + 超时算 UNKNOWN + 连续 N 次 + 跨点聚合。
2. **F02 不幂等**：delta 重试叠加 →一切收敛到声明式 upsert。
3. **F06 回滚窗口已关**：双写早停无法切回 → 停双写作为独立变更决策，要求 green 跑满一个完整业务周期。
4. **F07 对账打挂生产**：一条 `COUNT(*)` 打挂全部 backend → 按分区拆、限并发、设超时，把对账当生产变更设计。
5. **F09 差异用比例糊过去** → 可接受差异的定义是机制已知且已量化，不是比例小。
6. **F05 green 看起来健康其实是空的**：`SELECT 1` 被 FE 常量折叠、从不下发到任何 backend，空的 compute group 也会被报告为健康 → 探针必须走数据面（`SHOW BACKENDS` Alive + 触达存储的 canary），且要数到 N 不是数到 1 (src: `p_elastic_compute.md`)。
7. **F12 长连接不跟着切**：权重改了旧连接还在打老侧 → 盘点各跳 idle timeout，最短的一跳决定行为。一手证据：一条连接空闲 **431 秒**后被杀而 MySQL 的 `wait_timeout` 是 8 小时，所以凶手只能是中间网络层的 TCP idle timeout，用 heartbeat 加 keepalive 绕开 (src: `oncall_track_record.md` 案例 3)。

**挂哪个故事**：全部，按对方追的那条挑。这题是展示「我有清单不是有故事」的最好机会。
