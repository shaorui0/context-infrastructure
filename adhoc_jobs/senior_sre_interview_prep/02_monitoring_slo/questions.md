## A 组：可观测性架构设计（6 题）

### A1. 请设计一个 50 个 Kubernetes 集群、多 region 多合规域的监控体系。

**一句定位**：核心决策只有一个，就是「集群内 pull、跨集群 push」，因为分层 pull 的延迟是叠加的、而中心聚合的内存是不可分摊的，这两个问题都不是配置能解决的。

**展开结构**：
1. **先给约束再给方案**：50 集群、约 600 节点、每节点约 2,000 series，推出约 1.2M active series 和约 80K samples/sec，15s 采集间隔。多 region 多合规域（含 PCI 域和一个 GCP 集群）意味着网络边界多，中心不可能 pull 到每个 target。
2. **架构**：每集群一个 vmagent 在集群内 pull（保留服务发现与 `up` 的好处），relabel 阶段注入 `cluster` 和 cluster group，remote_write 加本地 persistent queue 推到中心 VM；vmalert 在同一存储上评估 recording 与 alert rules；Alertmanager HA 做路由；Grafana 加 Loki 构成读取与验证面。
3. **容量与分层存储**：热存储 SSD 3 个月约 250GB（约 4 倍压缩），冷存储 S3 5 分钟降采样 180 天约 25GB。
4. **必须一起设计的三件事**：label 一致性（inhibition 和路由都依赖 label 相等匹配）、cardinality budget（第一天就要有）、deadman's switch（监控必须能报告自己失效）。

**挂故事**：S01 主线，S02 补 label 与 SLI 物化。知识点 Q9 / Q10 / Q13。

### A2. 为什么不用 Prometheus Federation？

**一句定位**：Federation 的 45 秒延迟和每周 OOM 是架构属性不是配置属性，任何调参预算都修不好。

**展开结构**：
1. **四条结构性问题**：global Prometheus 的 head block 要在内存维护全局 1.2M series 占 5 到 10 GB（每周 OOM 两三次，重启留数据空洞误报 oncall）；两层 scrape 叠加 15s + 30s 使全局视图最多滞后 45 秒；`/federate` 在 50 集群负载下 scrape timeout 造成 Grafana 断点；每集群各维护 federation rules，新集群接入要手工改全局配置。
2. **哪一条最贵**：不是延迟，是数据空洞造成的假告警，因为它直接制造 alert fatigue。
3. **迁移后的数字**：lag 45s → <5s，OOM 每周 2-3 次 → 0，热存储 930GB → 250GB，新集群接入从「写 federation rules 加改全局 scrape」变成「部署 vmagent 配一个地址」。

**挂故事**：S01。知识点 Q10。

### A3. VictoriaMetrics、Thanos、Mimir 你怎么选？

**一句定位**：这是一个规模匹配的决策不是优劣判断，我们选 VM 的决定性维度是运维复杂度，因为 3 到 4 人的团队里这不是次要维度而是主要维度。

**展开结构**：
1. **先说我的证据强度**：我做了 VM 与 Thanos 的 POC（写入吞吐、压缩率、运维复杂度），最终是团队共识。**我没有在生产运维过 Thanos 或 Mimir**，所以我的对比是 POC 加架构分析。
2. **Thanos 那套复杂度买的是什么**：无限廉价的 object storage 长期存储加跨集群 PromQL 全局查询。我们的需求是热 3 月加冷 180 天降采样，本地 SSD 加 S3 覆盖了，买不到对应价值，而组件数（sidecar / store gateway / querier / compactor）换来的故障面是实打实的。
3. **什么情况我会重新评估**：有专职 observability 团队、需要保留两年原始精度、或已深度绑定 Prometheus 生态。
4. **VM 的具体收益**：压缩约 4 倍、vmagent 专职采集自带 persistent queue、MetricsQL 是 PromQL 超集（代价是边界差异，这是我们必须双写验证的原因）。

**挂故事**：S01 的 L4。知识点 Q12。
⚠️ 不要说「VM 比 Thanos 好」，一定要说规模匹配；不要暗示有 Thanos 运维经验。

### A4. 多租户平台的监控怎么设计？租户维度怎么加进来？

**一句定位**：tenant 身份必须走两条路径注入，应用侧打 tenant 标签、采集侧 relabel 打集群上下文，而这件事的真正难点不是打标签，是让 50 个集群的 label 命名一致。

**展开结构**：
1. **为什么要这个维度**：aggregate 指标掩盖局部故障，单个租户的问题消失在平均值里，导致「哪个客户在受影响」这个最重要的问题无法回答。
2. **两条注入路径**：应用在自己的 metrics 上打 `tenant`（只有应用知道在处理谁的请求），vmagent 在 scrape 时 relabel 注入 `cluster` 和 `kubernetes_cluster_groups`。合起来一条 series 同时携带应用层和基础设施层的身份，于是 recording rules 能按 `{tenant, cluster_group}` 聚合、alert 能按 tenant 单独触发、dashboard 能下钻 tenant × region × service。
3. **真正的工作**：项目之前各集群 relabel 各自为政，cluster 命名不统一、部分团队用 `client` 而不是 `tenant`，这会**悄无声息地**破坏告警路由、drill-down 和 inhibition 的 label 相等匹配。我写了统一的 relabel 模板分发到所有集群，并推动应用侧收敛到 `tenant`。
4. **代价与治理**：cardinality。四条控制手段加一句诚实的复盘（budget 应该第一天就有）。

**挂故事**：S02。知识点 Q6 / Q7 / Q23（label 一致性是 inhibition 的硬前提）。

### A5. metrics、logs、traces 你怎么分工？成本怎么控？

**一句定位**：metrics 负责发现，logs 负责证明，trace 我没有跑，这是我明确的补课项。

**展开结构**：
1. **成本模型的本质区别**：metrics 的成本和请求量几乎无关（1 QPS 和 10K QPS 的 series 数一样），随 series 数乘采集频率乘 retention 增长；logs 和 traces 的成本和请求量成正比。这决定了 metrics 可以全量常开，logs 和 traces 必须做采样或保留期取舍。
2. **我的具体分工**：histogram 触发告警（快、便宜、可高频评估），LogQL 从原始 access log 提取请求级真实延迟做交叉验证。LogQL 明确不做实时告警基础，因为依赖日志格式稳定、全量扫描慢、高流量下采样影响准确性。
3. **为什么必须交叉验证**：histogram 的插值误差在两个方向都会咬人。举 histogram P99 = 800ms 而 LogQL P99 = 2.3s 这个例子。
4. **trace 的缺口和替代**：我用 nginx 的四个时间字段做 ingress 这一跳的粗粒度 span 分解，覆盖率 100% 不采样，但看不到后端内部。补课方向是 OTel、tail sampling、以及 exemplars 补上「metric 报高延迟但找不到是哪条请求」这个缺口。

**挂故事**：S06 主线，S04 补分段分解。知识点 Q27 / Q28 / Q29。

### A6. 监控系统自己挂了怎么办？

**一句定位**：目标不是「VM 挂了告警照常」，而是分钟级告诉 oncall 数据不可信、走降级路径，因为一个不能报告自己失效的监控系统会让「没有告警」和「一切正常」在信号上不可区分。

**展开结构**：
1. **两层保障**：Alertmanager HA 双实例加通知通道冗余；deadman's switch，vmalert 持续输出必然为真的心跳，下游收不到就触发「监控失联」；再加一个 out-of-band 探针独立监控关键接口，不依赖同一条链路。
2. **为什么放弃「照常工作」这个目标**：要做到那个程度需要一套完全独立的第二监控栈，成本远超收益，而且第二套栈自己也需要 deadman。所以正确的目标是可检测的失效加明确的降级路径。
3. **同一个原理的另一个形态**：Loki 的 LogQL pattern 在 ingress 格式变更后静默失效，查询不报错只是返空，「没有数据」被误读成「没有问题」。所以我的原则是每一条依赖解析的关键查询都要有配套 canary 证明管道活着。

**挂故事**：S01（deadman 是切换门禁的一部分）、S06（pattern 静默失效）。知识点 Q13 / Q33（Detection 项塌到 0）。

## B 组：SLO 与告警制度（6 题）

### B1. SLI、SLO、SLA 有什么区别？你怎么定义 SLI？

**一句定位**：SLA 是承诺、SLO 是内部目标、SLI 是测量，而我真正开始懂它们不是因为读书，是因为从 demo 环境换到 production 之后背后站着一个签了字的客户。

**展开结构**：
1. **定义与关系**：SLI 是选来代表「好」的指标；SLO 是「<SLI> 在 <窗口> 内达到 <目标>」；SLA 是 SLO 加违约赔偿，通常比内部 SLO 宽 1 到 2 个数量级，因为你需要在违约之前有反应时间。
2. **我的理解来源**：在 demo 环境 SLO 是概念，系统挂了重启就好；到 production，抽象的「稳定」被翻译成「月度可用性 ≥ 99.9% 否则赔偿」，infra 从躲在业务后面变成抖动直接转成客户的损失、电话、流失。
3. **SLI 规格化的五件事**：好事件定义、有效事件定义（分母范围）、测量点、聚合窗口、计算公式。我落地的是 event-based 的一族 SLI（QPS / error ratio / P95 P99 latency / saturation / per-tenant SLI），并诚实说明**分母范围这一层我做得不够严格**。
4. **一个我坚持的口径**：`SLI = requests_under_threshold / valid_requests` 而不是 P99 本身，理由见 B3。

**挂故事**：S08。知识点 Q14 / Q15 / Q17。

### B2. 你怎么落地 error budget？（⚠️ 本方向最大的诚实点）

**一句定位**：我落地的是 SLO 的工程侧，制度侧我没有建成，我不会把这两半说成一半。

**展开结构**：
1. **先划清边界，主动说**：我做了 SLI 的 recording rule 物化、per-tenant SLA 追踪、以及「PAGER 必须有 SLO 基准」这条准入规则。**我们没有一份写下来的 error budget policy，没有把「预算烧光就冻结发布」变成产品与 SRE 的正式契约，也没有固定的 SLO review 会议。**
2. **归因而不是找借口**：SLO 定义需要 service ownership 支撑，在我们的组织结构里这不是我能单方面推成的，我当时选择先把可测量性做实。
3. **我知道正确路径**：挑一个有明确 owner 的服务试点 → 先只做测量（budget 消耗上 dashboard 跑满一个完整窗口）→ 拿真实数据谈目标值 → 写 policy 从软条款开始（剩 50% 暂停高风险变更，剩 0% 冻结非修复性发布，谁能豁免、怎么记录）→ 建 review 回路，review 的不只是达标情况还包括这个 SLI 是否还代表用户体验。
4. **给一个数字证明我懂机制**：SLO 99.9% 的 30 天窗口，预算是 43,200 分钟 × 0.1% = 43.2 分钟；burn rate 14 倍意味着约 2.14 天烧完，也就是每小时烧掉约 2% 月预算。

**挂故事**：S08 的 L5。知识点 Q16 / Q19。
⚠️ 这题的正确策略是**主动暴露边界然后给出路径**，因为包装成已建成体系一个追问就穿，而主动划边界加清晰路径在 senior 面试里往往是加分项。

### B3. Latency 的 SLO 应该怎么定？P99 ≤ 500ms 这种写法有什么问题？

**一句定位**：问题在于把 quantile 当成了 SLI 本体，正确的写法是「99% 的请求在 500ms 内」这种比例型 SLI，而这个区分我是踩了两次分位数事故才真正内化的。

**展开结构**：
1. **四层分离**：SLI 是衡量什么、Histogram 是怎么记录分布、Quantile 是怎么查看统计值、SLO 是施加什么目标。混在一起就会得出「P99 高了所以出事了」这种既可能对也可能错的结论。
2. **比例型 SLI 的三个数学优势**：只需读 bucket 边界上的一个累积计数不需要插值；分子分母都是加法所以天然可跨实例聚合（分位数不可加）；和 error budget 是同一种数学对象可以直接进 burn-rate 计算。
3. **我的两次一手教训**：分位数被算高造成假警报（多实例采集错位加分桶聚合偏差把 P99 虚高，日志和 APM 都干净，以假告警结案）；分位数被算低造成假信心（t-digest 把真实 5 秒的尖刺抹成约 0.3 秒，如果只信聚合我会得出「最大延迟 300ms 一切正常」）。
4. **一个实操推论**：**SLO 的阈值必须落在 histogram 的 bucket 边界上**，否则 SLI 计算里永远含着一次插值。这条在设计 bucket 时最重要，也最常被忽略。

**挂故事**：S09 主线，S04 补 t-digest。知识点 Q3 / Q4 / Q17 / Q35。

### B4. 多窗口多燃烧率告警怎么设计？

**一句定位**：长窗口决定「这个消耗速度是否严重」，短窗口决定「现在是否还在发生」，两个一起用是为了同时拿到抗抖动和自动恢复。

**展开结构**：
1. **公式与直觉**：`burn rate = 实际错误率 / (1 - SLO)`，burn rate = 1 意味着刚好月末用完预算。
2. **`[理论]` canonical 三档**（30 天窗口）：2% 预算 / 1 小时 → burn rate 14.4 → 长窗 1h 短窗 5m → page；5% / 6 小时 → 6 → 6h + 30m → page；10% / 3 天 → 1 → 3d + 6h → ticket。短窗口取长窗口的 1/12 是灵敏度与误报的经验取值。快慢分层的意义是 14.4 抓快速烧穿、1 抓缓慢退化，后者不该 page 但必须有人处理。
3. **`[一手]` 我实际落了哪一半**：fast burn 的双窗口确认，5m 和 30m 都超阈值才升级 PAGER，作用是滤掉瞬时抖动同时保留持续恶化。slow burn 的 1h/6h 一档我写了设计但没在生产跑满。
4. **诚实边界**：跑满三档的前置条件是每条链路都有确定的 SLO 目标值，而我们当时的阈值有一部分是经验值；而且我的 pager 上仍有大量静态阈值规则在运行，我不能说「我们的告警都是 burn-rate 驱动的」。

**挂故事**：S02 的 L2，S03 的 baseline 提供诚实边界。知识点 Q18。

### B5. 你怎么减少告警噪声？（行为面高频，也是我最强的一题）

**一句定位**：我审计了一个每天约 960 条、约 85% 是默认 P3、背后 367 条 paging 规则的 pager，然后我认为真正的核心不是清掉多少条规则，是论证了告警系统不做功就必然熵增，所以解法必须是准入控制。

**展开结构**：
1. **测量先于改动**：Phase 0 把体验变成数字。367 条规则散在 30 个文件；每天约 960 条，85% 是 P3（因为不写 priority 时 P3 就是默认值）；一条 `for: 0m` 的 OOM-kill 规则因 18 个 pod 连锁 crash 三天出 80 条；一条告警单次触发 fan-out 到 6 个 channel 两分钟后又一轮；同一个卡住的 job 每小时 page 一次三小时三条；超出平均 28% 和超出 300% 的 job 拿到同一个 P1；12 个 channel 里 2 个早已无消息也没人察觉。
2. **四个结构性根因**：进 pager 的 label 是一行代码的免费开关没有准入门槛；`continue: true` 的重叠路由造成扇出；所有 receiver 都没配 dedup alias；一条旁路脚本直接向 pager 平台写入、对所有路由和 inhibition 不可见。
3. **熵增机制（这一段是这题的差异化）**：激励不对称。加告警便宜且可见，出过一次事故加一行 label 就路由进 pager，作者还显得尽责；删告警有风险且不可见，删错要为漏掉的故障负责，删对什么都不会发生。同时每条规则的语义随系统演化静默失效而失效不产生信号（90% 阈值的节点内存告警诞生于 90% 还不是 K8s 节点正常水位的年代）。所以这是「加免费、删受罚、失效无声」三个条件下的默认轨迹，不是任何人的失误。
4. **结论**：清理改变状态，准入控制改变速率。三类持续做功的结构是准入控制（P1/P2 门槛、强制 ownership label、CI lint 拒绝不带 `runbook_url` 的规则）、常设测量（把 pager 本身变成 SLO 对象）、review 回路（季度评审按 owner 分配）。

**挂故事**：S03 主线，S02 补三层分级设计。知识点 Q20 / Q21 / Q22 / Q24。
⚠️ **baseline 是实测，下降数字全部是验收门禁目标不是已达成结果。** 任何场合不得说「我把告警降了 X%」。

### B6. 什么该 page 什么该进工单？inhibition 怎么设计？

**一句定位**：划线的判据不是严重程度而是「需要多快的人工介入」，而降噪要分清 inhibition 解决因果派生噪声、grouping 解决规模噪声，这两件事不要混。

**展开结构**：
1. **三层与判据**：PAGER 是用户可感知的错误或延迟且需立即人工介入，量极少每条必须是真问题；HIGH 是高风险但当下用户不一定受影响（consumer lag、replica 不足、replication down）走 Slack；MEDIUM 是趋势与容量预警走工单。判断一条该不该 page，问三个问题：不处理会怎样、动作是什么有没有 runbook、这个动作必须人做吗。
2. **量化判据**：偏离基线低于 2 倍不告警，2 到 4 倍 P2 进 channel 不 @，高于 4 倍 P1 page 并 @ owner 附 runbook。这把「严重程度」变成能写进 rule 的表达式。
3. **inhibition 只做因果明确的抑制**：`NodeNotReady` 抑制同节点 `PodUnableToStart`；不做「A down 抑制 B」，因为 B 可能同时有独立故障，被抑制就是盲区。失败模式不对称：做窄了多看几条，做宽了掩盖真实故障。技术前提是 `equal` 字段要求 label 值相同，所以 label 一致性是硬前提。验证方式是 staging 人工触发上游故障看下游是否被正确抑制，并保留 firing 历史供 postmortem。
4. **datacenter 级故障几百条怎么办**：`group_by` 折叠、`group_wait` 30 到 60 秒聚齐、检测到系统性故障时 PAGER 只发一条全局事故其余降级。
5. **一条容易漏的**：绕过 Alertmanager 的旁路发送对 dedup 和 inhibition 完全不可见，**降噪机制的有效性取决于是否所有告警都必须经过它**。

**挂故事**：S02 的 L4，S03 补旁路根因。知识点 Q21 / Q23 / Q24。

## C 组：排障方法论（6 题）

### C1. 延迟高了，你怎么定位到是哪一层？

**一句定位**：我不先看「慢不慢」，我先做分段，因为三段的比例本身就是答案，而且这一步几乎零成本就能把责任范围砍掉三分之二。

**展开结构**：
1. **分段等式与判别规则**：`request_time ≈ front_gap + upstream_connect_time + upstream_response_time`。connect 高（>50ms）指向网络链路或建连；front gap 高指向 client 到入口的前段；`request_time ≈ upstream_response_time`（ratio ≈ 1.00）说明时间全在后端。
2. **真实案例的定案**：怀疑是 A/B 集群切换导致变慢。三个独立角度全部指向后端：逐请求分段（最大那条 5.067s，`upstream_response` 5.066s，ratio 1.00，front gap 0.001s，connect ≈ 0）；A/B 持续分位（P99 典型值 60ms vs 66ms，持续最差 70ms vs 81ms，差距全在 `upstream_response`，`upstream_connect` 两边都是 1ms）；dashboard 自洽（专门指示网络问题的 Waiting Latency 面板全程 ≤50ms 且不与尖刺对齐）。
3. **顺序也是设计**：我们的 SLA dashboard 决策树是串行的，先看 Waiting 因为它最便宜、一眼同时回答「影响多大」和「是不是网络」，高就直接走网络分支不用再看 Upstream；Waiting 干净再看 Upstream；两者都干净但总分位还高就是夹在中间的 infra 层（ingress controller 本身、APISIX），常见原因是最近 reload 或 config push、controller CPU、连接饱和。
4. **局限要主动说**：多 upstream 时 `upstream_response_time` 是总和分不出哪个慢；connection reuse 会让 waiting 偏低；这是入口视角看不到后端内部；入口之前的代理层不在 log 里。所以这是第一层诊断工具不是最终结论。

**挂故事**：S04 主线。知识点 Q29 / Q34。

### C2. 讲一次你排查过的最难的问题。

**一句定位**：一个 P100 精确等于 1.00 秒、P50 到 P95 完全正常的周期性尖刺，最后定位到 nginx 的限流 Lua 插件每请求同步调用一个单副本 10 线程的 memcached，socket read timeout 把 nginx worker 阻塞了整整一秒。

**展开结构**：
1. **从数字读出方向**：P100 精确 1.00s 意味着这不是自然变慢而是一个 timeout 被打满了，自然退化会给出 0.87 或 1.34 这种数不会反复精确落在 1.00。所以第一个动作是把链路上所有等于 1 秒的配置项找出来。P50 到 P95 正常说明触发条件是偶发的不是持续负载。
2. **三线并行排除**：upstream 侧 4 个 pod、0 restart、0 OOM、CPU 只用到 limit 的 2%，而且慢请求的 `upstream_response_time` 是 0.095s 量级、状态全 200，也就是后端不但没慢还正常返回了；nginx 配置从 ConfigMap 到 nginx.conf 到 per-ingress annotation 三层全审，所有 timeout 是 5s / 60s / 无限，唯一出现 1s 的是 `global-rate-limit-window` 而那是限流窗口不是 proxy timeout。
3. **定案靠三重对齐**：error log 里找到 `global_throttle.lua` 报 memcached get 失败、`lua tcp socket connect timed out` 指向 `:11211`、`read timed out`。但这只是相关性，因果是靠同一秒（08:07:11）、同一 client IP（192.168.212.64）、同一请求路径三重对齐建立的。
4. **根因链与结构性问题**：单副本 10 线程的 memcached 接不住 `pool_size=10000` 的连接池，accept queue 溢出触发 timeout，Lua 插件同步阻塞 nginx worker 0.3 到 1.0 秒。结构性教训是**关键路径上的同步依赖，其可用性等级必须不低于主路径**，一个「非核心」的限流辅助组件成了每个请求的 SPOF。

**挂故事**：S05。知识点 Q26（saturation 飞盲）/ Q34（λ > μ）。
⚠️ **修复后数据缺失**，只能讲到根因定案与建议表，不能说「修完从 1.00s 降到 X」。1.00s 的确切配置项来源也没查到源码级证据，被追问要承认这是留下的尾巴。

### C3. 你怎么判断一条告警是真的？

**一句定位**：先证伪真实用户影响，再解释指标，因为这是两种完全不同的工作模式，顺序错了会花很长时间去解释一个不存在的问题。

**展开结构**：
1. **动作**：找一个**独立于告警数据源**的信号确认用户影响。告警来自 metrics，那就去看日志和 APM。日志里没有慢请求、错误率没动，那么用户没受影响，优先级立刻从「止血」降到「解释指标」。
2. **真实案例**：一条 P99 越限告警，同窗口的应用日志与 APM 显示没有慢请求也没有错误率波动。证伪之后再解释：多实例采集时间错位叠加 histogram 分桶聚合偏差把 P99 算虚高，以假告警结案并附完整证据链，然后加固规则让同一偏差模式无法再呼叫值班。
3. **这类偏差的共同特征**：它是**计算产物而不是系统行为**，所以在独立数据源上找不到对应。
4. **加固思路**：把条件从「分位数越限」改成同时要求一个与用户影响更直接相关的信号动起来；用 multi-window 确认（采集错位造成的偏差往往不能在两个不同长度窗口上同时稳定成立）；对样本量设下界。
5. **把 disproof 变成显式设计目标**：告警系统不只要发现问题，还要帮助快速排除假阳性和 telemetry skew，这是我在架构里专门写进去的一条目标。

**挂故事**：S09 主线，S04 补 t-digest 反方向。知识点 Q3 / Q17。

### C4. 你怎么避免归因错误？相关性和因果性怎么区分？

**一句定位**：我的硬规则是归因不许只看单一信号源，而且一个能解释现象的信号出现时，先问它能解释多少百分比而不是问它能不能解释。

**展开结构**：
1. **反例先讲**：一个 ClickHouse 节点 CPU 92%（30 核用掉 27.6 核），第一眼看 `system.merges` 得出的初判是 merge 欠债，这个信号是**真的**（merge 确实在跑，确实占约 10% CPU），它只是不是主因。交叉验证 `system.processes` 与线程级 `top -H` 之后结论反转：3 条并发的 `SELECT *` 全表扫（每条约 7 亿行）占约 67%，merge 占约 10%。
2. **为什么会看错**：先看到的信号会成为锚，尤其当它在直觉上是一个已知的常见原因。10% 和 67% 的区别不在于哪个是真的，在于哪个决定了墙钟。
3. **归因错的代价**：按 merge 处理的动作是调后台任务配额和 TTL 分区策略，作用在错误的地方且生效慢；按查询处理的动作是短期限流或 kill、中期变成准入控制问题。方向完全不同。
4. **通用形态**：这条规则可迁移。在 nginx 上是 access log 与 error log 按时间戳加身份对齐；在 latency 上是三段分解必须和 dashboard 的网络指示面板自洽；在延迟指标上是 histogram 与原始日志互证。
5. **诚实的自我批评**：我做到的是写进 case 库加在交接里反复讲，**没有做到把它变成一道机械门禁**（比如 triage 模板里强制填两个信号源）。依赖记性的纪律会随人员流动衰减。

**挂故事**：S10 主线，S05 补三重对齐。知识点 Q25（USE 全绿不代表用户没事）。

### C5. 讲一次你自己犯的错。

**一句定位**：我因为一个 LogQL 的转义错误加一个 `2>/dev/null`，下过一个完全错误的结论：「48 小时内没有超过 1 秒的请求」，而实际上有 5 秒的。

**展开结构**：
1. **错误本身**：LogQL 的 `|~ "...\.[0-9]"` 里的 `\.` 会被当成非法字符转义，Loki 返回 `HTTP 400: parse error ... invalid char escape`，结果是 0 行。我在一次延迟排查里用 `|~ " [1-9][0-9]*\.[0-9]{3} "` 扫 48 小时慢请求，全程报 400 但被 `2>/dev/null` 吞掉了。**看起来像没数据，实际查询根本没跑。**
2. **为什么这类错误特别危险**：日志侧的失败倾向于表现为「没有数据」，而「没有数据」很容易被误读成「没有问题」。同一类问题的另一个形态是 LogQL pattern 在 ingress 日志格式变更后静默失效，查询不报错只是提取字段变空。
3. **同一个坑我踩过第二次的另一个版本**：memcached 那次调查初始用 3 小时窗口，没找到任何 `request_time >= 1s` 的请求（最大 0.634s），如果停在那里方向会全错，扩到 6 小时才拿到那 9 条。
4. **沉淀成三条纪律**：LogQL 里字面点用字符类 `[.]` 不用 `\.`；**永远不给会真正报错的命令加 `2>/dev/null`**；下「没有数据」这种结论之前先用一条无过滤的 sanity query 确认管道确实有数据流过。更上一层的原则是每一条依赖解析的关键查询都要有配套 canary。

**挂故事**：S06 主线，S05 补窗口问题。知识点 Q13（不能报告自己失效的检测手段就是盲区）。
⚠️ 这题不要美化，先把错误和错误结论讲清楚再讲纪律，senior 面试看的是你有没有把教训结构化。

### C6. 一个新人接手 oncall，你怎么让他快速上手？

**一句定位**：我不给他一堆 dashboard 链接，我给他一条串行的决策路径，因为 dashboard 的价值不只在有哪些 panel，还在于它是否隐含了一条正确的排查顺序。

**展开结构**：
1. **第一步是读告警本身**：抓 severity、cluster、namespace、时间戳、client、metric 加阈值。**缺字段就停下来问，不要 guess。** 调查窗口是时间戳 ±3 分钟（rule 评估窗口大于 5 分钟时按 2 倍放宽）。
2. **第二步是判噪音**：点告警消息里的 source URL 直接进 vmui 看当前值，如果时间窗拉到 24 小时仍持续 firing，大概率是 chronic 噪音，走另一条 playbook 而不是当事故处理。
3. **第三步是按 alertname 路由到第一站 dashboard**，然后走那条串行决策树（Waiting → Upstream → Infra），关键是明确写出「看到什么就分叉」而不是三个面板并排让人自己挑。
4. **第四步和第五步**：钻日志（窗口 ±3 分钟，用 time-pinned link）；形成**单一假设**写到事故频道，用一条 query 验证，再操作。任何变更类操作前写清意图。
5. **配套资产**：minimal good page 让他第一分钟能回答三个问题（用户受影响吗、哪一层、有变更吗），加一份高频踩坑清单（比如 OOM 要看 working set 不看 RSS、模板变量选全部会掩盖单点热点、PromQL 永远加 cluster filter）。

**挂故事**：S08（minimal good page 与 top-down）、S04（决策树来源）。知识点 Q30 / Q31 / Q32。

## D 组：成本与规模（6 题）

### D1. 这套监控系统的成本在哪？你怎么控？

**一句定位**：metrics 的成本几乎与请求量无关而与 label 基数的笛卡尔积成正比，所以控成本的抓手是 cardinality 和 retention 分层，不是采集频率。

**展开结构**：
1. **成本结构**：metrics 的成本是 series 数乘采集频率乘 retention，主要落在内存（active series 的 index 与 head）和磁盘。我们的实际数字是 1.2M active series、约 80K samples/sec，热存储 3 个月约 250GB（约 4 倍压缩），冷存储 S3 5 分钟降采样 180 天约 25GB。
2. **架构本身就是一次降本**：同一个 3 个月窗口在 Federation 下要约 930GB，迁到 VM 之后约 250GB，这是压缩带来的，不是删数据换来的。
3. **retention 分层**：tenant SLA 序列 90 天、排障序列 30 天、基础设施 15 天。分层的逻辑是不同数据的价值衰减速度不同，排障数据一周后基本没人看。
4. **冷热分离与降采样**：热数据保原始精度供排障，冷数据 5 分钟降采样供趋势和容量规划。25GB 存 180 天这个数字说明降采样的杠杆有多大。
5. **日志侧的成本模型不同**：Loki 只索引 label 不索引正文，存储远小于 Elasticsearch 的全文倒排，代价是没有 label 约束的查询会变成暴力扫描，所以查询纪律本身也是成本控制手段。

**挂故事**：S01。知识点 Q7 / Q27 / Q28。

### D2. series 爆炸了你怎么止血？

**一句定位**：止血必须在采集侧做，在查询侧做没有用，因为存储压力已经产生了。

**展开结构**：
1. **定位**：用 TSDB status 或 cardinality 接口找 top metric 和 top label，先确认是「哪个指标」还是「哪个 label」。
2. **止血**：在采集侧用 relabel 的 `labeldrop` 或 `metric_relabel_configs` 的 `drop` 把凶手切掉。
3. **爆炸来源按危险程度排**：把无界的东西塞进 label（user_id、request_id、trace_id、带 ID 段的 URL path、error message、pod IP），这类是「无界」不是「大」；多个中等基数 label 相乘；高频重建的资源作为 label（CrashLoop 时的 pod name）；**histogram 的隐藏乘数**，一个 histogram 有 N 个 bucket 就是 N+2 条 series，给它加一个基数 20 的 label 实际增加 20 × (N+2) 条，这项最容易低估。
4. **长期治理四条**：tenant 级 recording rules 只覆盖核心 SLI；基础设施指标一律不带 tenant label；retention 分层；定期 cardinality 审查。
5. **诚实复盘**：这四条是被增长曲线逼出来的，**cardinality budget 应该在第一天就存在**。如果重做我会在采集侧加硬门禁：新指标上线前声明预期 series 数，超预算的 label 组合直接拒绝，和我在告警治理里用的准入控制是同一个思路。

**挂故事**：S02 的 L3，S01 的 L5。知识点 Q6 / Q7。

### D3. 这套架构能撑多大规模？下一个瓶颈在哪？

**一句定位**：三层可独立扩展所以理论上限不是问题，实际瓶颈有三个而且我们已经踩到了第一个。

**展开结构**：
1. **可扩展性的结构**：vminsert / vmstorage / vmselect 分层，写入和查询独立扩展，这是相对单机 Prometheus 的核心优势。
2. **三个实际瓶颈**：Loki 在高流量下全量扫描慢（已踩到，因为不做全文索引）；高 cardinality 下 vmstorage 压力大；**vmalert 规则多了之后评估周期跟不上**，我们的缓解是把 tenant 级和全局 recording rules 拆到不同 rule group 分开评估。
3. **下一步的架构动作**：cluster 模式的水平扩展和 vmselect 侧的查询缓存。
4. **我会怎么提前发现瓶颈**：监控监控系统本身。remote_write 的队列长度、丢样本数、发送延迟、远端返回码分布是最小集；vmalert 的规则评估耗时和 `lastError` 是第二组；这两组不上 dashboard，退化就不可见。

**挂故事**：S01 的 L5。知识点 Q11 / Q8。

### D4. 怎么做容量规划？

**一句定位**：容量规划的第一性原理是排队论而不是趋势外推，因为利用率超过大约 70% 之后尾延迟是指数爆炸的，所以「留 30% 余量」不是保守是数学。

**展开结构**：
1. **`[一手]` 监控侧的容量推导方式**：从可测量的输入往上算，50 集群 × 约 12 节点 ≈ 600 节点 × 约 2,000 series/node → 约 1.2M active series，配 15s 间隔 → 约 80K samples/sec。这种从单位量往上乘的方式比「拍一个总量」可验证得多，而且新集群接入时能直接算增量。
2. **`[理论]` 排队论的约束**：Little's Law（`L = λW`，并发数 = 吞吐率 × 平均延迟）；M/M/1 和 M/M/c 告诉我们利用率超 70% 尾延迟指数爆炸；推论是容量规划必须看延迟分布不是均值。
3. **Saturation 才是容量的正确指标**：Saturation 问的是「还剩多少余量」，最好的指标往往是队列长度或等待时间而不是利用率。CPU 的 saturation 是 run queue 长度不是 CPU%；线程池的 saturation 是排队任务数不是活跃线程数。
4. **一个反面案例**：memcached 没有 exporter，`current_connections` 和 `listen_disabled_num` 这些真正的 saturation 指标完全飞盲，我只能用 file descriptor 数当代理指标（正常 24，spike 时 54，翻倍就开始 timeout）。**关键路径上的依赖如果没有 saturation 可观测性，它就是一个隐藏的容量天花板，你只能在它被撞穿之后才发现。**

**挂故事**：S05（memcached 容量天花板）、S01（容量推导）。知识点 Q26 / Q34。

### D5. 可观测性数据除了告警还能干什么？

**一句定位**：它能给不可逆决策提供证据。我在提交一个不能 ALTER 的表布局之前，先挖了 14 天生产 `system.query_log` 共 7,470 万条日志行，结果画面完全反过来了。

**展开结构**：
1. **场景**：原始方案建立在一份 50 条精选查询的 benchmark 上，而分布键这类决策一旦落地不能 ALTER。
2. **取证结论**：绝大多数流量（远超 90%）是点查，键是一个高基数的用户标识，而且大部分是无界的「取最新值」重建，没有任何时间过滤条件能事后加上去。于是第二张服务表从「也许要」变成必须要，设计随之加宽。**按 benchmark 设计会优化错的负载。**
3. **为什么 benchmark 不可信**：人挑查询时会不自觉地挑「有代表性的」和「有意思的」，这两个标准都不等于「按频次加权后占流量的」。
4. **这个方法的局限（主动说）**：query_log 反映的是客户端在既有能力约束下发出的查询，一个慢到没人敢用的查询在 log 里就是低频的，迁移后可能爆发；扫全量 log 本身有成本，而且要先确认它是全量记录还是采样的；SQL 是文本，形态归类需要模板化而归类口径会影响结论。
5. **把证据强度和决策可逆性挂起来**：如果只有访谈加 benchmark 这一档证据，我不会做不可逆的决策，我会先选一个可以 ALTER 的保守布局并把 query_log 打开，两周后拿真实画像再做那个不可逆的选择。**这个案子最值钱的不是我挖了 7,470 万行，是我在提交不可逆决策之前先问了「我的证据够不够支撑不可逆」。**

**挂故事**：S07。知识点 Q27。
⚠️ 这题在监控面试里只讲「telemetry 作为决策证据」这个切面，不要展开 Doris 引擎层的工作（归属边界见 `contexts/resume_highlights_doris_dcluster.md` §0）。

### D6. 一次大版本迁移，你怎么保证不出事？

**一句定位**：我的门禁是「等价性证明」而不是「测试通过」，具体是两周双写窗口加三条必须同时满足的等价条件，门禁通过前旧栈一直在线做 fallback。

**展开结构**：
1. **为什么不能靠假设**：VictoriaMetrics 用 MetricsQL，和 PromQL 有边界差异，所以「规则还会照常触发」不能假设，必须逐条验证。
2. **三条等价条件**：vmagent 的 remote_write 同时写新旧两侧使两套栈都有完整数据；每条 alert rule 在两侧同时评估、diff firing 行为、修完所有分歧；dashboard 查询在 MetricsQL 下返回等价结果。三条都过才动通知路由。
3. **fallback 与失败可见性**：门禁通过前 Federation 栈一直在线；平台本身必须响亮地失败，vmalert 持续输出心跳，deadman's switch 加 out-of-band 探针把「监控失联」在分钟级变成明确的 page。
4. **配套的验证方式**：inhibition 规则在 staging 人工触发上游故障验证下游是否被正确抑制，并保留 firing 历史供 postmortem 回溯。
5. **切换后的持续验证**：三个信号，deadman 心跳、PAGER action rate、漏报追踪。
6. **诚实边界**：素材没有描述逐集群灰度的分批切换过程和正式的回滚预案文档，所以我讲的是双写窗口、等价性门禁、staging 验证和 fallback 这四件确实做了的事，不会加一个我没做的灰度流程。

**挂故事**：S01 的 L3。知识点 Q12 / Q13。
⚠️ 不要声称做了「逐集群灰度」或「正式回滚预案文档」，`p_vm_platform.md:170` 明确说明素材不支持这两项。

## 附：答题时的四条通用纪律

1. **先给结论再展开。** 每题的「一句定位」就是那个结论，说完再铺 beat。
2. **数字必须能溯源。** 不确定的数字宁可说「这个量级」也不给精确值。已知的口径冲突（VM 部署模式、通知平台名称）见 README 的待确认清单。
3. **主动划边界比被追问后承认强得多。** 特别是 B2（error budget 制度侧没建成）、B4（只落了双窗口）、B5（下降数字是门禁目标）、C2（修复后数据缺失）这四题。
4. **归属用「I designed / I proposed and drove / I evaluated and recommended / I implemented」四档说清。** VM 引擎选型是第三档（团队共识），三层告警设计是第一档，service-impact-first 的转向是第二档。
