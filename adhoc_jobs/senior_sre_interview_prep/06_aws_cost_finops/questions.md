## 组一：成本可见性与归因（Inform 层，他最薄的一环，但答题结构可以很硬）

### Q1「你们的云成本是怎么看的？用什么工具？」

**一句定位**
「我们的可见性是停在账单科目层的：能看到 EC2、EBS、S3、data transfer 各花多少，但拆不到集群、namespace 或租户。这是我明确知道的缺口，也是我认为该优先补的一层。」

**展开结构**
1. 说清现状边界：账单科目层可见；公司环境里有 Kubecost（我没深入用过它做决策）；⚠️ 「Cost saving dashboard」那条待确认后再提。
2. 说清为什么这是问题：不知道成本分布，只能优化你正好看见的地方。
3. 给出具体补法（这才是加分项）：cost allocation tag 打在 Launch Template 的 TagSpecifications 上（不是事后给实例打标）→ CUR 2.0 导出 → Athena 查询 → 按 cluster/team/env 聚合。**我们是 kubeadm 自建控制面不是 EKS，所以 EKS split cost allocation data 用不了，容器层归因只能走 OpenCost。**
4. 收尾拉回强项：「但我在自己负责的系统里做过更细的东西：单查询成本分析（S02）。方向是对的，只是没有横向铺开。」

**挂**：诚实边界为主 + S02 收尾。第 3 步的「我们不是 EKS 所以某个 feature 用不了」是很强的信号，证明他知道自己环境的约束。

### Q2「Cost Explorer 和 CUR 有什么区别？什么时候必须用 CUR？」

**一句定位**
「Cost Explorer 够用来发现，不够用来归因。它只有 AWS 预设的维度，回答不了任何业务维度的问题。」

**展开结构**
1. Cost Explorer：交互式看趋势和切维度，日/月粒度留 14 个月（开 Multi-year 到 38 个月），**resource-level 只留 14 天**，API 每次请求 $0.01。
2. CUR / Data Exports：逐行明细（一个资源一小时一项用量一行），能任意 SQL、能 join 自己的数据。CUR 2.0 是当前主推，legacy CUR 无新功能。支持 FOCUS 格式导出（跨云列名统一，多云才有意义）。
3. 分界线：**「这个月为什么涨了」用 Cost Explorer 五分钟；「这 3 万美元具体是谁花的」必须下到 CUR + Athena。**
4. 加一条实操细节：Data Exports 不像 legacy CUR 附现成建表 SQL，官方给的是 CloudFormation 模板自动建 Glue Database + Crawler + Lambda + S3 event notification 保持 catalog 同步。

**挂**：纯 `[理论]`。答到第 3 步的分界线就够，第 4 步是被追问时的深度。

### Q3「怎么落地 cost allocation tagging？」

**一句定位**
「tagging 的难点不是技术，是覆盖率。所以我会从强制机制入手，而不是从文档和规范入手。」

**展开结构**
1. **定最小 tag 集**：owner / environment / cost-center / service。四个就够，多了没人填。
2. **用强制机制不靠自觉**：SCP 或 IAM condition 拒绝无 tag 创建、IaC 模块里写死默认 tag、AWS Config rule 检测未打标资源。**锚到自己：我们节点全走 ASG + Launch Template，所以正确注入点是 LT 的 TagSpecifications。**
3. **定 untagged 的兜底归属**：不能让 10% 的账单挂在「未知」上，那会让整个 showback 失去可信度。
4. **把覆盖率本身做成指标**（tagged spend / total spend）并给目标值。
5. 补一条容易答错的机制：**tag 激活后能回溯，窗口 12 个月**，但只能回填标签当时确实存在的时段（不能凭空造标签值），每 24 小时只能提交一次 backfill。账户级上限 500 个 active cost allocation tag key。

**挂**：`[理论]` + ASG/LT 的一手锚点。第 5 步的回溯窗口是很多人的过时知识，答对显示知识是新的。

### Q4「你怎么发现浪费？」

**一句定位**
「我用的判据是一个很简单的形状：**在增长但没有访问者**。我在数据层用这个判据抓到过 TB 级的浪费，云资源层是我要补的。」

**展开结构**
1. 讲 S06：ClickHouse 每次升级把旧系统日志表改名保留、从不删除，攒下 1.21 TiB trace 日志 + 308 GiB profiling 日志，无读者无写者但 parts 仍参与后台 merge，最后被一次一秒内的 merge 引爆成 OOM。一处确诊立刻跨集群审计，最严重的集群 1.65 TiB、另一 region 250 GiB。
2. **主动做那个自我批评**（这是本题的最高分）：「问题是它是被 OOM 发现的，不是被账单发现的。1 TB 级存储在多个集群持续增长、访问量是零，这本来是最干净的成本异常信号。这件事之后我对成本可见性的看法变了：**成本异常检测不只是省钱工具，它是一类独立于业务指标的浪费探测器。**」
3. 把判据推广成云资源清单：未挂载 EBS 卷、终止实例遗留的卷（`DeleteOnTermination=false`）、无生命周期策略的老快照、废弃 AMI 背后的快照、没有目标的 ELB、未关联 EIP、空 ASG、长期不动的 dev/staging、S3 上无生命周期的中间产物、监控栈自己的高基数 series。
4. 诚实收尾：「云资源侧这一遍盘点我没有系统性做过，我做过的是数据层的那一次。」

**挂**：S06（带诚实 reframe：主因是可靠性，成本是副产品，不要说成「我做了一次存储降本」）。

### Q5「Budgets 和 Cost Anomaly Detection 有什么区别？都要配吗？」

**一句定位**
「两个抓的是不同东西：Budgets 抓绝对值越线，Anomaly Detection 抓形状变化。业务在增长的时候，只有前者会不停误报。」

**展开结构**
1. Budgets：阈值告警 + 可触发动作（停实例、加 SCP）。每账户每月 2 个免费 action-enabled budget。适合「不能超过 $X」这类硬约束。
2. Anomaly Detection：ML 检测异常花费，**检测本身免费**（只有 SNS 邮件超免费额度才收费）。适合「有东西悄悄涨起来了」。
3. 为什么都要：增长期账单本来就会涨，Budgets 会一直响到没人看；反过来 Anomaly Detection 抓不到「缓慢但持续超预算」。
4. 补一句判断：**告警本身不解决问题，关键是有 owner 和响应流程。** 这一点和告警治理是同一个道理，我在告警噪音上有过一手教训（可以引到 90 目录的告警治理素材）。

**挂**：`[理论]` + 告警治理的跨方向连接。

### Q6「RI 和 Savings Plans 怎么选？」（必问）

**一句定位**
「AWS 自己现在的官方立场是 SP 优先于 RI，EC2 User Guide 里有明确的推荐语。RI 现在只剩两个真实理由：Marketplace 转售和 zonal RI 的容量预留。」

**展开结构**
1. **先说清语义差异**（这一步答错就露）：**SP 承诺的是每小时消费额（$/hr），RI 承诺的是具体的实例配置。** 所以 SP 天然跟着实例族变化走，RI 不会。
2. **四种 SP**：Compute（up to 66%，最灵活，跨 family/region/OS，覆盖 EC2/Fargate/Lambda）/ EC2 Instance（up to 72%，锁 region + family）/ SageMaker AI（up to 64%）/ **Database（2025-12 re:Invent 新增，12-35%，仅 1 年期 No Upfront，覆盖 Aurora/RDS/DynamoDB/ElastiCache 等）**。
3. **RI 剩下的价值**：RI Marketplace 可转售（只能卖 Standard RI，Convertible 不可上架，AWS 收 12% 服务费，需上架满 30 天，单账户终身上限 $50,000 或 5,000 个 RI）；zonal RI 才有容量预留语义。Standard 不可交换但折扣更高；Convertible 可换 family/type/platform 但**不能跨 region**，且新 RI 总价值须 ≥ 旧 RI。
4. **给一个决策规则**：确定不变的核心 baseline 用 EC2 Instance SP 拿最深折扣；架构在演进中用 Compute SP 换灵活性；需要容量保证用 zonal RI；需要退出通道用 Standard RI。
5. **诚实边界**：「承诺折扣的实际采购决策我没有参与过，这是我明确的补课项。我能讲清机制和决策框架，但没有管过一个 SP 组合的 coverage 和 utilization。」

**挂**：`[理论]` 为主 + 明确边界。**不要报 Standard vs Convertible 的精确折扣百分比差**，官方只有定性表述。

### Q7「Coverage 和 Utilization 有什么区别？你会怎么管？」

**一句定位**
「Coverage 低是钱没省够，Utilization 低是买多了在付没用的承诺。后者比不买还糟，因为它是纯损失。」

**展开结构**
1. 定义：Coverage = 被折扣覆盖的用量 / 总用量；Utilization = 承诺被用掉的比例。
2. **关键洞察：两者反向拉扯。** 追 coverage 会买多让 utilization 掉，追 utilization 会买少让 coverage 掉。
3. **所以健康做法是刻意不追 100% coverage**：只覆盖「历史最低谷用量」而不是「平均用量」，波动部分留给 On-Demand 和 spot。
4. 加一条组织层的真实冲突：**spot 化会吃掉 SP 的可覆盖基数。** FinOps 团队刚买 3 年 SP，平台团队接着把负载 spot 化，两边都在「优化成本」，结果是浪费。所以这两件事必须同一个人或同一个流程统一决策。

**挂**：`[理论]`。第 4 步是很强的组织维度信号。

### Q8「你们做了弹性架构，那承诺折扣策略应该怎么变？」（这题是他的加分题，要主动往这儿引）

**一句定位**
「这两件事有一个直接的互动关系，而且顺序很重要：**先做架构级降本，再定承诺策略。反了就会买一堆用不掉的承诺。**」

**展开结构**
1. **架构降本让 baseline 消失。** 我们的 heavy 池原来是静态 2 节点常驻，那是完美的 SP 候选（7×24 稳定用量）；改成 floor-0 弹性之后变成「平均每天 2 台跑 2 小时」，这时候买承诺会让 utilization 崩掉（src: S01）。
2. **承诺应该覆盖真正的 baseline，也就是那个永远不上 spot 的部分。** serving 池是 on-demand 常驻、一次 spot 回收等于查询中断加缓存清空，所以永远不上 spot（S01）；StarRocks 那边 `query_wh` 是 on-demand always-on（S05）。**那两个池子才是 SP 的正确目标。**
3. **所以分池这个动作同时解决了两个问题**：可靠性隔离，和定价模型匹配。我做分池的时候是为了可靠性（按风险容忍度分），但它顺带把承诺策略也变清楚了。
4. **还有一个翻转点要算**：负载变密到某个程度，弹性的收益（省闲置）会小于代价（冷启动 + 反复伸缩），常驻加承诺反而更便宜。这个翻转点应该被算出来当触发条件，而不是等账单异常了才发现。

**挂**：S01 + S05。这题把外环知识和内核经历焊在一起，是本方向最能拉分的一题。

## 组三：架构级降本（他的主场）

### Q9「讲一个你做的成本优化。」（必答，主力题）

**一句定位**
「我做的是架构级的降本：不是在既有结构上找便宜，是改变系统结构让成本随负载归零。具体是把重查询算力池的成本结构从固定容量改成按需容量。」

**展开结构（30 秒版）**
1. **先给数字**：静态 2 节点重查询池 on-demand 约 $772/月；实测 burst 形状（平均每天 2 台跑约 2 小时）on-demand 约 $63/月、spot 约 $24/月，省约 92% / 97%。
2. **说清为什么能这么做**：不是因为装了 autoscaler，是因为存算分离：BE 不持有本地数据，tablet 在 S3，本地 EBS 只是 cache，所以杀节点安全、不需要 DECOMMISSION 搬数据。
3. **说清代价**：冷启动约 66 秒起节点 + 约 2 分钟 backend 注册，只加在一个本来就延迟容忍的类别上；serving 路径的点查一条都不经过这个池子，物理隔离。
4. **说清起点是算术不是直觉**：这件事的起点是一次 query log 挖掘，我算出单查询成本比约 1,240×（引到 S02）。

**口径纪律**：主动说「这是按实测 node-hours 和 list price 建的成本模型，不是账单前后对比」。spot 的 97% 当时是投影（决策是装好 node-termination handler 之后才切 spot）。

**挂**：S01 主线，S02 做深度，S05 做广度（同一模式在两个引擎上做过）。

### Q10「你怎么衡量一个系统的成本效率？」（必问）

**一句定位**
「总额指标回答不了任何决策，我用的是单位成本。我实测过我们系统里最贵的一条查询和最便宜的一条相差约 1,240 倍，这个分布直接决定了架构。」

**展开结构**
1. **先说总额的三个缺陷**：业务增长时它一定涨（涨了不代表变差）；它不能回答「该不该花」（账单涨 20% 但请求量涨 50% 其实是效率提升）；它没有决策指向性。
2. **给自己的例子**：cost per query。月度累计窗口查询平均 196,354 ms vs 频率最高点查平均 158 ms，比值约 1,240×；那条窗口查询跑 18 次约等于 21,755 条点查的总算力。**频率和成本指向完全相反的方向。**
3. **说清用它做了什么**：否掉「一个池子服务所有查询」→ compute group 物理分池；否掉「常驻重查询池」→ floor-0 弹性；定了分类器的 recall-first 风险姿态（误判 heavy 只浪费，误判 light 会被内存硬限杀掉再重试，代价不对称）。
4. **主动交代精度边界**：这是墙钟耗时比不是美元比。严格的 cost per query 应该是「资源占用 × 时间 × 单价」，我用墙钟做代理，因为两类查询跑在同规格节点上且我要的是量级不是精度。真要美元化，正确做法是给 compute group 打成本分配标签、用 node-hours 反推摊销。**这一步我没走完。**
5. 往上一层：SaaS 的终局指标是 cost per tenant（毛利基础）；AI 负载的对应指标是 cost per token / per inference，那也是 FinOps Foundation 2026 框架把 AI 列为独立 Technology Category 之后推荐的 KPI。

**挂**：S02。第 4 步的主动交代是这题的分水岭：能说清自己指标的精度边界，比报一个漂亮数字强。

### Q11「给你一个云账单，你怎么做降本？」（必问，方法论题，答题结构本身就是评分点）

**一句定位**
「我会按两个顺序做：**先归因再优化，先架构再运营。** 大多数降本项目失败是因为跳过了归因，只能优化你正好看见的地方。」

**展开结构（五步，可以在白板上画）**

**第 0 步：把账单分解成三个因子。**
```
账单 = Σ ( 用量 × 单价 × 时长 )
         ↑      ↑      ↑
      架构决定  折扣决定  弹性决定
```
这个分解决定了后面所有动作的优先级，因为**用量和时长的天花板是数量级，单价的天花板是折扣率**。

**第 1 步：归因（Inform）。** Cost Explorer 切维度找大类 → 下到 CUR + Athena 拆到资源和 tag 层 → 找出 top 5 成本科目和它们的增长率。这一步的产出是一张「谁花了多少、在涨还是在跌」的表。**不做这一步就开始优化是最常见的失败模式。**

**第 2 步：先找纯浪费（零风险动作）。** 判据是「在增长但没有访问者」：未挂载卷、老快照、无目标 ELB、未关联 EIP、空 ASG、闲置环境、无生命周期的 S3 中间产物。这类动作没有 trade-off，先做完再谈别的。（可引 S06。）

**第 3 步：架构与弹性（收益最大，风险要评估）。**
- 问「这个负载的成本形状对不对」：稀疏且延迟容忍的负载不该常驻（→ S01 floor-0）；不同风险容忍度的负载不该共享定价模型（→ S05 三 warehouse）。
- 问「这个瓶颈在账单上对应哪个计费维度」：我在 Iceberg 上就是这么做的：profile 出 99% 时间在 OpenFile，推出「S3 按请求次数计费」的模型，所以动作是减文件数而不是加带宽，文件数 619 → 49（→ S04）。
- 问「idle 占多少」：K8s 上 `节点成本 ≥ Σrequests ≥ Σusage`，如果 idle 占 40%，那给 workload 做 rightsizing 就是在优化那 60%。**先压 idle 再做 workload rightsizing。**

**第 4 步：单价（运营级，最后做）。** rightsizing（多维度看 p95 不看均值）、实例族现代化、spot 占比、存储类分层、**最后才是承诺折扣**。承诺放最后是因为前面的动作会改变 baseline，先买承诺会买一堆用不掉的（→ Q8）。

**第 5 步：防回退（Operate）。** 把护栏做进 IaC 和 CI（tag 强制、request 上限、生命周期策略默认开）、把检测做成周期性自动检查、把单位成本做成常态指标。**只做一次性清理不建机制是这类工作最常见的失败。**

**收尾一句**：「而且我会明确列出『我建议不砍的部分』并说明理由：关键路径的冗余、副本数、跨 AZ 的可用性成本。能说清哪些成本不该砍，比砍得多重要。」

**挂**：S06（第 2 步）、S01/S04/S05（第 3 步）、诚实边界（第 4 步的承诺折扣部分）。

### Q12「S3 的成本有什么坑？」

**一句定位**
「最大的坑是**请求费不是存储费**。我在一个 Iceberg 场景里 profile 出 99% 的时间花在 OpenFile 上，于是我建的第一个模型就是『S3 按请求次数计费，不是按带宽计费』，所有动作都从这个模型推导。」

**展开结构**
1. **给单价**：GET/SELECT $0.0004/1000 请求，PUT/COPY/POST/LIST $0.005/1000 请求。**PUT 比 GET 贵约 12.5 倍**，所以写侧文件数比读侧请求数更值钱。LIST 和 PUT 同价，这是对象数极多的 prefix 上的隐形成本（Iceberg/Hudi 这类表格式就是为了避免全量 LIST 而存在）。
2. **给自己的一手结果**：文件数 619 → 49，FSIOTime 7.9s → 63ms（125×），冷查询 7.5s → 744ms。手段是 `target-file-size` 512MB→1GB、`commit.interval` 60s→10min、写批 50K→500K。**这些是手段，模型才是核心。**
3. **给另一条链上的反例**（这一步显示他会区分）：Doris 点查那边我也实测过，冷读聚合吞吐只有约 1MB/s、NIC 带宽用不到 1%，瓶颈是 GET 延迟乘 GET 数量，一次未剪枝点查要探遍 566 个 tablet / 6689 个 segment。但暖查询全命中缓存仍然 1.12s，**证明扇出是成本地板、S3 只是冷路径上的乘数**。所以那条链上最大杠杆是分区剪枝不是文件合并。**同一个方法，两条链结论不同。**
4. **补存储类的坑**：最短存储时长是真实陷阱（Deep Archive 存 30 天删掉仍按 180 天计费）；取回费加请求费经常反超省下的存储费；**Intelligent-Tiering 只对 ≥128KB 对象生效**，小文件场景无效，而且监控费约 $0.0025/1000 对象/月。

**挂**：S04 主线 + S03 做对照。第 3 步的「同一方法两条链不同结论」是很强的深度信号。

### Q13「gp2 换 gp3 能省多少？」

**一句定位**
「单价差是 20%（$0.10 vs $0.08 每 GB-月），但真正的收益通常更大：gp2 是 3 IOPS/GB，所以很多人是『为了拿 IOPS 而买大容量盘』，换 gp3 之后那部分多余容量可以直接砍掉。」

**展开结构**
1. gp3 把 IOPS/吞吐与容量**解耦**：免费包含 3,000 IOPS / 125 MiB/s 不随容量走，最大可配 80,000 IOPS / 2,000 MB/s，超出部分单独计费。
2. 所以迁移前要先核算真实 IOPS 需求，而不是照容量 1:1 换。
3. **诚实边界**：「卷类型迁移我们生产上没做过。我们的一手经验是 PVC 在线扩容对 gp2/gp3 StorageClass 是支持的，以及 StatefulSet 的 volumeClaimTemplates 首建后不可变这类坑。」
4. 顺手带一条快照的反直觉事实（如果对方在聊存储）：**快照是严格增量的，但删掉某个快照未必降低成本**，因为其他快照可能仍引用同一批 block。Snapshot Archive tier 是 $0.0125/GB-月 vs 标准 $0.05，但最短 90 天且提前删有早删费。

**挂**：`[理论]` + 明确边界。

### Q14「Graviton 你们迁了吗？迁移的难点在哪？」

**一句定位**
「Graviton 的生产迁移我没做过。但跨架构的构建和镜像问题我踩过，那是开发效率不是云成本，我把这两件事分清楚。」

**展开结构**
1. **先说清自己的边界**：Doris FE 从 QEMU 模拟 amd64 编译换成原生 arm64，build 从 43 分 55 秒压到约 3 分钟、镜像从 747MB 压到 43MB。这证明我处理过跨架构构建，但不等于做过 Graviton 成本迁移。
2. **说清收益量级**：最新一代是 Graviton5（2025-12 预览、约 2026-06 GA，首发 M9g/M9gd，region 有限）；官方声称 Graviton5 对 Graviton4 计算性能 up to 25%；家族级口径是「比同规格 x86 便宜 up to 20%」。托管服务支持已经很广。
3. **说清四个摩擦点**（这是本题的深度所在）：x86-only 容器基础镜像直接阻塞启动，需要 multi-arch 镜像；AVX/AVX-512 在 ARM 上无等价物要移植到 NEON；**一个 x86-only 的 sidecar 或 DaemonSet 能阻止整个集群上 Graviton**（监控 agent、安全 agent 最常见，这条在 50 集群的环境里是真正的阻塞点）；**Graviton 1 vCPU = 1 物理核（无 SMT）**，与 x86 典型 2 vCPU/核不同，容量规划的换算关系会变。
4. 收尾给一个务实的迁移顺序：先迁无状态且依赖少的（自己写的服务）→ 再迁托管服务（RDS/ElastiCache 换实例类型，风险最低）→ 有状态和有原生依赖的最后。

**挂**：`[理论]` + 跨架构构建的一手锚点（明确标注不是云成本）。第 3 步的第三条最能显示他懂 50 集群规模下的真实阻塞点。

### Q15「K8s 上怎么控成本？」

**一句定位**
「K8s 上有一个必须说清的错位：**你付的是节点的钱，但分配的是 request 的量。** 这中间有两个 gap，是两类完全不同的浪费。」

**展开结构**
1. **画出关系**：`节点成本 ≥ Σrequests ≥ Σusage`。第一个 gap 是**调度碎片**（pod 尺寸与节点尺寸不匹配、反亲和/拓扑约束、DaemonSet 占位、kube-reserved），第二个 gap 是**request 虚高**（开发按「不 OOM 就行」拍数）。治法完全不同。
2. **给一个碎片的真实例子**：我们的 Doris BE 请求 `cpu=8` 跑在 8 vCPU 节点上，kube-reserved 之后 allocatable 只有约 7.9，调度模拟永远报 Insufficient cpu，而且**没有任何事件指向那 0.1 核的差距**。改成 `cpu=7` 立即扩起来。**成本含义是：如果当时的处理方式是加大节点规格而不是降 request，就会为 0.1 核付一整档实例的钱。**
3. **说清 requests/limits 的成本语义**：CPU 是可压缩资源（超了被 throttle），内存不可压缩（超了 OOMKill），所以 memory limit 设低了是可靠性事故不是性能问题。QoS class 决定驱逐顺序，**Guaranteed 最稳但最浪费**。所以「把 request 全压到实际用量」是错的：**关键路径应该 Guaranteed 并接受浪费，可重跑负载才适合 Burstable/BestEffort。** 这和我按风险容忍度分 spot 池是同一个思路。
4. **说清 idle cost 是核心指标**：如果集群 idle 占 40%，给 workload 做 rightsizing 就是在优化那 60%。**先压 idle 再做 workload rightsizing。**
5. **说清工具与自己的约束**：OpenCost 是 CNCF Incubating 项目；Kubecost 在 2024-09 被 IBM 收购、现在叫 IBM Kubecost。AWS 的 EKS split cost allocation data 能按 pod 实际 CPU/内存消耗把 EC2 成本拆到 namespace/workload，**但我们是 kubeadm 自建控制面不是 EKS，所以那个 feature 用不了，容器层归因只能走 OpenCost。** OpenCost 的分摊语义是 `max(request, usage)`，故意让预留但没用的容量算在申请方头上，倒逼合理 sizing。

**挂**：S01（cpu=8 那个坑）+ S05（按风险容忍度分级的思路复用）+ `[理论]`。第 5 步的「我们不是 EKS」是这题的加分细节。

### Q16「Autoscaling 能降本吗？」

**一句定位**
「HPA 单独降不了本。缩了 pod 但节点还在，账单一分不少。真正省钱的是节点层，而节点层的瓶颈是时间尺度。」

**展开结构**
1. 三层分清：HPA 管 pod 数（减 Σrequests）、VPA 管 pod 尺寸（治 request 虚高）、Cluster Autoscaler / Karpenter 管节点数（真正省钱的那层）。**只有 pod 层和节点层联动才真的省钱。**
2. **给自己的一手论证：为什么我们没用 HPA**（StarRocks CN 场景）：CN 冷启动 3-5 分钟，reactive 伸缩追不上秒级查询期望；HPA 只看 CPU/mem，识别不了「无 MV 命中的 ad-hoc 重查询」这种业务语义，只有持有 cube coverage 信息的上游服务能在执行前判断。所以我们做的是 proactive 预拉起 + 前端「数据处理中」吸收等待。
3. **给一条控制论级别的结论**：执行有 3-4 分钟延迟的系统，必须对**持续**压力反应，不能以快于生效速度堆叠修正。我们的去抖设计就是这么来的：只有排队数持续 W 秒才扩，扩完 arm 一个 cooldown 匹配冷启动时长。
4. **给 CA 的真实坑**：从字面 0 节点扩容时，autoscaler 没有真实节点可查，只能靠 ASG 的 node-template label 和 taint tag 构造虚拟节点；缺 tag 就静默 Pending 且报错里完全不提 tag。**scale-from-zero 的典型失败模式是静默。**
5. **诚实边界**：Karpenter 我们没用。它比 CA 在碎片治理上结构性更强（直接按 pod 形状选实例类型、还能 consolidation），但我们的控制面是自建、节点走 Packer + Ansible + kubeadm 的 AMI 流水线，上 Karpenter 需要一次不小的改造。

**挂**：S05（不用 HPA 的论证）+ S01（CA 静默拒绝、去抖设计）+ 明确边界。

## 组四：成本与可靠性的权衡（senior 分水岭）

### Q17「怎么在不影响 SLO 的前提下降本？」（必问）

**一句定位**
「我的做法是**按风险容忍度给负载分级，然后只在能容忍的那一级上做省钱动作**。关键路径上我一分钱都不省。」

**展开结构**
1. **给最干净的例子（S05）**：同一套 StarRocks 上我按业务语义切了三个 warehouse：`query_wh` 跑用户面 MV 查询，on-demand 常驻保 50ms 级 SLA；`refresh_wh` 跑夜间 MV 刷新，spot，刷完销毁；`adhoc_wh` 跑 ad-hoc，spot，按需拉起。**硬约束是 on-demand 与 spot 不可混**，因为 spot 回收等于 in-flight query 失败。
2. **说清为什么这样分是对的**：MV 刷新是**可重跑的批任务**，失败代价是「今晚这批晚一点」不是「用户看到错误」，所以 spot 的风险恰好落在能承受它的负载上。反过来 `query_wh` 一秒都不敢上 spot。**风险容忍度决定定价模型。**
3. **给第二个例子（S01）**：Doris heavy 池的冷启动 3-4 分钟只加在延迟容忍的重查询上，serving 路径的点查一条都不经过；serving 池永远不上 spot。**同一个判断的两次应用。**
4. **给量化的接口**：如果一个降本动作会影响 SLI，就把它换算成 error budget 消耗量。这样它就有了预算约束：budget 有余量可以试，烧完了就停。**这是把成本决策纳入 SRE 框架的正确接口。**（诚实：error budget policy 的制度落地在我这里偏浅。）
5. **反过来守底线**：「有些成本我会明确建议不砍：关键路径的冗余、副本数、跨 AZ 的可用性成本。我会把这笔钱算出来，然后跟业务讲『这是买可用性的钱』，而不是默认它是浪费。」

**挂**：S05 主线 + S01 做第二例。

### Q18「多 AZ 高可用会带来跨 AZ 流量成本，你怎么权衡？」

**一句定位**
「先把跨 AZ 流量分成两类：**为可用性付的，和随机调度的副产品。** 后者是纯浪费该治，前者是在买可用性该付，两者要分开算。」

**展开结构**
1. **给机制和单价**：跨 AZ 同 region 流量是 $0.01/GB 单向、往返 $0.02/GB，**没有变成免费**（2022-04 免费的只有 PrivateLink / Transit Gateway / Client VPN 的跨 AZ，不含普通 EC2-EC2 和 NLB 跨区）。三类流量天然产生：副本同步（数据库、Kafka ISR）、LB 跨 AZ 转发、服务间随机调用。
2. **治副产品那部分**：K8s Topology Aware Routing 让 Service 优先转同 AZ endpoint；NLB 默认关 cross-zone（ALB 默认开且 ALB 的跨 AZ 免费，这个差异要说对）；有 affinity 的服务组按 AZ 编排。
3. **不动买可用性那部分，但要算出它多少钱**：这才是 senior 的做法：不是「跨 AZ 太贵所以单 AZ」，是「跨 AZ 副本每月 $X，一次 AZ 级故障的业务损失是 $Y，X 远小于 Y 所以这笔钱该花」。
4. **单 AZ 只用在可再生数据上**：One Zone-IA、单 AZ 缓存层、可重跑的批处理中间产物。
5. **诚实边界**：「跨 AZ 流量的成本审计我没有系统性做过。」⚠️ **注意这条与 `resume-expand.tex` 上的 "reducing unnecessary cross-AZ data transfer" 冲突，投简历前必须处理。**

**挂**：`[理论]` + 明确边界。第 3 步的框架是本题的分水岭。

### Q19「NAT Gateway 和 VPC Endpoint，什么时候用哪个？」

**一句定位**
「S3 和 DynamoDB 的 Gateway Endpoint 是完全免费的，所以『用它省 NAT』这道题不需要算，任何非零流量都是 Gateway Endpoint 更省。需要算的是 Interface Endpoint。」

**展开结构**
1. **给单价**：NAT Gateway $0.045/小时 + $0.045/GB 处理费，而且经 NAT 去互联网还要**再叠加**出网流量费（双重收费）。Gateway Endpoint（只有 S3 和 DynamoDB）无小时费无 GB 费。Interface Endpoint（PrivateLink）$0.01/小时/ENI/AZ + $0.01/GB。
2. **给 Interface Endpoint 的平衡点公式**：`月流量 × ($0.045 − $0.01) vs ENI 数 × 720h × $0.01`。低流量服务上 Interface Endpoint 可能比走 NAT 更贵，因为每个 AZ 一个 ENI 的小时费是固定的。
3. **锚到自己的架构（这是本题最好的一段）**：「Doris 存算分离让 BE 持续读写 S3。如果这些流量走 NAT，那就是 $0.045/GB 的处理费叠加在一个本来就请求密集的访问形态上。所以**『存算分离必须配 S3 Gateway Endpoint』是一条应该写进部署 checklist 的规则**。」
4. **诚实边界**：「我们当前有没有配这个 endpoint，我要确认一下，这正是我说成本可见性薄的具体表现：这类科目应该在账单上被看见，我们看不见。」

**挂**：`[理论]` + Doris 架构的推导。第 3 步是从自己架构推出结论而不是背 feature，这是关键区别。⚠️ 面试前跟瑞哥确认第 4 步的实际情况（已列入 S07 提问清单第 12 条）。

### Q20「可观测性自己的成本怎么控？」

**一句定位**
「我在这上面有一手场景：600+ 节点、约 1.2M active series、约 80K samples/s。而我最想说的一条是自己的复盘：**cardinality budget 应该在第一天就存在，不该等增长曲线逼出来。**」

**展开结构**
1. **给成本模型**：成本 ≈ active series 数 × 保留时长 × 单位存储成本，而 series 数是**乘法爆炸**的那一项：加一个 label 不是加法而是乘法，**加 tenant label 是最典型的爆炸源**（节点级指标乘租户数）。
2. **给自己做的四条治理**：核心 SLI 才做 tenant-level recording rules；基础设施指标一律不带 tenant label；retention 分层（tenant SLA 90 天 / 排障 30 天 / 基础设施 15 天）；定期 cardinality 审查抓意外的高基数 label。
3. **给数字**：同一个 3 个月窗口，federation 下的 Prometheus 约 930GB，VictoriaMetrics 约 250GB（约 4× 压缩）；冷数据 5 分钟降采样放 S3，180 天约 25GB。**主动说清：省下来的不是靠砍数据，是靠换引擎加降采样分层。**
4. **给一条方法论**：**降采样而不是删除**，因为它把「保留时长」和「分辨率」解耦了。长周期趋势不需要秒级，短周期排障不需要 180 天，危险的是用同一份数据同一个 retention 去满足两种需求。
5. **诚实边界两条**：这个项目当时的驱动是可靠性（每周 OOM 2-3 次、45 秒数据滞后）不是成本，我只汇报了可靠性收益，没算过美元金额，这是遗憾；**日志的成本治理我有零散动作没有体系**（理论上知道该按 stream 分级保留、高基数字段留在 body 不提成 label、对高频重复日志采样、把日志量做成 showback 指标，但没落地过一次）。

**挂**：S08 + S06（日志 TTL 那部分）。

## 组五：组织与流程（Operate 层）

### Q21「怎么说服业务方接受成本约束？」（必问）

**一句定位**
「核心原则是**不要替业务做 SLA 降级的决定**。工程师最常犯的错是自己判断『慢 10 分钟没关系』然后就调了参数。我的做法是把 trade-off 量化成选项，让业务选。」

**展开结构**
1. **给自己真的走过这个流程的例子（S04）**：Iceberg 的 `commit.interval` 从 60 秒拉到 10 分钟，写侧文件数降约 3 倍，代价是端到端可见性变成约 10 分钟。**这条是和业务确认「10 分钟可接受」之后才定的。** 如果业务说不行，正确动作不是硬调这个参数，是回到别的杠杆（target file size 或写批大小）。
2. **给对话的四步结构**：
   - 把成本换成业务语言（不说「NAT 处理费每月 $X」，说「等于一个工程师半个月」或「每笔交易多花 Y 分钱」）
   - 把可靠性代价量化成**选项**而不是描述成**风险**（不说「可能会慢」，说「A 方案月省 $X 代价是 p99 从 200ms 到 400ms；B 方案月省 $X/3，p99 不变」）
   - 明确谁有权决定：**SLO 是业务契约，改 SLO 是业务决策；在 SLO 之内怎么省钱是工程决策。** 这条边界划清楚，成本对话就不会变成扯皮
   - 用 error budget 做共同语言，把降本动作的代价变成预算消耗
3. **也要能说不**：「老板要砍 30% 的时候，我会给一个带风险标注的方案组合，并且明确列出我建议不砍的部分和理由。**能说清哪些成本不该砍的人才是 senior。**」

**挂**：S04 的 `commit.interval` 那一段是这题的核心证据，务必用。

### Q22「Showback 和 Chargeback 有什么区别？你会怎么落地？」

**一句定位**
「区别是『展示』和『计入预算』。真正的难点不在技术，在归因精度必须匹配后果的严重性，所以我不建议为了『更严格』而过早上 chargeback。」

**展开结构**
1. 定义与阻力：Showback 是展示给花钱的团队，组织阻力低、靠自觉；Chargeback 是计入团队预算/P&L，行为改变力强但阻力高。
2. **给三个落地难点**：
   - **共享成本怎么分**（K8s 控制面、监控栈、日志栈、NAT、共享数据库不属于任何单一团队）。按用量比例、按人头、按收入比例都不「公平」，**关键是提前把规则说清楚并且不常改**，chargeback 的可信度来自可预测性而不是精确性。
   - **idle 成本归谁**。全摊给 workload 会让团队觉得账单虚高，不摊就没人有动力压 idle。OpenCost 的 `max(request, usage)` 语义是一种回答：预留但没用的算在申请方头上。
   - **精度必须匹配后果**。Showback 阶段 80% 准确度就够（目的是引发对话），一进 chargeback 每个争议都会变成会议。
3. **锚到自己**：「我们是多租户 SaaS，天然有 per-tenant 成本归因的需求，那也是算毛利的基础。我已经有租户维度的可观测性（per-tenant SLI recording rules），缺的是把成本维度挂上去。所以我知道下一步该做什么，只是还没做。」

**挂**：`[理论]` + per-tenant 可观测性的一手锚点。

### Q23「FinOps 在组织里应该谁负责？你们是怎么做的？」

**一句定位**
「诚实说：我们没有 FinOps 实践，成本是散在各个 owner 手里的。我做的是自己系统里的架构级降本，不是组织级的成本治理。」

**展开结构**
1. **说清 Inform / Optimize / Operate 三阶段自己的位置**：Optimize 强（且偏架构那一半），Inform 薄，Operate 基本没有。**并且主动说这个顺序是反的。**
2. **说清为什么会反**：Optimize 有立竿见影的成绩，Inform 是基础设施投入。跳过的代价是只能优化你正好看见的地方。
3. **给自己的证据（S06）**：TB 级的无主存储在多个集群持续增长，是被 OOM 发现的不是被账单发现的。**这件事让我改变了对成本可见性的看法。**
4. **说清理想形态**：FinOps 是跨职能的（工程 + 财务 + 业务），工程负责可见性和优化能力，财务负责承诺采购和预算，业务负责单位成本目标。**中央团队定标准和工具，分布式 owner 负责自己的账单**，集中式做不动，因为只有 owner 知道哪些资源该留。
5. **说清自己想承担的角色**：「我更适合做工程侧的那一半：把成本变成可观测的指标、把护栏做进 IaC、把架构级降本的机会找出来。承诺采购和预算流程我需要学。」

**挂**：诚实边界为主 + S06 做证据 + `[理论]` 做框架。

### Q24「你们有做过成本相关的机制建设吗？还是都是一次性动作？」

**一句定位**
「我在数据层建过机制，在云资源层没有。而我认为『只做一次性清理不建机制』是这类工作最常见的失败模式，因为浪费会长回来。」

**展开结构**
1. **给自己建过的机制（S06 三层）**：配置层给默认无 TTL 的内部日志表加 TTL、把数据量最大的日志直接关闭；流程层把「审计带后缀残留」写进升级 runbook 的最后一步（因为**每次升级都会重新制造这个隐患**）；舰队层定了「一处确诊立即全舰队审计」的动作。
2. **主动做自我批评**：「这三层里我最不满意的是没有做成自动化的检测项，仍然依赖 runbook 里的人工步骤。」
3. **也给弹性侧的机制**：空闲 reaper（所有 BE 无 fragment 活动超 30 分钟才回收到 0）是防「弹起来忘了缩」的成本泄漏，那是机制不是流程。
4. **说清云资源层的缺口和补法**：护栏做进 IaC 和 CI（tag 强制、request 上限、生命周期策略默认开）、周期性自动检测（未挂载卷、老快照、闲置环境）、单位成本做成常态指标。
5. 收一句原则：**「成本护栏必须在系统上线前定，事后治理永远是被动的。」** 这句话我是从 cardinality 治理里学到的：cardinality budget 应该在第一天就存在，而不是等增长曲线逼出来。

**挂**：S06 + S01（idle reaper）+ S08（cardinality budget 那句复盘）。
