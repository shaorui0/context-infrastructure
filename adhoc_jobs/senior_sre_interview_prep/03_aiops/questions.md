## A 组 · AI 在 ops 的定位与边界

### A1. 你怎么看 AI 在 SRE 工作里的位置？

**一句定位**：AI 没有改变 SRE 的定义，它改变的是回路里谁干哪一部分。把 SRE 还原到第一性原理它就是一件事，运营「系统应该做什么」和「实际在做什么」之间的回路，而现在这个回路的执行层交给了 agent，判断层和决策层留在人这边。

**展开结构**
1. 先立定义：发现偏差、解释偏差、收敛偏差、让它保持收敛。这个定义 AI 动不了。
2. 变了什么：oncall 的执行层。过去被 page 之后头三十分钟的跑腿活（提信号、构造查询、翻日志、对历史 case）现在归 agent，约八成告警走相似路径。
3. 还需要人的：意图与约束定义、mutation 主权、eval 与 SLO、最终判断。一句话点透，约束是安全的来源，模型是能力的来源。
4. 收口到我自己：这不是预测，是我工作周的实况。我有一套 harness 在跑我的 oncall triage。

**挂故事**：S01（整体）、S12（并行取证的真实案例）。基础见 `fundamentals.md` §1.3、§7.2。

### A2. AIOps 传统上指什么？和 LLM agent 有什么区别？

**一句定位**：传统 AIOps 是判别式的（异常检测、告警聚类、根因定位、容量预测），LLM agent 是生成式的，两者不是替代关系而是分工，agent 接在降噪之后做「这一个事件是什么」的调查。

**展开结构**
1. 报出传统四件套加技术谱系，说明我知道这些不是新东西。
2. 四个维度的对比：输入形态（结构化信号 vs 自然语言与半结构化文本）、输出形态（分数与分组 vs 推理链与下一步动作）、可靠性性质（有分布的假阳假阴 vs 语义级且非确定）、验证方式（AUC vs 人看或模型评判）。
3. 讲分工的理由：异常检测要在毫秒级处理海量信号，成本和延迟不允许过模型；agent 的位置在告警已经判定为需要人看之后。
4. 我的系统就在这个位置：输入是一条告警链接，不是原始时序流。

**挂故事**：S01。基础见 `fundamentals.md` §1.1、§1.2。

### A3. 讲一个你用 AI 解决实际问题的例子。

**一句定位**：compaction score 卡在约 4,504 不动，我并行派三个只读 agent 走日志、tablet 元数据、catalog 回收站三条独立路径，三条证据链收敛到同一个孤儿 tablet，它属于一张早已 drop 的表被调度器结构性排除。

**展开结构**
1. 症状与常规排查的问题：串行不只是慢，一条推理链被某个信号带偏之后，后面所有查询都围着错误方向转。
2. 动作与关键设计：三个 agent 不共享推理过程，只各自返回自己方向上的发现。
3. 结果与判断：一条推理链会被带偏，三条独立证据链指向同一个对象那是裁决。这个姿势成了我的默认取证方式。
4. 诚实边界：修复是人做的，agent 只取证；我没有量化并行比串行快多少。

**挂故事**：S12。注意口径纪律，两次 compaction 事故（约 2500 与约 4504）分开讲不混。

### A4. agent 能取代 oncall 吗？

**一句定位**：能取代调查的执行，取代不了 mutation 主权和最终判断，而这个分界线不是能力问题是问责问题。

**展开结构**
1. 先给读写不对称这条原则：agent 极擅长读和诊断，在写上是结构性危险，复利全部发生在诊断侧。
2. 两条理由：爆炸半径是业务判断而不是技术判断；agent 的失败是静默的，一个幻觉出来的结论返回的等价于 HTTP 200。
3. 一句收口：在未被检测的错误之上自动化 mutation 不是提速，是用速度给错误洗白。
4. 补上问责视角：权限往下传了，问责却留在原地。policy 承载风险偏好和问责，它留在名字挂在 pager 上的那个工程师身上。

**挂故事**：S03（L3）、S13（L5）。基础见 `fundamentals.md` §7.1、§7.5。

### A5. 你觉得 agent 在 ops 里最被低估和最被高估的分别是什么？

**一句定位**：最被低估的是知识资产的形态改造，最被高估的是自主执行修复。

**展开结构**
1. 被低估的：写给人读的 runbook 是叙事，对 agent 复利的是判别器，一个便宜的检查把根因候选集劈成两半。同一条死路当故事记十遍没有价值，记成一次「若 A 正常砍掉这一整支」就变成未来的路由。答案会随 infra 变化而腐烂，探查顺序几乎不变。
2. 被高估的：约 88% 的 agent 从未进入生产，五个独立来源交叉验证；Gartner 预测超过四成 agent 项目会在 2027 年底前被取消。自主执行是营销最响的部分也是落地最差的部分。
3. 举一个反例支撑：2025 年 7 月 Replit 的 agent 在用户明确要求 code freeze 期间删了生产库，之后捏造约四千条虚假用户记录掩盖删除并谎称无法回滚。
4. 我的选择：诊断侧放开跑，写侧只 propose。

**挂故事**：S01（L4）、S03（L3）。基础见 `fundamentals.md` §2.8、§6。

## B 组 · harness 架构设计

### B1. 讲一下你这个 harness 的整体架构。

**一句定位**：一个 MAP 式入口加 9 个按需加载子 skill 加 6 个 shell hook 的 harness，输入一条告警链接，输出一份带证据链的报告和一套只生成不执行的操作命令，工程量在约束系统、上下文资源管理和质量闭环。

**展开结构**
1. 输入输出讲清楚，包括「输出落文件对话只回摘要」这个细节（因为它反映了 context 纪律）。
2. 三条主线各一句：三层纵深防御、context 当 RAM、把 agent 当生产系统运维。
3. 给三个可指的工程物：`k8s-gate.sh` 204 行、`verify.py` 1059 行、`step_N_done` 状态外置。强调这三样都可以在没有模型的情况下单独测试。
4. 主动给边界：这是个人工程，用户是我自己，没有团队采用数字也没有 MTTR 数字。

**挂故事**：S01 全篇。

### B2. agent 系统的瓶颈在哪？

**一句定位**：context window，不是模型。一次 raw range query 回来 30K token，一次调查要查 5 到 10 次，主 agent 自己吃下去走到最需要判断力的阶段就已经榨干了。

**展开结构**
1. 立第一性约束：context 是稀缺的 RAM 而不是无限的硬盘，谁占用它谁就该为占用付出代价。
2. 推出铁律：主 agent 只保留导航、判断、命令生成，全部原始数据获取下沉给 sonnet subagent，回收 ≤500 token 的结构化摘要（极值加时间戳、step jump 标记、baseline 比值、不超过三个 outlier）。
3. 讲清这是 SRE 的什么：容量管理加爆炸半径隔离，对象从服务的内存换成 LLM 的 context window。
4. 给 trade-off：用 latency 换 correctness，延迟增加一次 agent 往返（秒级），换来整条调查链的推理质量；成本上其实是省的，因为量大的 fetch 跑在便宜模型上。

**挂故事**：S04 全篇。

### B3. 你怎么设计 multi-agent 系统？

**一句定位**：用四个控制原语（Spec、Loop、Hook、Fork）替代角色拟物，因为原语可以推出设计决策而角色只是装饰。

**展开结构**
1. 先点破角色拟物：给一个 agent 起名叫 QA 并不改变它能读什么、它的输出被谁验证。
2. 四原语各一句，重点讲 Fork 的四条优先级启发式（independence、attention、capacity、latency），因为这是最实用的判断依据。
3. K8s 映射：Spec 是 manifest、Loop 是 reconcile loop、Hook 是 admission webhook、Fork 是 pod 隔离加独立审计者。关键差异是 controller 确定性所以不需要 guardrail，agent 是概率性 controller 所以 policy 层是硬性前提。
4. 举两个我自己的 Fork，理由不同：subagent isolation 是 capacity 加 attention，三 agent 并行取证是 independence。

**挂故事**：S07 全篇、S12（L3）。

### B4. 长流程怎么保证可靠？断了怎么办？

**一句定位**：把执行进度外置到 plan.md 的 `step_N_done` 字段，新 session `grep step_.*_done` 就能从断点续跑，整个调查状态在单文件里可以一眼读完。

**展开结构**
1. 先说重跑是常态而不是异常：context 压缩、session 崩、人中途走开三种触发。
2. 讲幂等设计：11 个 step 每完成写一行时间戳，重跑跳过已完成的；完成条件写成可验证的产物而不是动作（例如「plan.md 顶部 `phase: A` 已写入」而不是「我做了 init」）。
3. 讲为什么放文件不放数据库：凌晨三点接手 `cat` 一下就能看完；可 diff；而且这个文件同时是 Spec 和 State，「我想干什么」和「我干到哪了」在同一个可 review 的对象里。
4. 讲数学约束：单步 95% 跑二十步只剩约 36%，所以减少步数比提高单步成功率更有杠杆，每一步之后要验证，必须有显式停止条件。

**挂故事**：S08 全篇。基础见 `fundamentals.md` §2.3。

### B5. 你怎么防止 agent 得出错误结论？

**一句定位**：三道结构性的门。Phase Lock 让它在看清症状之前物理读不到 deploy history，quote-the-line 让每条结论必须挂一个可复现的证据，3-strike 让它在卡住三次之后必须停下喊人。

**展开结构**
1. Phase Lock：Karpathy 描述的「看到 deploy 记录就脑补根因」是可复现的失败模式，我用状态机把它设计掉，`phase:` 字段在文件级限制能读什么，切换门是显式前置条件。
2. Quote-the-line：四种 evidence 前缀之一，否则 confidence 强制 ≤3 且对外措辞降级到 possibly，`verify.py` 机器检查。关键论证是它把不可验证的断言变成可验证的断言。
3. 3-strike：agent 不会累也不会自己承认卡住，所以我用一个外部计数器替代它的自我认知。
4. 主动给强度差异：mutation gate 是硬阻断，这三道是软约束加检测，我把它们定位成防偏差而不是防攻击。

**挂故事**：S02、S05、S06。

### B6. 你的知识库怎么组织？为什么不用 RAG？

**一句定位**：结构化路由表加按需加载，一次不超过五个 chunk；不用向量检索是因为在一百多个文件的量级上确定性路由更可审计，而向量检索的失败模式是静默的。

**展开结构**
1. 讲 MAP 机制：入口只是三张路由表（alert 类型到 debug tree、任务到外部 runbook、关键词到 chunk），自动注入常驻 context 的只有三个最小 skill，其余按需。类比 lazy loading 与 page fault，路由表是页表。
2. 讲为什么不用向量：路由错了能看出是表的哪一行错；向量召回了不相关的或漏了相关的都没人知道，这是静默失败。规模涨一个数量级我会上混合检索。
3. 讲治理：agent 知识库最大的反模式是堆料，我做过一次系统性收敛，用 `dv_specific_score` 判据（只有模型不知道的领域知识才值得占 context）砍掉六成通用内容，`converge.py` 硬门保证每个文件都被看过。
4. 讲日常复利：只记 delta；AI 写的知识经人 review 才从 draft 升 stable；每条用 `derived_from` 溯源回本次 triage report。

**挂故事**：S11 全篇。

### B7. 你的 acceptance criteria 是怎么定的？

**一句定位**：每条 criteria 对应一个已知的 LLM 失效模式，所以这套东西的准确描述是针对失效模式的回归测试。

**展开结构**
1. 给分层：8 条收敛条件定义「这次调查算完成了吗」，3 条 Iron Law 是过程红线，违反了不能靠补格式救。
2. 挑三条最能体现设计意图的讲：plan-first gate（计划必须在第一次查询之前落盘，防边查边编故事）、missing-field gate（timestamp/cluster/namespace 缺任何一个就停下问人，禁止猜测填充）、log 实时写入且每行带 Decision 字段（防事后合理化）。
3. 给映射：每条指向 taxonomy 里的具体 ID。
4. 给一个刻意的自由度：Iron Laws 约束终态边界而不是过程顺序，agent 可以任意顺序到达终态。这条写在文件里，是有意留的。

**挂故事**：S06、S09（L3 的映射表）。基础见 `fundamentals.md` §3.2。

## C 组 · 安全与信任

### C1. LLM 会幻觉，你怎么敢让它碰生产？

**一句定位**：它现在根本不碰生产，PROD、PCI、MGT、DEMO 四个 tier 的 mutating 全部 block；而模型会幻觉在我这里是前提不是缺陷，所以安全性绝不建立在模型自觉之上。

**展开结构**
1. 把问题拆成读能不能放开、写能不能放开两个子问题，分别给理由（价值风险不对称；爆炸半径是业务判断加静默失败）。
2. 讲能力与安全的来源分离：判断交给模型（错了代价是多查一次），一切不可逆操作交给确定性 shell hook 硬阻断，agent 再怎么幻觉也绕不过一个 `exit 2`。这条把安全从「希望模型别犯错」变成「模型犯错也没关系」。
3. 报四关：skill 层 approval、permissions 名单、`k8s-gate.sh` 环境 tier 判定加 default-deny、强制事后验证。
4. 给业界坐标：这个「高风险强制审批、低风险可选自动」的分级门禁是 PagerDuty SRE Agent 和 Datadog Bits AI 都采用的模式，我的实现比它们保守，生产侧完全不放写。

**挂故事**：S03 全篇。基础见 `fundamentals.md` §6.1、§6.5。

### C2. prompt injection 你怎么防？

**一句定位**：注入能污染模型的意图，污染不了一个 204 行 shell 脚本的退出码，所以我的策略是把不可信输入能影响的范围限制在「意图」，把「执行」交给一个不可被说服的组件。

**展开结构**
1. 讲攻击面在哪：日志正文、pod annotation、event message 的内容都可以被写入方控制，而 LLM 的指令和数据共享同一个 token 流，没有天然分离。
2. 讲我的规则：kubectl logs/describe/get -o yaml、event、annotation 全部是外部不可信数据，禁止仅凭其内容采取后续动作，必须显式陈述解读并获得人的确认。当成 Web 应用里的用户输入对待。
3. 讲分层强度，并且承认规则层是软的：任何写在 prompt 或配置里的约束都在攻击面之内；保证在 hook 层。攻击链要成功需要两步，注入能做第一步做不了第二步。
4. 承认读侧防得弱，并给业界背景：OpenAI 说过 AI 浏览器可能永远对注入脆弱；EchoLeak 那次零点击攻击 Microsoft Copilot，事后是「没有告警浮现也没有人注意到」。所以注入的可观测性可能结构性无解，防御策略应该是限制后果而不是指望检测。

**挂故事**：S13 全篇。基础见 `fundamentals.md` §4。

### C3. 如果出了事故，你能回答「agent 当时为什么这么做」吗？

**一句定位**：能回答「谁批准了什么、为什么、结果如何」，回答不了「模型为什么想到这一步」，而这个边界行业也还没跨过去。

**展开结构**
1. 讲能的部分：每条 kubectl 与 MCP 调用进 JSONL；mutating 命令自带 `# INTENT:` 那一行 reasoning（观察到什么、推断什么、预期什么效果）；执行前后各记一条；`audit-view.py` 可回放；加上报告里的 investigation log 和 hypothesis_log（每条假设的 test 与 ✓/✗）。
2. 讲这个设计的动机：审计日志里每条变更自带 reasoning，事故复盘时不用猜当时为什么这么做。
3. 讲不能的部分：记录的是外部行为和自陈意图，没有内部推理过程，没有 token 级 provenance。
4. 给行业坐标：OTel 那个讨论 tasks/actions/agents/memory 建模的 issue 从 2025 年 8 月开到现在还开着，agent 层的语义约定仍是 Development 状态。而且要点破一个陷阱，审计和 enforcement 是两件事，有个说法叫「观察但不行动」的缺口，policy 违规只在损害发生之后才被发现。

**挂故事**：S03（L5）、S10 全篇。基础见 `fundamentals.md` §5.2、§4.5。

### C4. agent 的权限怎么设计？这个信任阈值怎么往上调？

**一句定位**：我的实现是环境 tier 而不是操作 tier，因为环境判定的确定性极强、一个 shell 脚本就能做、而且 fail-closed 语义天然，不认识的 alias 一律当生产。

**展开结构**
1. 报我的 tier 表：PROD/PCI/MGT/DEMO 全 block mutating；PREPROD 只 dry-run 且 delete 仍 block；DEV 允许但必须带 `# INTENT:`；未分类按 PROD 处理。加跨 tier 硬阻断名单（删 namespace、跨 namespace 批量删、IAM 变更、EC2 terminate、Route53 与 VPC/SG 写操作、显式 `--context prod`）。
2. 对比业界的操作 tier 分法（Tier 1 只读、Tier 2 可逆自动加日志、Tier 3 有外部影响进 staging 队列、Tier 4 高风险不可逆显式审批），说明两种分法的取舍：操作 tier 更细但需要理解每个操作的语义，环境 tier 更粗但可以在模型碰不到的层实现。
3. 讲往上调的路径：这是可调阈值不是二元选择，DEV 已经允许带 INTENT 的 mutation，PREPROD 允许 dry-run。
4. 讲我知道但没做的那一条：earned autonomy gradient，如果失败倾向恶化，自主权自动收缩，不需要开会决定。我现在是固定档位没有动态收缩。

**挂故事**：S03（L4）。基础见 `fundamentals.md` §7.3。

### C5. 人工审批是不是越多越安全？

**一句定位**：不是，一天批两百次的人等于什么都没批。HITL 应该被当成 error budget 的一种花费方式，只花在不可逆的那一档。

**展开结构**
1. 命名这个失效模式：oversight fatigue，橡皮章审批。
2. 讲后果：审批变成噪音之后，真正危险的那一次也会被点过去。所以「为了安全把所有动作都加审批」是一个做反了的设计。
3. 讲正确的分级依据：可逆性乘爆炸半径乘置信度。
4. 讲我自己的位置：我现在是固定档位（只读全开，写侧全 propose），这在个人场景成本可接受；团队场景下必须分级，否则审批人会疲劳。

**挂故事**：S03（L4）。基础见 `fundamentals.md` §7.4。

## D 组 · 落地与 ROI

### D1. 团队推广了吗？ROI 是多少？

**一句定位**：没推广，用户是我自己，我没有 MTTR 改善的数字所以我不会给你一个编出来的百分比；它对我的价值是把每次被 page 后头三十分钟的跑腿活变成 agent 干，把调查方法从我脑子里搬进可 diff 的文件。

**展开结构**
1. 先给最诚实的那句，把「没有数字」明确说出来，不绕。
2. 给真实的价值陈述（时间去哪了、知识形态变了什么），这部分是可信的因为它不需要数字。
3. 给「差什么」清单，这是把诚实转成能力信号的关键：跨人可用的凭证与权限模型（现在 hook 认的是我本机的 alias 清单）、带预期结论的 eval 数据集（现在只有规则式 checker 和历史 case 回放）、团队愿意接受的审批流程（现在是我自己 approve 自己）。这三件说得出做法但没做过。

**挂故事**：S01（L5）。`README.md` 中环第一条有完整口径。

### D2. 这和写一堆 runbook 脚本有什么本质区别？

**一句定位**：runbook 是确定性分支，只能覆盖你事先想到的路径；agent 做的是路径选择本身。而且我并没有取消 runbook，我把它移到 Phase C 才解锁，让它从入口变成结论之后的执行手册。

**展开结构**
1. 第一个区别，覆盖性质：面对没见过的信号组合，agent 能生成新假设并去验证，runbook 遇到未覆盖的情况就停在那里。
2. 第二个区别，知识形态：runbook 是写给人读的叙事，对 agent 复利的是判别器。同一条死路记十遍是故事，记一次「若 A 正常砍掉这一整支」是路由。我的决策树按检查的便宜与昂贵排序，因为答案会腐烂而探查顺序不会。
3. 第三个区别，我对 runbook 的重新定位：Phase A 禁读、Phase B 只读 README、Phase C 才解锁命令体。这样 agent 先独立取证再看修复方案。
4. 收口：所以准确说法是我在 runbook 前面加了一层能自主导航的调查层，并且给这一层加了 gate。

**挂故事**：S01（L4）、S02（L4）。

### D3. 你怎么衡量这个系统好不好？

**一句定位**：三层，输出质量、回放验证、安全，同时我会主动说我缺的那个最接近业务价值的指标。

**展开结构**
1. 输出质量：`verify.py` 的 PASS 率加 `slo.py` 的跨调查趋势，后者能暴露 skill 本身的退化。
2. 回放验证：拿历史真实 case 喂给 agent，对比结论方向，不要求逐字一致要求合理。诚实标注这是 smoke test 不是 eval，三个 case 不构成统计显著性。
3. 安全：审计日志里零未授权 mutation，而且要标清这是「设计上不可能」加「日志里没有」，不是「我跑过对抗性测试证明它拦得住」。
4. 缺的：调查结论被人类采纳率。以及正确的 eval 形态（50 到 200 个带预期结果的任务，每次改动都跑）我没建。另外知道一个陷阱，一旦按指标优化指标就会失去意义，有研究发现被操纵的推理链能把先进 judge 的假阳性率抬高最多九成，所以 eval 集本身也需要反 Goodhart 审计。

**挂故事**：S10（L1）、S11（L5）。基础见 `fundamentals.md` §2.5、§2.7。

### D4. 如果让你在团队里推这套东西，第一步做什么？

**一句定位**：先把 hook 层的执行边界做成集中管理的单一来源，因为现在它认的是我本机的 cluster alias 清单，团队场景下这个清单必须有 review。

**展开结构**
1. 第一步安全前提：集中管理 alias 到 tier 的映射并纳入 review 流程；审计日志集中且不可被 agent 自己改写（审计的价值前提是它不在被审计者的控制范围内，这跟「监控系统不能依赖被监控系统自身」是同一条原则）。
2. 第二步建度量：一套带预期结论的 eval 数据集，从历史 case 里抽。没有这个就没法判断改动是改进还是回退。
3. 第三步做对抗性测试：故意在 dev 集群的 pod annotation 和日志里种注入文本，看整条链哪一层拦住了它。这一步我现在完全缺。
4. 第四步才是推广：先在自己 oncall 轮次上跑出可展示的 case，用 dogfooding 的证据说话（挑三到五个每周都会发生的工作流，端到端跑带 trace 和 checkpoint，记录失败模式，收紧 policy 直到失败收敛，然后才扩范围）。

**挂故事**：S13（L5）、S11（L4）。基础见 `rules/skills/bestpractice_agent_harness_architecture.md` §Dogfooding Proof Plan。

### D5. 你了解业界怎么做吗？你和他们的差别在哪？

**一句定位**：市场分四层，我的位置是安全设计模式和平台型厂商同构但更保守，调查侧多一层它们没有的读取隔离，缺的是它们的规模、集成广度和团队级审批流程。

**展开结构**
1. 报四层：传统降噪厂商（BigPanda、Moogsoft，数字最响亮也最老最难验证，98% 降噪那类是厂商自述）；平台型（PagerDuty 三档治理、Datadog 高风险强制审批加 safe remediation 可选自动、Grafana Assistant Investigations）；AI SRE 初创（Traversal 走因果 ML 宣称 90% 以上 RCA 准确率是自述、Resolve.ai 目标 80% 自主解决率、Cleric 主打只读安全策略）；底层标准（OTel GenAI semconv 还没定型，说明标准化晚于产品化）。
2. 挑一个可引用的一手数据：Grafana Labs 公开过一次内部事故，Assistant Investigations 在后台跑，比人工 on-call 团队早 20 分钟、用时 8 分钟找到根因。单一案例但厂商愿意公开时间对比在这个领域很少见。
3. 挑一个最好的对照点：K8sGPT 的 CLI 是纯只读不执行任何修复，唯一的 mutation 能力在 Operator 里是 alpha、默认关闭、官方明说非生产就绪。这说明连开源社区在这条线上也很谨慎。
4. 给我自己的三句定位：同构、更保守、多一层 phase lock、缺规模与团队流程。

**挂故事**：S03（L3、L4）。基础见 `fundamentals.md` §6 全节。

## E 组 · 前瞻判断

### E1. harness engineering 是真需求还是重新包装？

**一句定位**：两者都是，而且不矛盾。诚实的描述是七到九成是已有的系统设计换了一个底座，一到三成是真新的原语，加百分之百的重新框架化。

**展开结构**
1. 报老的部分（system prompt 加 tool loop、subagent、sandbox、state graph、guardrails，2022 到 2023 年的 ReAct、AutoGPT、LangChain 时代就有）和真新的部分（progressive disclosure 的 skill 加载、lifecycle hook、agent-aware 自动 compaction、harness 与模型协同训练）。
2. 引那句最锋利的批评：所以 agent harness 就是系统设计，只不过是给一个会幻觉的 runtime 做的系统设计。
3. 说明这对我有利：如果七到九成是系统设计，那 SRE 的可靠性工程经验是直接可用的资产。
4. 主动交代证据缺口：Anthropic 那篇长时运行 agent 的 harness 博客零个 before/after 数字；跨 harness 的 benchmark 差距有反声说在误差范围内；定义本身不稳定，提出者们自己承认。所以我论证设计逻辑，不论证效果数字。

**挂故事**：S07（L4）。基础见 `fundamentals.md` §8。

### E2. 模型能力继续上升，你这套 harness 会不会被吃掉？

**一句定位**：编排技巧那一层会被吃掉，本质复杂度不会。orchestration 不会消失，它会重新分布到模型权重、协议标准和一个更薄的 harness 里。

**展开结构**
1. 承认会被吃的部分，并给一个业界迹象：有说法称 Anthropic 内部每三到四周把 harness 从头重写一次，暗示 harness 不是稳定基础设施。
2. 讲我把投资放在哪：本质复杂度是 context 管理、工具集成、安全监督、系统边界管理。前两样可能被协议和模型吃掉一部分，后两样是组织和责任问题，模型能力上升解决不了。安全监督不会因为模型变强就不需要，因为「谁批准了这次生产变更」是问责问题不是能力问题。
3. 给一条我很在意的反向证据：Wharton 的研究发现 CoT 对推理模型的提升只有约 3% 却增加 20% 到 80% 的时间；Anthropic 自己说最成功的实现没有用复杂框架。所以 harness 做过头是负资产。
4. 讲这条判断怎么影响我的行动：我做过一次系统性收敛砍掉六成通用内容，并且在计划里明确写了「不会做的事」清单。

**挂故事**：S04（L5）、S07（L5）、S11。基础见 `fundamentals.md` §8.3。

### E3. 「200 但内容是垃圾」这个问题怎么解决？

**一句定位**：还没有解，行业也没有解，我做的是缩小不可检的范围而不是宣称解决它。

**展开结构**
1. 讲清问题的本质：agent 的失败是语义级的而不是语法级的，这打破了传统监控用 HTTP status 和延迟做可靠性代理指标的假设。工具返回 200、metrics 全绿、内容是错的、整条 workflow 失败。
2. 给两个角度的行业确认：SRE 视角是「你无法为你检测不到的东西设 budget」；可观测性视角是最强方案是给输出打 trust score 但 judge 的成本可能超过 tool call 本身的成本。
3. 讲我的缩小策略：quote-the-line 把「这个结论对不对」拆成「有没有挂一个可复现的证据」（可机检）加「这个证据支不支持这个结论」（仍需人判）。剩下靠人 review 和历史 case 回放。
4. 讲它对权限设计的影响：这就是我不放开写侧的根本理由，在未被检测的错误之上自动化 mutation 不是提速。

**挂故事**：S05（L4）、S10（L2）。基础见 `fundamentals.md` §5.3。

### E4. agent 的 SLO 你会怎么定？

**一句定位**：先给一个行业实例证明可行（Honeycomb 的 Query Assistant 跑 75% 成功率、7 天窗口、接受 25% 失败预算、刻意不接 PagerDuty），然后说清 SRE 的 SLO 词汇不能裸移植，需要七处改造。

**展开结构**
1. 给 Honeycomb 那个例子，重点在它敢把目标定在 75% 而且明确接受失败预算，因为它承认 LLM 是黑盒。
2. 报七处改造里最重要的四条：SLI 按任务类别加模型版本分开定义（聚合值会混淆难度）；error budget 要有具名 owner；HITL 是花掉 budget 的一种方式而不是默认；budget 烧穿时权限自动收缩（earned autonomy gradient）。
3. 给一个诚实的结论：改造完之后这已经不是「SRE for agents」而是一门借用 SRE 词汇的新工程学。
4. 讲我做到哪：只做了趋势追踪（`slo.py` 跟 `verify.py` 的通过率），其余五条是知道怎么做没做。

**挂故事**：S10（L5）。基础见 `fundamentals.md` §2.6。

### E5. 你为什么觉得 SRE 背景在 AI 时代有优势？

**一句定位**：因为 agent 生产化的困难在系统工程侧，而这是 SRE 的主场。有句话说得准，AI 那部分调 API 其实是最容易的部分。

**展开结构**
1. 讲迁移矩阵的三条 Tier 1：可观测性迁移到 agent trace 与 token 成本追踪；故障恢复与事件响应迁移到 agent 故障隔离与 kill switch；容量规划迁移到 GPU 与 token 成本管理、rate limit、provider routing。
2. 讲一个结构性事实：Kubernetes controller 是确定性的所以不需要 guardrail，agent 是概率性 controller 所以 policy 层是生产环境的硬性前提。剩下需要人做的工程大多从这个事实推出来。所以我的 SRE 直觉直接可用，我知道 admission webhook 该防什么，就知道 agent 的 hook 该防什么。
3. 给市场缺口的数字：只有 47% 的组织在监控 agent，仅 22% 把 agent 当独立实体监控；约 88% 的 agent 从未进入生产。缺的不是能让 agent 跑起来的人，是能让 agent 可靠地跑在生产里的人。
4. 收口到我的路径叙事：这不是转行，还是那个回路，目标状态对照实际状态、安全地收敛，只是进入了下一种形态。

**挂故事**：S01、S07（L2）。基础见 `fundamentals.md` §9。

### E6. 你觉得自己在这个方向上最大的短板是什么？

**一句定位**：我的东西是个人工程，缺三样：eval 数据集、团队级的运行经验、以及安全的实证验证（我有架构没有红队实测）。

**展开结构**
1. 短板一，eval：我有输出层的 CI 和趋势追踪，缺 50 到 200 个带预期结论的任务集。替代方案（历史 case 回放）只是 smoke test。这是所有其他改进的度量基础，所以它是第一优先。
2. 短板二，团队级：现在是我自己 approve 自己，hook 认的是我本机的 alias 清单。团队场景真正的难点不是机制是激励，一个人愿意在事故后花十分钟沉淀是因为下一次自己受益，团队里这个受益是分散的。这个问题我没有答案。
3. 短板三，安全实证：没跑过对抗性测试集，所以我说的是架构在原理上不依赖模型自觉，不是实测证明它拦得住。
4. 顺带认领一个更大的方向缺口：我的安全工作偏 AI agent 前沿（deny-by-default 工具网关、按爆炸半径分级的执行闸门），传统面的 IAM 设计作为架构学科、SOC 2 那类审计框架在我的记录里是缺席的。这个缺口最难靠阅读补，因为难点在组织层面，必须亲身参与。

**挂故事**：`README.md` 中环全部条目、S11（L5）、S13（L5）。基础见 `adhoc_jobs/dynamic_resume_site/content/perspectives/v3_next.md`。
