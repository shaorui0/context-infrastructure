# Story S16 — 宽表点查的 IO 扇出：三层引擎改造（STAR）

> 定位：这是 01 方向的**旗舰引擎故事**，也是全部备考材料里唯一一条"我在引擎里下过判断"的线。

## 三层结构（这是叙述骨架，按解决问题的性质分，不按动作顺序分）

| 层 | 性质 | 解决的问题 | 一句话 |
|---|---|---|---|
| **L1 基础架构迁移** | 换地基 | 性能的**前提条件**变了：CH 的快依赖排序键与预先建模，而查询形态一旦不可预测，那个前提就没了 | ClickHouse → Doris 存算分离，把容量与隔离变成可调度的东西 |
| **L2 核心架构层** | 建控制面 | 不可预测的到达 + 互相伤害 + 常驻成本：**管的是「落在哪」** | 弹性计算层 = 评估 → 路由 → 轻重分离 → 主动供给，四件事一个闭环 |
| **L3 定向优化层** | 挖掉浪费 | 输入不可约束（agent 生成 SQL）：**管的是「跑多贵」** | Global Point + Prefetch，只打「可避免的扇出」 |

依赖是单向的：L2 需要 L1 的存算分离（池才可能是元数据构造）；L3 需要 L2 的评估信号（正是它暴露了宽读被字节模型错价）。但 **L3 的安全性不需要 L2 判定正确**。

**两层的分工必须说清，这是最容易被听成"三个优化"的地方：**

> **L2 不让任何一条查询变快，它让每条查询落在对的地方，并让那个地方按需存在。L3 才是真的让一条查询变便宜。**

**一句话主张（开场用）：**

> 宽表点查的成本不在扫描量，在 **IO 扇出与它的串行度** —— 这个判断是 L3 的起点，也是我做完 L2 之后才敢下的。三层都 fail-open：坏索引只能让查询变慢，不能改变结果。

## S — Situation（只给约束，不讲背景故事）

存算分离的 Doris（cloud 模式，算力与 S3 分离）。一张约 **3,727 列**、**~50 亿行**、**566 tablet** 的反欺诈事件宽表（`design/00-architecture.md:39,145`）。两类负载共用一套算力：

- **交互点查**：20ms 量级预算，按用户维度取数
- **宽读**：几百列量级，越来越多由产品功能和 AI agent 生成 —— **输入形态我们控制不了**

约束：不改数据的物理分布（分区/分桶策略维持不变，`design/00-architecture.md:52`）。

## T — Task

不是"让查询变快"。是：**让这两类负载在同一套集群上都可预测** —— 点查不被宽读拖垮，宽读不被当成便宜货放进交互池。

## A — Action：四步，每步都是「先测量 → 再下判断 → 才动手」

### A1. 先证伪自己的直觉

第一反应是加 bloom filter 减少扫描行数。做了：**行数降 73%，墙钟纹丝不动** —— 因为那个用户的行散在 **2,044 个文件**里。

这一步的产出不是优化，是**推翻成本模型**：真正的货币是打开多少个 IO 单元，不是扫过多少行。

### A2. 确认错价是系统性的，不是个案

反方向再撞一次：**3,727 列 `SELECT *` 冷跑 253 秒**，而 planner 的字节体量模型（rows × avg_row_bytes）判它 **light**。

一个高估（被过滤器夹住的 window 点查被判 heavy）、一个低估（宽读被判 light）—— 同一个病因：**估算器结构性看不见扇出**。

### A2b. 为什么优化必须是「定向」的（L3 存在的理由）

这一步的论证顺序很重要，反了就变成"我优化了 `SELECT *`"，然后必然吃到"为什么不直接改 SQL"。

正确顺序是：**先确认输入不可约束，再选优化目标。**

1. SQL 文本、负载、查询形态**全部是我们控制不了的输入**，而且越来越大的一部分由 AI agent 生成 —— 不是人手写、再经过 review。所以"教育调用方"这条路在架构上不存在。
2. 剩下的唯一杠杆：**让调用方可能写出的那些形态本身变便宜。**
3. 但不能什么都优化 —— 判据是：**这条查询的成本里，有多少是「可避免的扇出」**。只打浪费，不打必要成本。

按这个判据筛，两种形态合格：

| 形态 | 浪费在哪 | 手段 |
|---|---|---|
| 非分桶列上的点查 | 打开 566 个 tablet，其中 565 个是纯浪费 | 跨 tablet 点查索引，打开任何 tablet **之前**探测 |
| 宽读（几百列） | 列文件**必须**开（不是浪费），但**串行**是浪费 | 预热 footer 里已有偏移的列 meta page，读循环不动 |

**所以这不是"优化 `SELECT *`"** —— 我们没让宽读少读列，我们让它别串行。这句话是防住那个质疑的关键：**我攻击的是浪费，不是用户的 SQL 风格。**

### A3. 把扇出拆成两个正交的轴，分别下手

| 轴 | 能不能剪 | 做法 |
|---|---|---|
| **tablet 轴** | 可以剪 | Doris 所有内建索引（zonemap / bloom / inverted / short-key / primary-key）都是 **tablet-local** 的 —— 只能回答"这个值在不在我已经打开的这个 tablet 里"。当表不按你过滤的列分桶时，点查只能开全部 tablet。缺的是一个 **plan 期就能回答"哪些 tablet 可能含 X"** 的全局层 → `GLOBAL_POINT` |
| **列轴** | 剪不掉，但能重叠 | 宽读真需要 N 个列文件。但读代码读出来：每列**最多三次**远程读，**只有第 2 次（data page）有数据依赖**，ordinal index root page 与 dictionary page 的字节偏移在 segment footer 解析完就已经在内存里（`column_reader.h:210,281`）→ 并发预热 meta page，串行循环走热缓存 |

**GLOBAL_POINT 的形状**：每个 rowset 一个 bloom，落成 S3 上独立的 `.gpidx`；FE 在 plan 期提取 `=`/`IN` 谓词，把探测值按写路径**逐字节相同**的方式编码，**每 BE 一个 RPC**（566 tablet 通常只对应几个到十几个 BE，`design/04-m3-plan-time-prune.md:284`），结果与 planner 的 tablet 集合**求交**。demo：64 → 1 tablet，`probes=1, degraded=0`（`README.md:126`）。

**预取的形状**：串行循环之前先并发烘 meta page（step A），再提前打开每列的 cache 窗口（step B），按 1 MiB 缓存块去重后丢给**已有的** `segment_prefetch_thread_pool`。串行循环（step C）**一个字节都不改**。

### A4. 让 planner 说真话

把优化器算完就丢掉的 per-operator 估算暴露成 `EXPLAIN ESTIMATE PLAN`（纯增量 diff，15 files / +1,310，不改 cost model 与 statistics calculator），并把"字节体量"这种估算换成**结构事实**：输出列数（`plan.getOutput().size()`）、被夹住的输入基数（WINDOW / PARTITIONTOPN 的 `input_cardinality`）。

后来 v3 干脆砍掉所有依赖 CBO 字节估算的规则。**一个可信为事实的信号，胜过一个更好看但不可信的数字。**

## 五层追问防线

### L1｜"你怎么知道成本在扇出上，而不是在扫描量上？"

两次反向测量互相印证：bloom 砍掉 73% 行数、墙钟不动（一个用户的行散在 2,044 个文件里）；3,727 列 `SELECT *` 冷跑 253 秒而估算器判 light。一个证伪了"少扫行数就会快"，一个证伪了"字节少就便宜"。**扇出是地板。**

### L2｜"加 GLOBAL_POINT 会带来什么新问题？"（主动全讲，别等被挖）

| 新问题 | 具体代价 | 出处 |
|---|---|---|
| **写放大** | 每个 rowset 建 bloom，复用写路径已有的列值流，**只多一次 hash + 插入，无额外 IO** | `design/00-architecture.md:120` |
| **存储** | 规划量级 **10–20 GB**（不是最初估的 6–8 GB，因为 `optimal_bit_num` 向上取 2 的幂，最坏 ×2）；preprod 实测 4 BE 下每 BE **3–4 GiB**、单 BE 最坏 **≈14 GiB** | `design/00:176`、`design/14:26`、`design/15:234` |
| **plan 期多一跳 RPC** | 500ms 预算；**冷 BE 上可能真付一次 S3-bound 的停顿**才降级（cache-only prune 方案被否为"太复杂"） | `README.md:101`、`design/12:34-36,129-130` |
| **缓存挤占（真正的代价）** | `.gpidx` 走 file cache 的 **INDEX 队列**（默认 `index_percent=5%`），而 NORMAL 是**剩余**队列 —— **加给 INDEX 的每一个百分点都直接从装列数据的 NORMAL 里扣** | `design/15:238-245` |
| **compaction 耦合** | 正常 compaction 免费重建；但 **ordered-rowset 快路径**（`do_compact_ordered_rowsets`）直接 link segment、不走 column writer，输出 rowset **静默失去索引** | `design/06:43-53` |
| **假阳性** | 见 L3 | |
| **回收泄漏** | `.gpidx` 不在 recycler 的枚举路径里，不修就**永久泄漏在 S3** | `design/09:170` |

### L3｜"bloom 会误判，你怎么保证结果对？"

**FPP 必须定义成"每 tablet 的预算"而不是"每个 bloom 的参数"**：`p = p_tablet / B`，而 **B（每 tablet 的 bloom 数）由 segment/rowset 数决定，不是一个 config 旋钮**（`design/00:151,161`）。

| B | tablet 级并集 FP | 期望误扫 tablet 数 |
|---|---|---|
| 1 | 1% | ~6 / 566 |
| 5 | 5% | ~28 / 566 |
| 50 | ~40%（并集界已饱和） | ~226 / 566 → **剪枝基本失效** |

**这是这个索引最深的一个结构性代价：它的价值随 B 衰减，也就是把查询性能耦合到了 compaction 的健康度上。** 主动说这句 —— 它证明我知道自己引入了什么长期负担，而不只是拿到了一个 demo 数字。

正确性上只朝一个方向倒：**over-scan, never skip**（I1）。每条失败路径都退化成"这个 tablet 必须扫"：描述符缺失、bloom 读不到、未 backfill、RPC 超时、BE 本地视图落后于快照版本 V（`design/04:232-235`）。proto 里那个字段刻意叫 **candidate 而不是 pruned** —— BE 侧任何遗漏都自然表现为"多返回候选"（安全），而不是"多剪"（错误）（`design/04:269`）。

**全设计里唯一能突破 I1 的语义路径是字节编码不一致**（谓词字面量经 Nereids 类型强制后与列的存储编码不同）—— 所以任何编码不确定就**不剪**，`DECIMAL` 直接禁掉（scale 差异会破坏逐字节相同）。代价是 DECIMAL 列永远吃不到剪枝收益，而且部分查询会**静默**失去剪枝、不报错（`design/04:121-143`、`README.md:76`）。**宁可漏掉一些本可剪枝的查询，也不能编码错一次：前者损失收益，后者返回错误数据。**

### L4｜"那在你们的场景里，哪个问题更大？"（这题是高潮，答案必须落在量级上，不是偏好上）

先给判断框架：**我不是在比较收益大小，我在比较代价的形状 —— 有界的代价可以用旋钮管理，无界的代价必须用架构消灭。**

1. **假阳性 vs 漏判**：假阳性的代价是多扫一个 tablet（**有界、可预算**，FPP 是旋钮）；漏判的代价是结果错（**无界、不可接受**）。所以整个设计只朝一个方向倒，不是保守，是这两个代价的形状不对等。
2. **写放大 vs 不加索引**：写侧是**常数级摊销**（复用已有列值流，一次 hash + 插入，零额外 IO）；不加索引是**每次点查都付 566 倍的 tablet 打开**。一个常数摊销 vs 一个每查询乘法 —— 在点查是主流量的画像下不用犹豫。
3. **缓存预算 —— 这才是我们真正付出的代价，而且它是唯一一个纪律解决不了、只能靠容量规划的。**

第 3 条要给出真实的对比，因为它是**同一块缓存上的两个正交需求**：

| | bloom 侧（INDEX 队列） | 列数据侧（NORMAL 队列） |
|---|---|---|
| 工作集 | 3–4 GiB / BE（单 BE 最坏 14 GiB） | 宽读一次 441 个 1 MiB block |
| 常驻收益 | 探测 0.03s；剪掉 565 个 tablet 的**下游全部 IO** | 每个 block 省一次 ~97ms 往返 |
| 未命中代价 | 每文件 ~100ms S3 往返，落在 **500ms plan 期预算**里；**预算爆掉就整个剪枝失效，退回全扇出** | 线性变慢 |
| 失效曲线 | **悬崖** | **斜坡** |

**结论：INDEX 队列要按「单 BE 最坏工作集」而不是「平均值」来配。** 理由是失效曲线的形状不同 —— bloom 侧是悬崖（部分常驻仍然要付冷读，而冷读吃的是 plan 期硬预算），列数据侧是斜坡（少缓存就是线性慢一点）。**给悬崖留余量，让斜坡去承受压缩** —— 剩下的全给 NORMAL，因为那边正是 43 秒宽读要吃的。

而且**两边都必须在设定这个值之前算清楚**（`design/15:247`）；配小了会把一次性冷读成本变成**永久、不收敛的 S3 账单**（`design/14:155-158`）。

### L5｜"这套东西出过事吗？"（最有分量的一段，一定要自己讲出来）

出过，preprod，而且**是一次静默失效**。

**时间线**（`design/14:49-67`）：4 BE 在灌数 → 07-28 16:09:57 缩到单 BE `be0` 做单机查询性能测试 → 16:10:32 FE daemon 给 be0 预热了**一次，这是它这辈子收到的唯一一次预热** → 两天灌数与 compaction 产生了新的 `.gpidx` → 07-30 扩回 4 BE，三台新加的 BE 拿到**全新的 BE id** → 07-31 手工跑 `gpidx_cache_check.py` 才发现：

| BE | CACHED | MISSING | WRONG_Q |
|---|---|---|---|
| 三台重新加入的 | 386–405 | — | — |
| `be0` | **0** | **313** | **73** |

**根因（P1）**：预热 daemon 维护 `Map<beId, lastStartTime>`，`lastStartTime` 没变就跳过。三台新 BE 因为 id 是新的被正常预热；be0 保留了 id 且从未重启，于是从 07-28 16:10:32 之后**每一轮都被跳过**。

> **"守住的是错的不变式。'预热过一次'对'现在还在缓存里'什么都没说。"**（`design/14:97-98`）

常驻性会被**完全不涉及重启**的事件破坏：成员变化（一致性哈希的 owner 集合移动了 tablet，没有任何进程重启）、容量压力驱逐、新数据（灌数/compaction 产生过去任何预热都没覆盖的文件）、队列放错导致的 churn。

**放大器（P4）**：`index_percent` 默认 5%，而这一步在 preprod 上**被跳过了**。单 BE 那段窗口里 be0 独自持有全部 tablet 的 bloom，约等于 4 BE 时单机足迹的 4 倍 —— **它自己就超出任何合理的 5% 预算，于是那段窗口把 07-28 那次预热的成果自己挤掉了（"自己挤自己"）**。

**三个必须一起讲的判断：**

1. **正确性全程没受影响** —— I1 成立，每条失败路径都退化成过扫，从不跳过 tablet。这是纯粹的性能与成本问题（`design/14:184-185`）。
2. **但它是静默的** —— 靠手工跑脚本才发现。所以修复的第四件事（D4）是把 `checked/resident/repaired/failed` 做成每轮 sweep 的计数器和 BE metric，**让常驻性可观测，而不是靠人想起来去查**。
3. **修复顺序本身是个判断** —— D1（先把 INDEX 队列按最坏工作集配够，纯配置）必须**先于** D3（常驻性修复回路）上线。否则任何"发现缺失就重读"的机制，在预算小于工作集的前提下，每一轮都会重读，把一次性冷读变成永久 S3 账单。

**修复的核心约束（G4/V4）**：**一次针对完全常驻的 BE 的修复 sweep，必须发出零次 S3 GET、零字节读取**（`design/15:56,106`）。这一条直接否掉了所有"按周期重读工作集"的方案：

| 被否方案 | 否决理由 |
|---|---|
| A1 每轮无条件重预热 | 违反 G4，60s 周期下约 60MB/s 永久浪费 |
| A2 BE 自主 sweep、不要 FE | **BE 不知道自己的一致性哈希归属**，会漏掉因成员变化被移到它身上的 tablet —— 正是这次事故的场景 |
| A3 FE 走 HTTP `list_cache` 检查 | 每 sweep 每 BE 上百次 HTTP，还要复制队列后缀逻辑 |
| A4 把 `.gpidx` block pin 住不许驱逐 | **把它们从预算核算里摘出去了，会让配错容量这件事变得不可见** |
| A5 只做队列扩容当配置事故处理 | 是正确的**第一阶段**，但单独不够 |

还有一个容易忽略的细节值得讲：D2 要给写路径加一个**新的** `is_index_data` 标志，而不是复用已有的 `is_index_file` —— 因为倒排索引的 writer 已经把后者置为 true，复用会**静默把所有倒排文件搬进 INDEX 队列并撑爆预算**（`design/15:124-146`）。这是"复用一个看起来对的旗标"的典型陷阱。

### L5b｜"还有别的坑吗？"——M3：整个 plan 期剪枝静默从未触发

两个独立根因，都在 FE（`design/11`）：

1. `columnFilters` 在剪枝执行的那个时点**永远是空的** —— 它只由 `computeColumnFilter()` 写入，而 `OlapScanNode` 里唯一的调用方是短路点查路径的 `lazyEvaluateRangeLocations()`，正常路径根本不走。
2. **而且"那就在 `init()` 里调一次"也修不了** —— `PhysicalPlanTranslator.visitPhysicalFilter()` 先递归子节点（在那里创建并 `init()` 了 `OlapScanNode`），**之后**才把谓词挂上去。这不是偶然，是 Nereids 翻译器"自顶向下访问、自底向上构造 fragment"的固有顺序，`init()` 时 `conjuncts` 就是空列表。
3. **而且那个天真修法是不安全的** —— 在 `init()` 期剪枝会 pin 自己的快照版本，早于查询真正读的版本（后者由 `setVisibleVersionForOlapScanNodes()` 统一 pin）。版本单调，于是 `V_prune ≤ V_scan` 恒可能；一旦 `V_prune < V_scan`，被剪的 rowset 集合是查询读取集合的**真子集** → 违反 superset 不变式 → **静默少返回行**。

**修法**：把剪枝整体移到 `ScanNode.setVisibleVersionForOlapScanNodes()` —— 物理计划已翻译完（谓词挂好了），且那里正在计算查询真实的读版本。顺带治好两个潜在性能问题：per-partition 的 MS RPC 从 O(partitions) 降到 0 次额外调用，BE 探测 RPC 从 O(partitions × BEs) 降到 O(BEs)。

**这个 bug 的类别值得点名**：一个**静默的、依赖顺序的 planner no-op** —— 编译通过、运行不报错、不打日志、就是永远不触发。而它能活到端到端测试才被发现，是因为单测 `GlobalPointProbeEncodingTest` **绕开了整条调用链**，只在隔离环境里测编码逻辑。**教训：验证要覆盖调用顺序，不只覆盖函数正确性。**

## 被否决的方案（证明这是选择，不是唯一想到的做法）

| 方案 | 否决理由 |
|---|---|
| **精确倒排 KV 存 FDB**（`hash(value) → tablet posting`） | 需要 ~200–300 GB + 50 亿次 FDB put，会压垮共享的 MS/FDB。零假阳性是它的优势，**保留为可替换后端**，如果哪天精确性成为硬需求（`design/09:7-22`） |
| **路由表 + `TABLET()` hint** | 最强的务实替代，建议作为 baseline 先量。没选它是因为 **`tablet_id` 在 split/merge/schema change/restore 后不稳定**，还需要双写与新鲜度窗口（`design/09:56-58`） |
| **转置 bloom / bit-sliced**（hash slot → tablet bitmap） | 会把 per-rowset 设计特意消灭掉的**新鲜度问题**重新引入 —— 一个可变的全局聚合必须回答"它是否已经包含刚提交的 rowset"。标为 tablet 数涨到几万时的**首选演进路径**（`design/09:72-75`） |
| **S3 上的精确 router（SST / 完美哈希）** | 工程量显著大于 bloom，等于在 Doris 里再造一个 LSM（`design/09:83-85`） |
| **FE / sidecar 内存里的剪枝目录** | 精确结构 5.4 GB 塞不进 FE 堆，等于为"省一次缓存读"引入一个新的有状态服务（`design/09:87-95`） |
| **改分桶键为 eventId 让 bucket pruning 生效** | 会打散 user_id 的局部性，牺牲现有所有按用户的查询，且要重建 50 亿行。**非目标：不改变物理分布**（`design/09:203`、`design/00:52`） |
| **bloom 落进 segment footer** | 读它就得打开 segment 文件，等于否掉"不打开数据文件就剪枝"这个全部意义 |
| **跨 rowset `BloomFilter::merge`** | 不同大小的 bloom 合并在语义上根本行不通，写了就是越界读（`design/00:102`） |

预取侧同样有一条**我删掉自己第一版实现**的记录（`01-design.md §9`）：第一版是独立预取路径（`PrefetchStage` 枚举 + 新 virtual + 自己的块折叠算术 + 4 个 config），已提交，两天后整个折进已有的 `SegmentPrefetcher`。理由：两套东西在 data page 上重叠、**两个提交者对着同一个 file cache、两套互不知情的 cap、没有共享去重**；而真正新的那个想法（meta page 预热）的正确位置在 `_init_segment_prefetchers` 之前，独立版本到不了那个代码路径。

**并且把结论反转的条件写下来了**：如果必须发在已部署的 4.0.5 上（那里 `SegmentPrefetcher` 不存在，复用意味着 backport 1,185 行 / 27 文件），"保留两套路径"才是对的。**"这个答案完全取决于一个事实：目标版本是 4.0.7 还是 4.0.5。"**

## 我为自己的方案划的边界（主动说 = 加分）

1. **预取收益未实测**，且 baseline 要在 4.0.7 上重建（见 R 节）。
2. **原本想用的验收指标不可用**：预取走 dry-run read，把 `query_id` 与 cache stats 置空，所以 profile 里 `remote_io / remote_n` 会掉到接近零 —— **IO 没有消失，它只是不再被归因了**。我不能用"每次 fetch 的延迟没变"去证明"我并行化了而不是搬运了工作量"。替代验收：数预取任务提交数，或比对前后写进 file cache 的总字节数（应持平）。
3. **step A 本身不是零 IO**：后面的 `load_ordinal_index()` 照样阻塞，只是阻塞在热缓存上。**它消掉的是串行化，不是那些读。**
4. **array 列（94 个，2.5%）phase 1 直接跳过**，理由是硬的：item 子列**根本无法预取**，因为需要哪些 item page 取决于 offset，而 offset 还没读；而现有 fallback 是 `ALL_DATA_BLOCKS`，对宽表点查是灾难性的。覆盖率 3,633/3,727 = **97.5%**（查 `information_schema.columns` 实测，无 variant/map/struct）。
5. **默认关闭**（`enable_wide_column_segment_prefetch=false`），两个 gate（≥64 列、≤128 行）保证扫描型查询完全不受影响；**代价是失去独立回滚**（一个总开关盖住两步），且动了 compaction 也走的共享代码。
6. **预取线程池是全局节流阀**：BE 级、32 worker、单查询 441 block —— 并发宽点查会**排队而不是把 S3 并发翻倍**。这是有意的。
7. **`EXPLAIN ROUTE PLAN` 的 policy 刻意不 upstream**（业务耦合七处），只有 mechanism 备成干净 PR。这条是判断题不是能力题，单独作为一个 story 讲。
