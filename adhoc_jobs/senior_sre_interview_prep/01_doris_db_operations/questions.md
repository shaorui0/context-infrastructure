## A. 架构设计题（7 题）

### Q1. 设计一个同时服务毫秒级点查和 ad-hoc 分析的数据层。

**一句定位**：这两类负载不能共享机器，所以真正要设计的不是「一个更快的引擎」，而是**物理隔离加执行前的准入判定**，因为扩容是分钟级机制而 OOM 是秒级事件。

**展开结构**：
1. 先量化负载的真实形状，不要从 benchmark 出发。我挖了 14 天生产 query_log、74.7M 行，发现远超 90% 是点查，而重查询不到 3% 却承载不成比例的算力，单查询成本比约 1,240 倍。
2. 存储层用存算分离，让计算可以物理切成两个池（常驻 serving 池 + 弹性 heavy 池），池内再用 workload group 管配额。
3. 判定必须在 plan time：执行前 6 到 8 毫秒判 heavy/light，heavy 走弹性池、light 留常驻池。
4. 安全保证不依赖判定的准确率：漏判在轻池撞固定槽位内存硬限、秒级熔断、自动升级重跑。

**挂故事**：S01 主线 + S03（负载画像）+ S04（准入路由）+ S05（弹性池）。基础点 Q1/Q29。

### Q2. 存算分离和 shared-nothing 怎么选？

**一句定位**：先拆掉一个常见误解：存算分离在 2026 已经是现代 OLAP 的默认架构，不是任何一家的独门武器，所以「要存算分离」不构成换引擎的理由，真正的分水岭是开源自建还是云托管。

**展开结构**：
1. 三个可观测差别：扩容时数据动不动、状态集中到哪一层、成本曲线的形状。
2. 我的实测锚点：serving 池 2 台扩到 4 台，移动零字节数据，tablet 归属以元数据操作 rebalance。
3. 代价要给数字：缓存部分命中差约 10%、完全 miss 差约 35%，弹性是分钟级不是秒级，新增 FDB + MetaService + Recycler 的运维面。
4. 诚实的边界表达（这句最加分）：如果核心痛点只是自建扩容太重要弹性，最小动作是迁到 ClickHouse Cloud 拿 SharedMergeTree、SQL 零改写；我们选 Doris 是因为要的是一个组合。

**挂故事**：S01。基础点 Q1/Q2/Q3。

### Q3. 存算分离引入了哪些新的失败域，HA 怎么设计？

**一句定位**：存算分离**不消除状态，它把状态集中到一层，而那一层从此不能偷工减料**，所以 HA 必须组件层和业务层两层正交。

**展开结构**：
1. 三个新的有状态失败域替换了「每台机器挂盘」：MetaService（≥3，挂了内表全停）、FoundationDB（≥3，损坏要 `fdbrestore` from S3）、Recycler（≥2，S3 GC）。
2. 元数据恢复链路深了一跳：FE BDB-JE → MetaService → FoundationDB。
3. 业务层是 compute group 做节点池级硬隔离、workload group 做 cgroup 级软隔离，解决的是 blast radius 而不是「系统还在不在」。
4. 主动交边界：`fdbrestore` 我没有实际演练过，小时级 RTO 是推断不是实测，这是我知道的最大一块没验证的地方。

**挂故事**：S01 的 L3。基础点 Q22/Q34/Q35。

### Q4. 给一个 OLAP 集群设计弹性算力（scale-to-zero）。

**一句定位**：弹性首先是一笔经济账，其次才是基础设施模式。静态池 92% 到 97% 的成本纯粹是空转时间，这笔算术就是整个模式的全部理由。

**展开结构**：
1. 成本论证先行：静态 2 节点 heavy 池 on-demand 约 $772/月，实测 burst 模式（平均每天 2 台跑约 2 小时）on-demand 约 $63、spot 约 $24。
2. 控制面收缩到一个写原语：读 CR、定位目标 compute group 下标、JSON-patch `replicas`。平台 operator 拥有状态时自建工具应该缩小，我为此重写了三次、每次都在移除职责。
3. 触发与回收要匹配执行延迟：队列去抖（`waiting_query_num ≥ K` 持续 W 秒才扩，扩完 arm cooldown）匹配 BE 约 3 到 4 分钟冷启动；回收是保守 reaper（所有 BE `currentFragmentNum==0` 且空闲超 30 分钟）。
4. 就绪判定必须分层，因为每个信号都会说谎，`SELECT 1` 会被 FE 常量折叠、空池也报健康。

**挂故事**：S05 主打，S04 提供触发信号。基础点 Q3/Q36。

### Q5. 50 亿行的宽表怎么做表设计（分区 / 分桶 / key / 索引）？

**一句定位**：分布键是唯一 ALTER 不了的决策，所以它必须由真实的谓词分布决定，而且要在提交前用 A/B 验证。

**展开结构**：
1. 定容原则先讲：单 tablet 保持 1 到 10 GB，桶数最好是 BE 数的整数倍、单分区一般不超过 128。我的取值是按天 AUTO PARTITION 加 `HASH(user_id) BUCKETS 16`，关键论证是 16 桶针对单个日分区而不是全表。
2. 分布键选择要从负载画像来：主流量是无界的取最新值重建，没有时间谓词，所以时间分区剪不掉任何东西，必须让分布键等于查询谓词的键。
3. 不可逆决策的验证方法：同数据镜像键的两表 A/B、四次测量，再在 15M / 107M / 286M 三个检查点各复测一次，证明延迟随表增长保持平坦。
4. 我踩过的反面：那张表的分桶键是 `user_id` 而另一条点查路径的谓词在 `eventId` 上，于是分桶剪枝完全失效，扇出到全部 566 个 tablet。表设计没错，错的是那条路径没被算进设计的时候。

**挂故事**：S03（A/B 与三点复测）+ S08（剪枝失效）。基础点 Q9/Q11。

### Q6. 数据层怎么做多租户隔离防 blast radius？

**一句定位**：隔离要分两级，而且要分清哪一级是硬的：compute group 是节点池级物理隔离（硬），workload group 是 cgroup 级配额（软），只有前者能保证一个租户的失控查询碰不到另一个租户的机器。

**展开结构**：
1. 为什么这在 AI 负载下变成刚需：一个 prompt 炸裂成一串并发查询，一个租户失控的 agent 查询不能拖垮整仓，这是业界公认的三个命门之一。
2. 内存维度的隔离靠 workload group 的 cgroup 硬限（`overcommit=false` 超限即 reject），这也是我选 Doris 最承重的那条论证，因为 ClickHouse 的对应机制仍是 best-effort。
3. QPS 维度的隔离在 serving 链路上是租户级限流和配额，我处置过一次大租户尖峰，做法是先降级（把非关键的 recompute/backfill 限速在线清零）再限额扩容。
4. 制度层要把成本回压给制造问题的一方：error budget 耗尽就对超预算的 user/resource_group 做配额降级，而不是让全体用户承受。这一条我写过设计，没落地。

**挂故事**：S15（QPS 维度）+ S01/S04（内存维度）。基础点 Q4/Q33/Q35。

### Q7. 给一个 OLAP 集群设计备份恢复方案，RPO / RTO 怎么定？

**一句定位**：我要先划边界，我做过的是一次跨集群恢复演练不是制度化的 DR；然后我可以讲清这套方案的结构性弱点和我认为该怎么做成制度。

**展开结构**：
1. 现状诚实交代：EBS snapshot 加 PV/PVC 置换加重启加校验，恢复量级约 5.2B 行，RPO 是 snapshot 周期隐含的约 24 小时，没有定期演练，RTO 没写成 SLO。
2. 块级快照的三个结构性弱点：块级一致不是应用级一致（恢复可能需要 crash recovery，时长不可预测）、粒度是整卷（做不了表级恢复，逻辑误删代价不成比例）、跨集群依赖 PV/PVC 置换（有状态编排里最易错的一步）。
3. 正确的分类是把「逻辑误删」和「集群级损毁」当两类故障配不同手段，而不是用一套 snapshot 覆盖两者。
4. 做成制度的四步：先定 RPO/RTO 目标再反推 snapshot 频率、恢复演练进日历且验收标准是数据面探针加业务 SQL 结果 diff、所有「判定失败」的分支都要独立的数据面复核、把恢复时长记录成指标否则 RTO 永远是拍的。

**挂故事**：S10。基础点 Q20/Q21/Q22。

## B. 故障排查题（9 题）

### Q8. 写入被拒（-235 / TOO_MANY_VERSION）怎么处理？

**一句定位**：**-235 是果，compaction score 上涨是因**，所以先看因不看果。

**展开结构**：
1. 因果链：导入频率大于 compaction 速度、rowset 和 version 持续堆积、撞到 `max_tablet_version_num`（默认 2000）就拒写。
2. 治本是减少 rowset 生成速率（攒批、降频、Group Commit），治标是调大上限（官方建议不超过 5000）并提 compaction 并行。
3. 宽表上必须保持 `enable_vertical_compaction`，按列组合并，内存只有原来的十分之一。
4. -238 是另一个错误码（单 rowset segment 数超 200），它的根因常常绕回分桶，所以先查分桶再调 segment 上限。

**挂故事**：S06。基础点 Q5/Q6/Q10。

### Q9. compaction score 飙升而且扩容重启都不动，怎么查？

**一句定位**：先分辨这个 score 是「高但在挣扎」还是「钉住不动」，这两种形状对应两类完全不同的根因，我两种都遇过。

**展开结构**：
1. 高但在挣扎（我那次约 2,500）是债务型：三因连乘（bulk load 期间关掉 auto-compaction 让债累积到单任务要合 2,506 段 × 3,727 列被 43 GB 内存 guard abort、cloud 模式无 peer cache 每段一次约 7 秒冷 S3 读、稀疏宽表 46 倍压缩衰减让段一开始就太小）。
2. 钉住不动（我那次约 4,504）是调度排除型：三条互相独立的只读调查线（日志枚举、tablet-meta HTTP 端点、catalog 回收站）收敛到一个已 DROP 表遗留的孤儿 tablet，它在结构上被排除在调度之外。
3. 加机器要先证明有没有用：日志里 632 次 no-op 唤醒对 9 次真实 merge，说明 worker 不缺任务缺，单 tablet 的 compaction 不能跨节点拆，这是 concentration-bound。
4. 修复配方是四件一起（auto-compaction 永远开、写 buffer 放大 4 倍、按月 bucket 数把 tablet 控在约 10 GB、更宽 column group 把 S3 重扫减少约 40 倍），冷点查 40 秒到服务端 100 毫秒内。

**挂故事**：S06 + S07，**必须分开讲不能混**。基础点 Q5/Q7/Q8。

### Q10. 一个亚秒级的 OOM，监控完全看不见，怎么办？

**一句定位**：换证据源，找一个时间分辨率高于故障时间尺度的源。30 秒采集对 1 秒尖刺在构造上就不可见，这不是配置没调好而是采样定理。

**展开结构**：
1. 现场取证一无所获：`SHOW PROCESSES` 和 `system.merges` 干净、内存停在约 2 GiB 基线、30 秒采集是一条平线，连报错文本 `current RSS: 8.85 GiB` 都在误导（那记录的是报错那一刻不是峰值那一刻）。
2. 破案靠引擎内部 1 秒粒度的 `system.metric_log`：基线约 2 GiB、一秒内冲到 21.60 GiB 服务上限、被 OvercommitTracker 杀、随即回落。
3. 然后问「什么东西一次性分配了 20 GiB」，答案是升级残留：改名后的 trace 日志表 1.21 TiB、profiling 日志表 308 GiB，无写者无读者但 parts 仍参与后台 merge。
4. 调大 pod 内存上限是最顺手也最错误的旋钮，因为这是无界增长型故障，调上限只推迟不阻止。

**挂故事**：S12。基础点 Q26。

### Q11. Kafka consumer lag 涨了，从哪查？

**一句定位**：**Kafka lag 通常是症状而不是病灶**，第一个分叉是分清 consumer lag 还是 mirror lag，第二个分叉是看错误码指向上游还是下游。

**展开结构**：
1. 我处理过三种不同病灶的同一症状：下游 ClickHouse 因僵尸表 merge OOM 拒写（`Code 241`）、下游 parts 爆炸触发写入 backpressure（日志 `Delaying inserting block by 10 ms because there are 1015 parts`）、topic partition 数不够导致 mirror 复制吞吐触顶。
2. 排除消费者自身：没有 OOM、没有重启、没有限流、资源正常，那重启消费者就不解决任何问题（mirror 那次就是这样，lag 在峰值过后自然收敛）。
3. 消费者失败会自我放大：失败批次进 30 秒 sleep 加 rebalance 的重试循环，同一批数据反复撞同一个失败，所以根因修完之后往往还要重启消费者打破循环。
4. per-partition 吞吐是 mirror 并行度的硬天花板，扩 partition 是不可逆操作，要先评 key 分布和 rebalance 影响。

**挂故事**：S12 + S15，另有 MirrorMaker 案例。基础点 Q37。

### Q12. 点查从 20 毫秒变成 8 秒了，怎么定位？

**一句定位**：先找一个能让候选变量消失的实验，而不是逐个调参数看变化。我用一条暖查询就把「S3 慢」这个假设推翻了。

**展开结构**：
1. 关键证据：暖查询缓存全命中、`BytesFromRemote` 总计约 139 KB（8 台 BE 里 7 台是 0），仍然 1.12 秒。所以地板与 S3 无关。
2. 时间去哪了：`OLAP_SCAN: partitions = 20/20, tablets = 566/566` 零剪枝，主导项是 `InvertedIndexSearcherSearchInitTime` 31.8 毫秒（打开 searcher）和 7,081 次 `BlockInitSeek`，因为倒排索引是 per-segment 局部索引、没有全局索引。
3. 三层可叠加可分离的成本：扇出（`A−C ≈ 114s`）、列读放大（`C−D ≈ 29.5s`，剪枝治不了）、冷 S3 列读（冷暖差 31.8s → 0.46s）。
4. 唯一同时治冷和暖的杠杆是分区剪枝，实测 69 秒到 0.9 秒；加 BE、调 scan 线程、加带宽全是错方向。

**挂故事**：S08，配 S03（bloom filter 那次同构）。基础点 Q11/Q12/Q15。

### Q13. 集群 CPU 打满，怎么归因？

**一句定位**：**绝不从单一信号源给 CPU 定根因，查询视图和线程视图必须互证。**

**展开结构**：
1. 我那次的实例：ClickHouse 节点跑到 92%（30 核用掉 27.6 核），只看 `system.merges` 得出的初判是 merge 欠债。
2. 交叉验证后结论反转：`system.processes` 配合线程级 `top -H` 显示 3 条并发 `SELECT *` 全表扫描（每条约 7 亿行）占约 67% CPU，merge 只占约 10%。
3. 处置分层：短期压低 `max_threads` 并把 `SELECT *` 改成按需列，长期给谓词列加 projection 或 bloom filter skip index。
4. 沉淀成规则写进了 case 库，这类「归因规则」比单次修复更有价值。

**挂故事**：oncall track record §1。基础点 Q25。

### Q14. 有状态组件 CrashLoopBackOff 而且 `kubectl logs` 为空，怎么查？

**一句定位**：`kubectl logs` 为空不代表没有日志，有些引擎只往容器内文件写；而 exit code 决定了你往哪个方向查。

**展开结构**：
1. 先看 exit code：137 等于 SIGKILL，加上日志里没有 JVM 的 OutOfMemoryError 栈，这说明是 cgroup 外部 kill 不是 JVM 内部 OOM，方向完全相反。我那次的根因是 `-Xmx8192m` 配上 `memory.limit` 只给 4Gi，22 小时内 142 次 OOMKill、平均每 9 分钟一次。
2. 143（SIGTERM）加空日志那次要 exec 进容器读文件日志：元数据里记了旧 pod IP，重启后 IP 变了、角色停在 UNKNOWN、查询端口不开、liveness 每 60 秒杀一次，累计 285 次重启。
3. 时间规律性本身是证据：均匀的重启间隔说明这是一个确定性过程在重复，不需要抓现场，只需要解释「为什么它总是在这个点死」。
4. 永久修法要治身份而不是治症状：headless Service 加 FQDN 注册，让节点身份不随 pod IP 漂移；quorum 参数和副本数当一对约束一起管（`electionNumber` 默认 3 而 `replicas=1` 就永远选不出 leader）。

**挂故事**：S13 + olap-fe-crashloop-ip-binding。基础点 Q18/Q36。

### Q15. 外部报 connection refused 但 pod 全是 Running，怎么查？

**一句定位**：refused 意味着链路上某一跳没人监听，所以沿链路逐跳走并**停在第一个失败的跳**上。

**展开结构**：
1. 先分错误类型，三种对应三个假设空间：refused 查监听方和转发规则、timeout 查路由和节点级出网、reset 查应用层和中间件的超时常量。
2. 逐跳：Client、DNS、NLB、NodePort、ingress-nginx、Service、Endpoints、进程。我那次断点在 `kubectl get endpoints` 返回 `<none>`。
3. 机制：operator 用 readiness label 做 endpoints 门控，pod 异常重启后 label 停在 `no`，Service selector 匹配 0 个 pod。
4. 修法让所有者收敛（rollout restart 让 operator 重写 label）而不是手改字段；机制性改进是把 `endpoints == 0 而 pod ready > 0` 这个矛盾状态做成指标，不需要阈值也不会误报。

**挂故事**：S14。基础点 Q36。

### Q16. 一条 P99 告警触发了，但你怀疑它是假的，怎么办？

**一句定位**：**先证伪真实用户影响，再解释指标。** 顺序不能反。

**展开结构**：
1. 第一步查同时间窗的应用日志和 APM：如果一条真实慢请求都没有、错误率也没抬头，那先按假告警处理。
2. 再解释指标为什么会说谎：多实例采集时间错位叠加 histogram 分桶聚合偏差，把聚合后的 P99 抬高了。
3. 结案要附完整证据链，然后加固规则（加 `for:` 持续时间、把分位数改成 recording rule、对齐采集时间），让同一偏差模式不能再呼人。
4. 相关的一个统计边界：t-digest 类分位估计对 P100 这种极端长尾是失明的，定 P999 的时候要注意统计方法本身的误差。

**挂故事**：histogram-skew-false-p99 + 延迟分解那组。基础点 Q26/Q28。

## C. 运维制度题（5 题）

### Q17. OLAP 的 SLI / SLO 怎么定？

**一句定位**：OLAP 的 SLO 和 OLTP 不一样，多了一维数据新鲜度，而且**查询延迟必须分冷热**，因为存算分离下冷查询延迟是固有代价，定一个全局阈值一定是错的。

**展开结构**：
1. 四支柱：查询可用性（99.9% 到 99.95%+，成功查询/总查询，5XX/429/超时算失败）、查询延迟（P99 缓存命中 <10s、冷/miss <60s）、导入成功率（99%+）、数据新鲜度（P99 端到端 lag <60s，拆成采集加 Kafka lag 加计算加可见性）。
2. 阈值不能拍：我那次 P95 <2s 是三条交叉验证得到的（MV 命中路径实测留 buffer、ClickHouse baseline 不能让体感退化、人因研究 2 秒是 BI 交互注意力阈值）。
3. 两视角 SLI 是我最满意的设计：同一个 metric，全局聚合是 infra 视角（系统不挂），label 切片是用户视角（我的那一份按时、成功、省钱），告警按 label 路由。
4. 诚实的覆盖率账：51 个 infra SLI 里 64% 可用、32% 缺 instrumentation，用户视角覆盖不到 10%。**讲我知道缺什么比讲我都有更可信。** error budget policy 的分级动作我写过设计，没跑满一个季度形成制度。

**挂故事**：S11（两视角 SLI）+ S01（四支柱）。基础点 Q27/Q28。

### Q18. 数据库大版本升级你怎么做？

**一句定位**：先查默认值变更，不是先查 SQL 兼容性；而且升级 runbook 的末尾必须有审计步骤，因为有些隐患是每次升级都会重新制造的。

**展开结构**：
1. 版本选择要看 patch 的修复清单：Doris 4.0.5 修 file cache 并发崩溃、4.0.6 修 Recycler OOM 并把 cloud 模式的 `enable_strict_consistency_dml` 默认关掉（破坏性变更）、4.0.7 还在修数据丢失和挂起类问题。所以关键业务钉 4.0.7 不用 4.0.0/4.0.1，4.1 线先在非核心链路验。
2. 升级顺序按传统做法先升一个副本观察再滚动，但对 quorum 型组件要先确认副本数和 quorum 参数一致。
3. runbook 末尾加审计：ClickHouse 升级会把旧系统日志表改名加后缀、从不删除，累积出 1.21 TiB 的僵尸表并引爆亚秒级 OOM。
4. 一处确诊全 fleet 扫，因为升级残留是横向缺陷、成因是升级动作本身。那次扫出最严重集群 1.65 TiB、另一 region 兄弟集群 250 GiB 且已经每天 3 次 OOM。

**挂故事**：S12。基础点 Q38。

### Q19. 一次几十亿行的迁移，正确性门禁和回滚点怎么设计？

**一句定位**：三层保证加月级回滚点，而且**验证方法本身要工程化**，因为我的对账查询真的打挂过 8 台 BE。

**展开结构**：
1. 三层：行数层（每月无损门禁，各切片行数之和等于重新计算的当月总数，对不上就告警且不标记完成）、原子性层（watchdog kill 的 load 提交为空）、去重层（Unique Key + MoW 让重试幂等）。
2. 回滚粒度是月：每月独立可重跑，流水线按字节预算调度、每对象 checkpoint、任何时刻可安全 kill，所以中断损失上限是一个月的进度。
3. 对账方法要重新设计：几十亿行宽 MoW 表上朴素 `COUNT(*)` 要合并 delete bitmap，会超时甚至打挂集群，所以按月分区计数并调高 timeout。**验证工具也是生产负载。**
4. 结果 99.945%（5,170,688,484 / 5,173,508,562），0.055% 缺口逐行归因到去重语义。**差异和丢失是两件事，能把差异逐条解释掉才叫对账完成。**

**挂故事**：S09 + S02（管线设计）。基础点 Q41。

### Q20. 不可逆的数据层操作怎么管？

**一句定位**：先列清哪些是不可逆的，然后按「不做的代价是否持续且用户可见」决定当场做还是走评审，判据不是这个动作有多方便。

**展开结构**：
1. 我的一组对照：MirrorMaker lag 那次没扩 partition（峰值过后 lag 会自然收敛，所以标不可逆、评 key 分布、走评审），大租户 QPS 尖峰那次扩了（在场的是持续的用户可见影响）。
2. Doris 侧最典型的不可逆决策是分布键，所以我在提交前跑了两表 A/B 加四次测量，再在三个数据量检查点复测。
3. 应急旋钮必须有明确上限加成文回滚方案（消费线程池 40 核心 / 80 上限），恢复要逐级（0 到 2 到 5 到 10）不能一把恢复。
4. 我自己的一条硬规矩：诊断阶段严格只读，写操作要有明确假设和预期效果才做。这条规矩在 DR 恢复那次救过一次大场面，当时下一步就是破坏性重跑。

**挂故事**：S15 + S03 + S10。基础点 Q40。

### Q21. 你怎么把 oncall 经验沉淀下来？

**一句定位**：沉淀的单位不是「修复步骤」而是「归因规则」，因为步骤会过期而判别方法不会。

**展开结构**：
1. 结构是症状、定位、修复、教训四段，保留完整因果证据链，去掉客户和集群标识。目前是 21 份完整调查记录（其中 20+ 是生产 P1/P2）、16 份 runbook、15 张快速分诊卡、7 棵 debug-tree、4 个根因模式、3 份 checklist。
2. 按失败域索引而不是按组件索引：路由/DNS/入口链路、调度/容量/节点压力、有状态系统承压、可观测性假信号、身份权限、变更管理、过载与大租户尖峰。这样新 case 能直接路由到既有 debug-tree。
3. 最有价值的产出是几条可迁移的规则：CPU 归因不许只看单一信号源、多租户同一分钟以同一机制失败是集群级信号、quorum 系统 liveness 必须保守、无界增长型故障调上限不是解。
4. 诚实的空白：身份/权限/访问控制这一域目前只有 runbook、没有蒸馏 case。

**挂故事**：全部 oncall 类故事（S10、S12 到 S15）。

## D. 权衡判断题（6 题）

### Q22. 举一个「加机器没用」的例子。

**一句定位**：我有三个，而且它们的机制各不相同，共同点是**先分清瓶颈是 concentration-bound 还是 resource-bound**。

**展开结构**：
1. compaction 积压：日志里 632 次 no-op 唤醒对 9 次真实 merge，说明 worker 不缺任务缺，单 tablet 的 compaction 不能跨节点拆。在任何人花钱之前证明掉。
2. 点查扇出：单 tablet 点查跑在 1 个 BE、LIMIT 点查 parallelism 被强制为 1，我实测 4→16 BE 对点查约等于 0（对全表冷扫才有 1.5 倍），而且 rebalance 还会制造更多冷缓存。
3. 内存类故障：调大 pod 内存上限对无界增长型故障只是推迟；宽表迁移的 livelock 内存随累积表大小增长，所以加内存必然再撞上。
4. 通用判据：看空转的 worker 有多少，如果 worker 大量空转而积压仍在，加 worker 一定没用。

**挂故事**：S06 + S08 + S12/S02。基础点 Q7。

### Q23. 分类器准确率不到 100%，你怎么保证不 OOM？

**一句定位**：分类器不是防 OOM 保证，它是准入控制的第一道筛；真正的保证是运行时的内存硬限加秒级熔断。

**展开结构**：
1. 两类错的代价不对称：漏判 heavy 等于 OOM 等于安全事故，误判 light 只是浪费容量，所以我追 recall 不追 overall accuracy。
2. 三层防御：L1 plan 期分类、L2 workload group 硬限（`overcommit=false` 超限即 reject、约 404 MB 固定槽位、约 3 秒熔断）、L3 自动升级 heavy 池重试加 audit。
3. 想通这一点之后的连带收益：分类器可以「够用就停」，可以用规则不用 ML（准入控制是安全关键，不可解释在这里是负债，而规则能输出 reasons 数组供审计），可以接受阈值不完美。
4. **一个声称 100% 准确的路由方案才是我会怀疑的。** 我能告诉你剩下那部分具体是什么、为什么 ML 和更多信号都修不了（运行时数据倾斜、并发、cache、UDF、spill、正则 CPU 炸弹），以及为什么这恰恰证明 L2 兜底是必须的。

**挂故事**：S04。基础点 Q29/Q30。

### Q24. spot 用在数据层的边界在哪？

**一句定位**：按池分治，而且决策要锚定实测 node-hours 而不是「spot 便宜」的教条。

**展开结构**：
1. serving 池永远不上 spot：一次回收等于查询中断加缓存清空。
2. heavy 池在构造上容忍中断：FE 约 2 秒心跳检测到 backend 失联、锁约 7 秒释放、失败查询重试一次，全部落在 spot 2 分钟回收窗口内；spot 价格比 on-demand 低约 62%。存算分离让杀 spot 节点安全，因为 BE 没有本地数据、不需要 DECOMMISSION。
3. 但反过来的账也要算：floor-0 已经让 on-demand 的绝对成本很小（约 $63/月），而一条 60 到 500 秒的重查询中途被回收浪费的是已完成的工作加约 3 到 4 分钟的重新扩容。
4. 实际决策：装好 node-termination handler 之前先用 on-demand，之后切 spot 优先的混合 ASG 加 on-demand 兜底。所以我讲的是决策框架，不是已经跑在 spot 上。

**挂故事**：S05。

### Q25. 什么该 upstream，什么不该？

**一句定位**：**engine emits data, caller decides policy。** mechanism 属于上游，校准过的 policy 不属于，而判断什么不该贡献也是贡献的一部分。

**展开结构**：
1. 背景：leadership 最初想把分类器和估算机制一起贡献上游。
2. 我逐行读完分类器列出七个具体的业务耦合点：workload group 锚定的内存阈值、5,000 万行 heavy 判定线这类校准常数、recall 优先的风险姿态、公司特有的查询形状、私有 fork 字段。
3. 反驳用的是第一个 PR 自己的设计原则，把 policy 塞进上游会自相矛盾。
4. 结果：mechanism 打成 8 commit 的干净 PR 对着 synthetic base branch，diff 恰好是 feature 本身；policy 留内部归档、从不提议 merge。措辞纪律：这是 engine-level work on an Apache Doris fork, prepared as an upstream PR，PR 没 merge 之前我不说 contributed to Apache Doris。

**挂故事**：S04 的 L5。

### Q26. 讲一个你算错的东西。

**一句定位**：我有一串，而且我认为**一个数字每次重测都变得更不好看，通常说明你正在收敛到真相**。

**展开结构**：
1. Benchmark 撤回：早期结果显示 Doris 在聚合上打赢 ClickHouse 3 到 5 倍，我自己 red-team 之后找到混淆变量（一台负载中的 8 核生产节点对一台隔离的 14 核 benchmark 节点），主动撤回了这个倍数。而且我查过公开的「Doris beats ClickHouse 6-40×」全部溯源到厂商自己，一手 ClickBench 数据说 ClickHouse 在平表扫描上仍然领先。
2. 直觉错误：「小切片等于小内存」是错的，内存等于 `row_group 行数 × 列数`。如果重来我会先做一个 10 到 15 分钟的单切片端到端验证再信任全量。
3. 规范级 bug：LIMIT 盲区，计划里任何位置出现 LIMIT 都会压制「扫描过大」的 heavy 信号，但 LIMIT 只约束 blocking 算子的输出、不约束底层扫描。parity 网兜不住它，因为 parity 只证明 Java 等于 Python、不证明规范本身正确。
4. 认知修正：我一开始担心 4.0.5 没有持久化缓存元数据、重启后冷读周期复发，现场核实之后这个担心不成立（`clear_file_cache=false`、LRU dump/replay 已 backport、缓存盘是 EBS 持久卷），铁证是同一块盘从重启后 2% 累积到 61%。于是我把升 4.1 的性价比下调了。

**挂故事**：S01 的 L5 + S02 的 L5 + S04 的 L5 + S08 的 L5。

### Q27. 如果重做这个项目，你会怎么做？

**一句定位**：三件事，一件是顺序，一件是缺口，一件是我不会改的。

**展开结构**：
1. 顺序会改：先做一个单切片的端到端验证（export、检查 footer 能不能加载、load 不 OOM、对账，约 10 到 15 分钟）再信任全量。我实际是先大规模跑然后才发现读侧的 footer 问题，这是可以避免的返工。
2. 缺口会补：迁移对账只证明行数对得上，不证明语义对得上，也不证明**查询结果等价**。正确的做法是抓 top N 条真实业务 SQL 在两边跑做结果 diff，那才是用户真正感知的一致性。这个方法我在 StarRocks 到 Doris 的验收里用过（抓 top 50 BI SQL 看 MV 命中率，≥80% 即过，1 到 2 人天），但迁移对账里没做。
3. 还会补的是宽表建表前的一个必测量：memtable 到 segment 的压缩比。它同时决定 write buffer、bucket 数和 compaction 的可行性，而它不在任何 sizing 文档里。
4. 不会改的是两条判断：路由是准入控制不是性能优化，所以分类器可以不完美；以及先证明静态方案结构性不可能再动引擎（承重的数字是 27% 的 heavy-miss 率这个安全问题，不是 45% 准确率这个头条）。

**挂故事**：S02 + S09 + S04。
