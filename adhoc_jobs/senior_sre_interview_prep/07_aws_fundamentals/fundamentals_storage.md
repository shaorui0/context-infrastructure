# AWS Fundamentals：Storage (EBS / S3 / EFS)

这一节的考点在哪：存储这块我有两个真正扎实的锚点：一个是 5.2B 行的 EBS snapshot 恢复演练（DR 故事，讲快照恢复的性能语义最有说服力），一个是 Doris 存算分离下 BE 本地 EBS/NVMe 当 file_cache、S3 当冷存储的真实性能数字（讲存算分离的性能模型最有说服力）。面试官如果往深了问存储，大概率会问到"快照恢复是不是瞬间可用"和"S3 当冷存储到底有多冷"，这两条我都能给出实测数字，不是背概念。

## 1. EBS 卷类型选型

**面试官会怎么问**：gp2/gp3/io1/io2/st1/sc1 怎么选？

**标准答案（理论骨架）**
- **gp3（通用型 SSD，当前默认推荐）**：baseline 3,000 IOPS + 125 MB/s 吞吐，**与容量大小解耦**，可以独立按需加购 IOPS（最高 16,000）和吞吐（最高 1,000 MB/s），不像 gp2 那样"容量越大 IOPS 越高"的耦合模型。
- **gp2（通用型 SSD，旧世代）**：IOPS 与容量强绑定（3 IOPS/GB，最低 100，最高 16,000），小卷 IOPS 低是常见坑；有 burst credit 机制（小卷可以突发到 3,000 IOPS，credit 耗尽后回落到基线）。
- **io1/io2（预置 IOPS SSD）**：需要极高且稳定 IOPS/低延迟的场景（大型 OLTP 数据库），可预置到远高于 gp3 上限的 IOPS（io2 Block Express 可到 256,000 IOPS），代价是价格最高。
- **st1（吞吐优化 HDD）**：大吞吐顺序读写场景（大数据、日志处理），不支持随机小 IO 场景，没有引导盘用途。
- **sc1（冷 HDD）**：最低成本、访问频率很低的数据，吞吐和 IOPS 都最低。
- 选型判据：先看访问模式（随机 vs 顺序）、再看延迟敏感度、再看是否需要独立扩展 IOPS 和吞吐（这是 gp3 相比 gp2 的核心卖点）。

**我的场景锚点**
- Doris BE/CN 节点本地缓存盘是 **1.3TB nvme**（`/dev/nvme2n1` → `file_cache`），8 台 BE 聚合 8×1.3=10.4TB，装得下 4TB 的表（`doris_wide_table_point_query_optimization_survey_20260724.md` §1）。这里的本地盘更接近 instance store NVMe 而非 EBS 卷本身（instance store 是随实例生命周期存在、断电清空的本地物理盘，不是 EBS），这个区分本身是一个值得讲清楚的细节：BE 用它做 cache 而非持久层，正是因为它不需要 EBS 的持久性保证，tablet 的持久层是 S3。
- `⚠️ 待确认`：BE/CN 节点如果还挂了独立 EBS 卷做其他用途（比如系统盘），具体类型（gp3 还是别的）没有素材佐证，不编造。

**如果被追问到边界**：能讲清 gp2/gp3 的解耦逻辑和 io1/io2 的适用场景，但没有一手证据说我们生产环境里为哪类工作负载精确选型过 io1/io2，这条是`[理论应用]`。

## 2. EBS 性能模型

**面试官会怎么问**：EBS 的 IOPS 和吞吐上限是怎么算的？卷大小和性能有什么关系？

**标准答案（理论骨架）**
- gp2：IOPS = 容量(GB) × 3，上限 16,000（容量超过约 5,334GB 才能打满上限而不用 burst），burst credit bucket 满 5.4M credit，耗尽后回落基线 100 IOPS。
- gp3：baseline 独立于容量（3,000 IOPS/125MB/s），超过这个基线需要显式加购，且加购的 IOPS/吞吐有自己的上限（16,000 IOPS / 1,000 MB/s），单卷理论上限受实例类型的 EBS 带宽上限二次约束（哪怕卷本身能给更高 IOPS，挂在小实例上也会被实例级 EBS 带宽封顶）。
- io1/io2：IOPS 独立预置，不依赖容量，但有 IOPS:容量 比例上限（如 io1 最高 50:1）。
- 关键心智模型：**卷的 IOPS/吞吐上限和挂载它的实例的 EBS 带宽上限是两个独立的天花板，实际性能是两者的较小值**，选型时容易只看卷规格忘了看实例规格。

**我的场景锚点**：这条是纯理论骨架，`[理论]`，没有素材佐证我们对 Doris BE/CN 节点做过这类容量×实例带宽的联合建模；但这是一个非常适合"用我的场景反推"的问题：如果面试官问"你们 BE 节点本地盘会不会被 EBS 带宽封顶"，诚实答法是"我们用的是本地 NVMe instance store 不是 EBS，所以不受 EBS 带宽上限约束，这也是选它做 cache 而不是选 EBS 卷的一个隐含理由"，这个回答体现了懂两者区别，而不是硬编一个具体数字。

## 3. EBS Snapshot 语义（本节最重，对应 5.2B 行 DR 故事）

**面试官会怎么问**：EBS snapshot 怎么工作的？从 snapshot 恢复的卷是不是马上就有完整性能？

**标准答案（理论骨架）**
- **增量语义**：第一个 snapshot 是全量，之后每个 snapshot 只保存自上次 snapshot 以来变化的 block（增量存储在 S3，AWS 管理，用户不直接看到底层结构），删除中间的 snapshot 不影响其他 snapshot 的完整性（AWS 内部做了依赖关系管理）。
- **跨 region 复制**：snapshot 可以 `copy-snapshot` 到另一个 region，是异步的对象存储级复制，用于跨 region DR。
- **Lazy load 与 initialization 惩罚**：从 snapshot 创建的新卷，**默认是懒加载**的：卷立即可用（可以挂载、可以读写），但第一次读取每个 block 时，如果这个 block 还没有从 S3 拉取到 EBS 层，会触发一次从 S3 的懒加载读取，带来额外延迟。这意味着"卷恢复完成"不等于"卷性能已经是稳态"，第一轮全量扫描（比如一次 `COUNT(*)` 或全表 GROUP BY）会比之后的稳态查询慢，因为它在过程中把大部分 block 强制预热了一遍。AWS 提供 Fast Snapshot Restore (FSR) 来预先把卷完全物化掉，避免这个懒加载代价，但 FSR 本身按小时+按 AZ 计费。
- 这条对任何"读快照恢复完成时间"类型的 SLA 声明都是致命的隐藏变量：如果不做 FSR 或不预热，"恢复完成"时刻的读性能远低于稳态。

**我的场景锚点（DR 故事的性能证据链）**
- 5.2B 行 prod EBS snapshot 恢复到独立卷，做了量化验证：恢复后跑 `count` 用时约 50 秒、`GROUP BY` 用时约 83 秒（`mining_notes.md`）。这两个数字本身就是"懒加载代价"的实测证据：它们不是纯查询计算时间，而是包含了大量 block 首次从 S3 懒加载的时间，这也是为什么验证环节特意选了会扫全表的查询（`COUNT(*)`、`GROUP BY`）而不是索引点查：点查只会命中少量 block，无法暴露懒加载对全表扫描的拖累。
- 这次 DR 演练用的是 MySQL/ClickHouse 的通用数据拷贝路径：**创建 EBS snapshot → 从 snapshot 恢复新卷 → 替换 PV/PVC → 挂载完成**（`reference-data-copy-snapshot-backup-restore.md`）。这条路径同样用于日常的跨集群数据拷贝（copydata 工作流），不是 DR 专用的特殊流程，这也是为什么我对这条路径的语义有把握：它是我在日常 oncall 里会直接接触的机制，不是仅存在于一次性演练里的知识。
- 诚实边界（严格按纪律执行）：这是**一次性 DR 演练，不是制度化的定期 DR 流程**；RPO ≈ 24h 是从"用日常 snapshot 频率"隐含推出的，不是一个写死在 SLA 里的承诺数字。被问"你们 DR 的 RPO/RTO 是多少"时，诚实答法是"我们做过一次全量恢复演练并验证了数据完整性和查询正确性，但这不是每天/每周跑一次的制度化 DR 演练，RPO 取决于日常 snapshot 频率，我们没有把它写成正式的 SLA 承诺"。

**如果被追问到边界**：如果问"你们怎么处理懒加载导致的恢复后首次查询慢"，诚实答法是：这次演练本身就是在验证"能不能恢复、数据对不对"，还没有走到"生产切换前要不要用 FSR 预热"这个更细的运维成熟度阶段，这是一个可以主动承认的改进空间，而不是不懂这个机制。

## 4. EBS 多挂载与 CSI Driver

**面试官会怎么问**：K8s 里 PVC 怎么对应到 EBS 卷？PVC 扩容有什么坑？

**标准答案（理论骨架）**
- EBS CSI Driver 是 K8s 和 EBS 之间的桥接：PVC 创建触发 CSI 建 EBS 卷 → attach 到 Pod 所在的 EC2 实例 → mount 进容器。
- 常见坑：`StatefulSet` 的 `volumeClaimTemplates` 里的 `storage` 字段**只在 PVC 首次创建时生效**，后续修改 StatefulSet spec 里的 size 不会自动扩容已存在的 PVC（K8s 的已知限制，需要单独对存量 PVC 做 `kubectl edit pvc` 或走支持在线扩容的 StorageClass 走扩容流程）；这是很多团队第一次遇到"改了 YAML 但没生效"的来源。
- EBS 本身不支持多实例同时挂载读写（EBS Multi-Attach 仅限特定 io1/io2 场景且要求应用层自己做并发控制，通常配合集群文件系统），绝大多数场景 PVC 是单 Pod 独占挂载（`ReadWriteOnce`）。

**我的场景锚点**
- 我们生产确认使用 **EBS-backed StorageClass**，`allowVolumeExpansion: true`，PVC 在线扩容**不需要重启 StatefulSet**（"online-resize clusters"，2026-02-25 daily record）。这条是我实际验证过的机制，不是理论：gp2/gp3 的 StorageClass 支持在线扩容是我们生产 oncall runbook 里写明的选项之一（ClickHouse 磁盘空间紧张时的标准处理路径之一）。
- `StatefulSet volumeClaimTemplates` 首建后不可变这条本身是通用 K8s 知识`[理论]`，我没有素材直接证明我们踩过这个具体的坑（区别于 EBS 层本身的在线扩容能力，这是两回事：EBS 卷可以在线扩容，但 K8s StatefulSet 的模板字段不会因为你改了 YAML 就自动改动存量 PVC，两者不冲突）。

## 5. S3 一致性模型

**面试官会怎么问**：S3 现在是强一致的吗？这意味着什么、不意味着什么？

**标准答案（理论骨架）**`[理论]`
- 2020 年 12 月起，S3 对所有操作（PUT 新对象、覆盖 PUT、DELETE）提供 **强读后写一致性（read-after-write consistency）**：写入成功后，任何后续的 GET/LIST 都能看到最新版本，不再有旧版本的"最终一致性"窗口。
- **不意味着**：跨 region 复制（S3 Cross-Region Replication）仍然是异步的，目标 region 看到最新数据有传播延迟；客户端本地缓存、CDN（CloudFront）缓存的 TTL 窗口也不受这条一致性保证约束；一致性保证的是 S3 服务本身的读写路径，不是你架在它上面的任何缓存层。

**我的场景锚点**：这条对我们最直接的应用场景是 Doris file_cache：BE 本地 file_cache 是 S3 数据的本地缓存副本，S3 强一致只保证"直接读 S3 能读到最新写入"，不保证"file_cache 里的旧副本会自动失效"，缓存失效/刷新是 Doris 引擎自己的机制（TTL pin、LRU），与 S3 一致性模型是两层独立的问题。这个区分本身是一个能体现理解深度的点：不要把"S3 强一致"和"我的缓存一定是新的"混为一谈。

## 6. S3 存储类与生命周期

**面试官会怎么问**：S3 有哪些存储类？生命周期策略怎么设计？

**标准答案（理论骨架）**`[理论]`
- Standard（高频访问）→ Standard-IA/One Zone-IA（低频访问，读取有额外费用）→ Intelligent-Tiering（自动按访问模式在多个层之间迁移）→ Glacier Instant/Flexible/Deep Archive（归档，检索延迟从毫秒到数小时不等）。
- 生命周期策略：按对象年龄或前缀设置自动转换层级或过期删除规则，典型模式是"30 天后转 IA，90 天后转 Glacier，365 天后删除"。

**我的场景锚点**：我们 VictoriaMetrics 的冷存储用 S3 做 5 分钟降采样数据的长期存储（180 天约 25GB，`p_vm_platform.md`），这是"S3 当低频访问冷存储"的真实用法，但素材里没有证据表明这部分 S3 数据配置了显式的生命周期策略（比如降采样数据是否会进一步转 Glacier 或过期删除），`⚠️ 待确认：VM 冷存储 S3 数据是否配置了生命周期策略`。Doris 的 S3（Iceberg on S3，见 `case_study_ch_to_doris.md`）是热路径直接依赖的存储层，不适用"冷数据归档"这个语义，这两个 S3 用法在我们架构里是完全不同的角色，回答时不要混着讲。

## 7. S3 请求成本模型与前缀分片

**面试官会怎么问**：S3 的请求费怎么算？为什么要做前缀分片？

**标准答案（理论骨架）**`[理论]`
- S3 按请求类型计费：PUT/COPY/POST/LIST 一类价格，GET/SELECT 另一类价格（通常 PUT 类比 GET 类贵约一个数量级），大量小对象的频繁读写会让请求费超过存储费本身。
- 现代 S3（2018 年后）已经对前缀做了自动分区，不再强制要求"加随机前缀避免热点"这个老讲法（这是很多人还在用的过时知识点），但极高请求速率（每秒数千次以上）的场景下，AWS 仍建议提前联系支持做分区预热，或者业务层面本来就该考虑请求聚合（比如批量 GET 而不是逐个小对象 GET）。

**我的场景锚点**：真实的存算分离冷读性能数据是我们最有说服力的证据：`⚠️ 冷读聚合吞吐 ~1MB/s，瓶颈是 GET 延迟 × GET 数量，不是带宽`（`doris_wide_table_point_query_optimization_survey_20260724.md` §2.2），这直接印证了"S3 请求数量是瓶颈"这条理论：加带宽/调 IO 速度是错误方向（冷读聚合吞吐只有约 1MB/s，NIC 带宽用不到 1%），真正的成本大头是大量小 GET 请求的延迟串行叠加，而不是单个请求的传输量。这是我能把"S3 请求计费模型"和"S3 请求延迟模型"两个维度都讲清楚、且有实测数字支撑的少数几个点之一。

## 8. S3 与存算分离（Doris file_cache，本节第二个真实数字支柱）

**面试官会怎么问**：存算分离架构下，S3 当存储层性能怎么样？本地缓存解决了什么问题、没解决什么问题？

**我的场景锚点（先讲场景，这条几乎是纯一手证据）**
- 存算分离确认形态：`s3_default_vault`，bucket 在 us-west-2，BE 本地 file_cache 用 1.3TB nvme，8 台 BE 聚合 10.4TB 装得下 4TB 源表。
- **根因模型（面试最值钱的一段）**："扇出是地板，S3 是冷路径乘数"：一次 `WHERE eventId=` 点查要探遍全部 566 个 tablet / 6689 个 segment 的倒排索引；现场实测**暖查询（缓存全命中、几乎 0 次 S3 读）仍然要 1.12 秒**，证明扇出本身就是成本地板，S3 只是冷路径上叠加的乘数，不是唯一瓶颈。
- **冷 vs 暖对照**：冷读到暖读，单条链路耗时从约 31.8 秒降到约 0.46 秒（那约 30 秒全部是冷 S3 列读，命中 file cache 即塌成亚秒）；naive 多扫的 565 个 tablet 从 S3 冷探倒排索引，额外耗时约 114 秒（`A − C ≈ 114s`）。
- **4.0.5 版本的一个真实修正**（现场核实过，值得讲，展示"我会去验证假设而不是假设成立"）：早期担心"4.0.5 重启后缓存清零、冷读复发"，现场三重证据证否：`clear_file_cache=false`（重启不删缓存数据）、LRU dump/replay 已启用（缓存元数据已持久化，该能力已 backport，非 4.1 独有）。修正后的结论是：冷读只在两种情况发生：全新/久未访问的数据，或者未剪枝时的扇出地板本身（暖查未剪枝仍约 1.12 秒，要开全部 6689 个 searcher），**两者都只有查询剪枝能治，缓存治不了扇出**。

**这一条的价值**：它证明我不只是"知道存算分离有本地缓存这回事"，而是亲自定位过"缓存命中率高≠查询快"这个反直觉结论，并且用现场实测数据推翻了自己一开始的错误假设（4.0.5 缓存清零问题）。这是整个 07 方向里最强的一条一手证据。

## 9. EFS 适用边界

**面试官会怎么问**：EFS 和 EBS 怎么选？什么场景用 EFS？

**标准答案（理论骨架）**`[理论]`
- EFS 是网络文件系统（NFS v4），支持多个 EC2/Pod 同时挂载读写（`ReadWriteMany`），弹性自动扩缩容量不需要预置大小；代价是延迟比本地 EBS 高一个数量级，吞吐模式（bursting/provisioned）需要按访问模式选择，不适合高 IOPS 随机读写的数据库工作负载。
- 典型场景：多 Pod 共享的配置/静态资源、CI 构建缓存、需要跨 AZ 共享文件的传统应用迁移；不适合的场景：数据库数据目录（延迟不匹配）、超高吞吐单一大文件顺序写。

**我的场景锚点**：`[纯理论，无一手经验]`，评估记录里没有找到我们生产使用 EFS 的证据。如果被问"你们用 EFS 吗"，诚实答法是"我们的持久化需求主要是数据库类（EBS PVC）和对象存储类（S3 做冷数据/存算分离），没有 ReadWriteMany 的强需求场景，所以没有引入 EFS"。

## 10. Instance Store 与 Spot 的组合

**面试官会怎么问**：Instance store 和 spot 一起用有什么要注意的？

**标准答案（理论骨架）**
- Instance store 是物理挂载在宿主机上的本地盘，生命周期与实例绑定：实例 stop/terminate 时数据丢失（reboot 不丢），这与 spot 中断（本质是 terminate）叠加意味着 instance store 上的数据在 spot 回收时必然丢失，只能承载可重建/可丢弃的数据（缓存、临时 scratch 空间）。
- 这正是"存算分离 + instance store 做 cache"这个组合成立的前提：数据丢了不影响正确性（S3 上还有权威副本），只影响性能（缓存要重新预热）。

**我的场景锚点**：这正是 Doris CN heavy 池的真实组合：本地 nvme（instance store 语义）做 file_cache，节点跑在 spot 上，节点被回收即数据丢失但无正确性风险，因为 tablet 权威数据在 S3。这条把第 1/4/8 三节的知识串成一条完整的架构论证链：**instance store 特性 + spot 生命周期 + 存算分离架构，三者互相成就，缺一个都不成立**。如果被问"spot 上跑 instance store 缓存会不会有一致性问题"，答案是不会，因为缓存从设计上就是"可丢弃、可从权威源重建"的角色，这条边界我能讲清楚。
